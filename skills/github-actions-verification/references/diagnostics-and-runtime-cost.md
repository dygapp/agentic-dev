# 诊断与运行成本控制

## 目的

当 GitHub Actions 的失败日志不足、环境准备异常耗时、运行任务被新提交淘汰或不同运行任务争用共享外部资源时，本参考说明如何让 CI 产生足够诊断证据，同时控制无价值等待、重复成本和资源竞争。

## 显式超时

不要把平台默认最大时长当作正常失败边界。

根据正常基线设置：

- Job 级超时；
- 高成本环境准备 Step 超时；
- service startup / health-check 超时；
- browser / E2E 超时。

超时的目标是区分“正常慢”与“当前运行环境已失去继续等待价值”，不是为了机械追求更短。

## 取消过期运行任务并匹配共享资源并发边界

当同一 PR / ref 出现新提交时，如果旧运行任务已不能证明最新状态，应使用当前仓库策略允许的并发 / 取消机制终止过期工作。

常见 GitHub Actions 配置：

```yaml
concurrency:
  group: <stable-pr-or-ref-key>
  cancel-in-progress: true
```

具体 `group` key 由使用方工作流决定，不在 Skill 中固定。

稳定 PR / ref key 解决的是“同一逻辑工作的新运行任务淘汰旧运行任务”。如果不同 ref 会取得同一个固定域名、代理名、端口、部署槽位、评审环境或临时数据库，该 key 仍可能比真实冲突域更窄。

此时应以共享资源标识或环境槽位建立排他边界，例如：

```yaml
concurrency:
  group: review-environment-<stable-resource-key>
  cancel-in-progress: <true-or-false-by-consumer-policy>
```

要求：

- 每个可能使用同一资源的触发路径 / ref 采用同一资源 key；
- 资源不同的运行可以使用不同 key，避免无必要的仓库全局串行；
- 长生命周期单实例环境显式记录当前所有者、用途、目标 Head、租约开始 / 续期 / 到期 / 释放和过期判定；不能只从运行任务是否仍为 `in_progress` 推断人工评审会话仍然有效；
- PR 自动验证通常只保留完成自动检查和外部地址验证所需的短生命周期；人工评审可以拥有更长且可观察的租约，但具体时长与续期信号由使用方仓库策略决定；
- 保护有效人工租约与让最新 Head 取得环境是不同目标。只有当前策略判定新运行任务取代旧工作，且释放闭环可靠时才启用 `cancel-in-progress`；否则有界排队或升级真实优先级冲突，不默认采用 `latest-head-wins`；
- key 只协调 GitHub 运行任务，不能单独证明外部资源已经释放；
- 运行任务被取消或进程退出后，按正常释放基线进行有界观察；若资源残留，只在所有者、租约 / 活跃状态、环境和授权明确时执行有界重试、释放或接管；
- 一次性解锁 / 恢复工作流应使用最小权限、记录目标资源和旧所有者，使用后删除或禁用；它不能成为绕过正常所有权策略的长期后门；
- 取得资源后重新读取所有者 / 状态，并验证对外地址或目标服务实际可用且对应当前运行任务 / Head。

如果资源所有者不明确，或处理需要清理生产资源 / 其他所有者的资源，应停止该项操作并升级，而不是通过扩大破坏性清理绕过竞争。

## 失败诊断 Artifact

如果 Agent 无法稳定读取完整 Job 日志，或远程运行环境的关键状态不在默认日志中，应优先让工作流生成可下载的最小诊断 Artifact。

容器化运行环境常见诊断包括：

```text
container/service list
container inspect
container logs
health-check result
network / port state
application startup logs
```

浏览器验证常见诊断包括：

```text
trace
screenshot
video when useful
test report
console / network evidence
```

后端或数据库验证可以按需保留：

```text
application logs
migration status
schema / health evidence
failing test report
```

这些条目代表实际命令、产物或日志类别时保持原样。

## 诊断流程

推荐：

```text
观察失败
→ 检查可用 Job / Step / 日志
→ 证据不足？
   → 增加最小诊断
   → 重新运行
   → 下载 / 读取 Artifact
→ systematic-debug
→ 最小根因修复
→ 重新取得当前验证证据
```

不要使用：

```text
Step 名称看起来可疑
→ 猜测根因
→ 随机修改
```

## 运行时观察与完成状态

人工提供的 UI 截图、可见日志、持续时间或人工取消记录，可以证明当前运行环境发生异常，也可以支持：

- 中止；
- 改道；
- 增强诊断；
- 调整验证策略。

但被卡住、取消或失败的运行任务不能作为完成通过证据。

## Artifact 的临时证据与持久输入边界

不要因为 Artifact 已通过人工复核，就让长期导入流程、评审环境或运行环境永久依赖该 GitHub Actions 对象。先判断角色：

| 角色 | 适合的载体与生命周期 |
|---|---|
| 单次运行证明 / 传输 / 诊断 / 评审快照 | 当前 Run Artifact；允许受 retention / expiry 约束，但要保留 Run、Head、名称 / ID 和 digest 等证据引用 |
| 已被适当权威接受、后续稳定消费的输入 | 使用方可长期发现和维护的版本化来源 / 权威载体；不以临时 Artifact 作为唯一来源 |

晋升的平台实现可以是将已接受内容无损复制、解包或重组到使用方选择的持久载体，但必须：

1. 在复制前后核对 digest、manifest、数量或当前声明需要的完整性属性；
2. 记录来源 Run / Head / Artifact、接受责任和晋升目标；
3. 让后续工作流显式读取持久输入，避免隐式回退到即将过期的 Artifact；
4. 对晋升后的最终 Head 重跑受影响的导入流程、全新环境、评审运行环境或其他完成验证；
5. 不版本化无持续价值的完整日志、临时诊断或调试推理；
6. 受敏感数据、许可、体积或保留政策限制时，不机械写入 Git，按仓库策略选择对象存储、制品库或其他持久载体。

## 环境准备成本

如果某一步稳定环境准备在每次 CI 中重复支付且成本明显高于业务验证本身，依次评估：

1. 是否可以提前到独立 Build Job；
2. 是否可以传递 Artifact；
3. 是否有官方 / 厂商维护的预构建运行环境；
4. 是否可以使用 service container；
5. 是否可以使用安全且可追溯的缓存；
6. 是否值得维护使用方自有薄镜像。

优化目标是缩短反馈路径，不是牺牲完成验证覆盖。

## 诊断信息的持久化边界

只有具有跨运行任务或跨执行单元持续价值的验证 HOW 才进入使用方的长期验证策略 / 工作流。

一次性失败日志、临时调查笔记和完整调试推理不因为出现过就自动升级为长期产物。
