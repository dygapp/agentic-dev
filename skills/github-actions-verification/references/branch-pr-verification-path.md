# 分支 / PR 验证路径

## 目的

本参考说明在使用 GitHub 的项目中，如何根据隔离性、可逆性、证据可观察性和仓库策略选择直接推送或分支 → Pull Request（PR）路径。

分支是 Git 的隔离机制；PR 是 GitHub 的协作与集成对象。PR 不是通用开发方法的强制概念。

## 决策维度

优先检查：

1. **隔离性**：未完成状态是否会污染共享默认分支；
2. **可逆性**：失败或改向时是否容易回滚；
3. **证据可观察性**：当前 Agent 运行环境能否枚举并读取相应 CI 运行任务；
4. **仓库策略**：是否要求分支、PR、复核、受保护分支或特定检查；
5. **迭代形态**：是否会经历多轮实现、CI、调试和复核。

## 何时更适合分支 → PR

常见条件：

- 当前工作需要多轮修改和 CI；
- 默认分支是共享权威基线；
- 仓库策略不希望未完成工作直接进入默认分支；
- 当前连接器 / 运行环境对 PR 触发的 GitHub Actions 运行任务可观察性优于推送触发的运行任务；
- 需要把差异、CI、复核和集成决策关联在同一个 GitHub 对象上。

常见路径：

```text
任务 / 功能分支
→ Pull Request
→ GitHub Actions
→ 当前证据
→ 已具备进入集成决策的条件
→ 人工权威 / 仓库策略
```

## 何时直接推送仍可接受

如果同时满足：

- 仓库策略明确允许；
- 工作低风险、短周期、可逆；
- 当前运行环境能完整取得该推送对应的当前验证证据；
- 不会破坏并行工作或共享基线；

则不为了形式完整性强制创建 PR。

## GitHub Actions 触发与证据

选择触发路径时先验证当前运行环境能否读取：

- 运行事件；
- Head SHA；
- `status` / `conclusion`；
- Job / Step；
- 必要日志 / Artifact。

如果 `push` 触发的运行任务已存在但 Agent 无法自动发现，而 `pull_request` 触发的运行任务可以稳定枚举，则切换为基于 PR 的流程属于有效的运行环境适配。

人工手工提供 Run URL / ID 可以临时补足观察能力，但如果该人工步骤会在后续每轮验证重复出现，应优先寻找可自动观察的验证路径，而不是长期依赖人工补链。

## 非目标

不要从本参考推出：

- 所有 GitHub 仓库必须使用 PR；
- 所有执行单元必须一一对应 PR；
- PR 创建后 Agent 自动拥有合并权限；
- 直接推送天然违反通用开发方法。
