# 容器化 E2E 与预构建运行环境

## 目的

当 GitHub Actions 需要同时验证前端、后端、数据库、浏览器或其他运行环境时，本参考提供一种降低重复环境准备成本的通用模式。

多容器不是目标本身。只有当不同运行环境的依赖、生命周期或诊断边界值得独立时才拆分。

## 验证分层

优先将验证分成：

```text
快速反馈
├─ 后端编译 / 单元测试
├─ 前端 type-check / build
└─ 定向检查

        ↓ 通过

完成验证
└─ 运行时 / 集成 / 浏览器 E2E
```

局部修复迭代优先取得低成本反馈；最终声明完成前仍必须执行完成条件所要求的完整验证。

## 构建与运行环境分离

当构建产物可以跨 Job 复用时，推荐：

```text
后端验证
→ 后端构建产物

前端验证
→ 前端构建产物

完成 E2E
→ 使用构建产物
→ 只启动运行环境
```

避免在 E2E Job 中重复完成已经成功的完整编译流程。

## 多运行环境拓扑

复杂 Web 使用方项目可以考虑：

```text
数据库 service / container
        │
        ├─ 后端运行环境 + 后端构建产物
        ├─ 前端 HTTP 运行环境 + 前端构建产物
        └─ 浏览器验证运行环境
```

是否拆分、拆成几个容器，由当前系统边界和验证成本决定，不固定数量。

## 镜像来源优先级

稳定基础运行环境优先考虑：

1. 官方或厂商维护的预构建镜像；
2. 当前平台可稳定访问的可信镜像仓库；
3. GitHub Actions service containers；
4. 使用方自有薄封装镜像；
5. 只有确有必要时才在每次 CI 从头构建完整运行环境。

在 GitHub Actions 中，常见来源包括：

- GHCR（GitHub Container Registry）；
- MCR（Microsoft Container Registry）；
- Docker Hub；
- 其他仓库策略允许的镜像仓库。

不要为了“统一镜像仓库”把本来由厂商稳定维护的官方镜像重新复制一份。

## 浏览器验证

如果浏览器测试框架提供官方预构建镜像，优先评估直接使用该运行环境，而不是每次运行都在线安装浏览器及系统依赖。

需要检查：

- package 与 image 版本兼容；
- browser binary 与 test runner 匹配；
- 当前 GitHub-hosted runner / container architecture 支持；
- 仓库策略和安全边界允许。

这些 package、image、runner 等名称在涉及实际工具或平台对象时保持原样。

## 数据库与服务依赖

对数据库、缓存、消息系统等稳定依赖：

- 优先使用 service container / 官方镜像；
- 设置明确 health check；
- 不把“container started”等同于“service ready”；
- E2E 失败时保存必要服务状态和日志。

数据库 Migration 发生变化时，如果当前运行环境能提供干净数据库，应在最终验证中执行完整初始化链：

```text
全新数据库
→ 完整迁移链
→ 应用启动
```

已有数据库上的增量执行仍可作为补充证据，但不能替代新环境初始化证据。

## 使用方自有镜像

只有当：

- 官方镜像无法满足固定依赖；
- 环境准备仍然显著昂贵；
- 多个工作流 / 使用方场景长期复用同一薄层配置；

才考虑维护使用方自有镜像。

自有镜像应保持薄、可追溯、可更新，避免构建包含所有工具的万能运行环境。

## 自动验证与人工评审状态隔离

同一工作流同时承担自动 E2E 和人工评审环境时，优先分离状态生命周期：

```text
自动 E2E
→ 收集报告 / trace / screenshot
→ 重建数据库并恢复版本化资源
→ 准备明确的人工评审示例数据
→ 暴露评审运行环境
```

人工评审环境应能说明：

- 当前数据库和静态资源来自哪个已知基线；
- 哪些数据是明确的人工评审示例数据；
- 自动测试创建的数据、导航、文件、缓存和会话是否已经清除；
- 重置后的服务健康、关键入口和外部访问路径是否重新验证。

除非使用方仓库明确将自动测试数据采纳为人工示例数据，否则不能直接暴露测试结束状态。

## Bind Mount 所有权与可重复恢复

容器可写 host bind mount 时，容器内 UID / GID 可能在 runner 文件系统留下普通用户无法删除或覆盖的文件。设计重置时应显式确认：

- 哪个运行环境创建文件，以及最终 ownership / permissions；
- 清理动作由哪个已授权身份执行；
- 是否需要在容器内清理、固定 UID / GID、调整 mount 模式，或采用其他当前平台允许的恢复方式；
- 清理后是否重新复制或重建版本化基线；
- 相同重置能否再次执行并得到同一已知状态。

`rm -rf` 命令被调用不构成清理证据。应重新检查目标路径、预期基线内容和后续运行环境启动结果。

这些规则只用于已授权的临时验证 / 评审环境，不授予生产数据或共享状态的破坏性清理权限。

## 非目标

本参考不要求：

- 所有 CI 使用 Docker；
- 所有 E2E 使用四个容器；
- 所有镜像都来自 GHCR；
- GitHub Actions 承担生产部署；
- 为每个执行单元单独设计一套容器拓扑。
