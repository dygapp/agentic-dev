## 1. 映射字段

A2 使用以下工作字段描述激活单元候选：

- **语义职责**：当前单元实际约束什么；
- **权威指针**：回到原指南的稳定章节位置；
- **触发条件**：什么任务、风险、状态或产物出现时才需要加载；
- **主要消费者**：最直接使用该规则的职责或执行者；
- **强度**：
  - **核心不变量候选**：跨多数任务成立，后续可评估是否进入极薄常驻核心；
  - **条件必需**：触发条件成立时必须遵守，但不应无条件常驻；
  - **指导默认**：提供默认做法，仍允许使用方权威或当前证据决定具体载体；
- **上下文层级候选**：常驻核心 / 任务能力 / 条件规则；
- **交叉关系**：只标记 A4 需要继续核验的摘要、职责消费或潜在重叠，不在 A2 给出删除结论；
- **证据锚点**：A1 已冻结的真实历史失效或正向使用证据。

这些字段只是阶段 A 的审计工作视图，不构成阶段 B 的最小检索契约。

## 2. 常驻核心候选

完整指南中只有少量语义具有“几乎所有任务都必须知道”的性质。A2 当前只提名三个候选，不把“重要”机械等同于“常驻”。

### UG-01 — 使用方仓库权威与项目事实边界

- **语义职责**：`agentic-dev` 提供可复用方法、技能与使用指导；使用方仓库拥有自己的项目事实、需求、架构、代码、测试与集成策略。其他聊天、个人记忆、其他项目规则以及 `agentic-dev` 自身项目规则都不能直接成为使用方事实。
- **权威指针**：§1“使用模型”；§2“开始前的知识边界”。
- **触发条件**：任何使用 `agentic-dev` 推进使用方项目的任务。
- **主要消费者**：所有使用方 Agent；项目恢复 / 规划 / 实施 / 复核职责。
- **强度**：**核心不变量候选**。
- **上下文层级候选**：**常驻核心**。
- **交叉关系**：与 `AGENTS.md` 的 Repository Authority / Knowledge Boundary，以及多个技能的 Authority Sources 存在明显交叉；A4 应判断哪些是必要常驻摘要、哪些只是职责局部重申。
- **证据锚点**：Issue #33、Issue #52 均支持使用方本地权威必须优先于上游项目事实。

### UG-02 — 渐进式披露与禁止依赖未持久化会话历史

- **语义职责**：只加载当前任务真正需要的最小权威上下文；项目事实和表达方式从仓库恢复，不从完整旧聊天或个人记忆恢复。
- **权威指针**：§2；§5.5；§7。
- **触发条件**：任何新上下文、任务切换、执行单元执行或恢复工作。
- **主要消费者**：所有新上下文；`execute-unit`、`converge` 以及项目治理职责。
- **强度**：**核心不变量候选**。
- **上下文层级候选**：**常驻核心**，但详细恢复顺序应按项目 / 职责条件加载。
- **交叉关系**：与 `AGENTS.md`、Roadmap 新上下文恢复入口以及多个技能的 Context Rules 高度交叉；A4 需区分核心原则与各职责的最小输入清单。
- **证据锚点**：Issue #33 的既有使用方连续演进实验直接验证“从持久化仓库权威恢复，而不是依赖旧会话”。

### UG-03 — 证据先于完成声明

- **语义职责**：实现存在、代码检查、历史结果、未运行命令或无法关联目标状态的证据都不能支持当前完成声明；声明必须由与目标状态和具体验收义务匹配的当前证据支持。
- **权威指针**：§5.7；§5.8；§10。
- **触发条件**：任何准备声明执行单元完成、功能已收敛、已具备进入集成决策条件的任务。
- **主要消费者**：`execute-unit`、`converge`、AI / 人工复核、验证职责。
- **强度**：**核心不变量候选**。
- **上下文层级候选**：**常驻核心**只保留薄原则；证据类型、平台触发、复用与晋升等详细规则继续条件加载。
- **交叉关系**：与 `AGENTS.md` 的 Current Evidence、`execute-unit`、`converge`、`external-operation-guidelines.md` 及 `github-actions-verification` 交叉；A4 需避免把平台细节一起提升为常驻内容。
- **证据锚点**：Issue #52 的最终 Head 重新取得当前 CI / Review Environment 证据，是该原则的正向使用样本。

## 3. 条件激活单元映射

### UG-04 — 外部需求来源采纳为使用方权威

- **语义职责**：外部文件、URL、其他仓库或人工提供资料只是需求来源；只有被当前项目显式采纳后才成为使用方权威需求，并继续通过澄清 / 规格说明形成 WHAT / WHY 权威。
- **权威指针**：§2.1“需求来源与使用方权威”。
- **触发条件**：新项目启动、接收外部需求、迁移已有需求文档、引用其他仓库材料。
- **主要消费者**：项目初始化、`clarify-intent`、`specify`。
- **强度**：**条件必需**。
- **上下文层级候选**：条件规则。
- **交叉关系**：与 `specify` 的 Authority Sources / Domain Authority 生命周期存在职责消费关系；不应因此默认常驻。
- **证据锚点**：A1 当前没有专门历史失效场景；保留为后续评估补充候选，不据此新增场景。

### UG-05 — 新项目最小启动骨架

- **语义职责**：新项目先建立足以让新上下文继续工作的最小仓库权威，不从大而全模板开始。
- **权威指针**：§3“新项目：建立最小启动骨架”。
- **触发条件**：Greenfield 项目、尚无可恢复仓库权威的初始化工作。
- **主要消费者**：项目初始化 / Bootstrap 类职责。
- **强度**：**指导默认**；最小权威边界是必需的，具体目录与文件名不是强制。
- **上下文层级候选**：条件规则。
- **交叉关系**：与 §3.2、§6.2 的最小长期产物原则重叠；A4 需要判断是否属于同一核心原则的不同生命周期应用。
- **证据锚点**：Issue #33 / #52 属于既有使用方，不直接证明 Greenfield 结构，但支持“本地可恢复权威优先”。

### UG-06 — 项目路线图创建门槛与职责

- **语义职责**：只有项目需要跨里程碑、阶段或新上下文恢复整体路线时才建立薄路线图；README 只链接，不并行复制易变化状态。
- **权威指针**：§3；§6.2。
- **触发条件**：项目首次满足跨里程碑 / 多阶段 / 新上下文恢复需求，或已有路线图需要维护。
- **主要消费者**：项目初始化、项目治理、`converge`。
- **强度**：**条件必需**。
- **上下文层级候选**：条件规则。
- **交叉关系**：与 Roadmap 自身、README 和 `converge` 项目路线检查交叉；A4 应区分“何时需要路线图”和“路线图当前内容”两类不同权威。
- **证据锚点**：Issue #33 Finding 2 为 README / Roadmap / GitHub 证据职责分离的正向使用样本。

### UG-07 — 规划候选不得提前获得执行单元身份

- **语义职责**：Roadmap、Backlog、Issue、顺序号或 `EU-xx` 名称不能让尚未完成上游阶段的规划 / 需求候选获得执行单元身份；候选执行单元只由 `slice-work` 在规格说明就绪后形成。
- **权威指针**：§3 路线图候选段；§5.4。
- **触发条件**：Roadmap 排序、未来工作登记、准备切分执行单元、看到预编号 `EU-xx` / Unit ID 时。
- **主要消费者**：规划职责、`slice-work`、`readiness-check`、新上下文恢复。
- **强度**：**条件必需**。
- **上下文层级候选**：任务能力 + 条件规则。
- **交叉关系**：与 `slice-work` / `readiness-check` 的身份边界是直接职责消费；A4 需判断使用指南只应保留激活提示还是当前完整解释。
- **证据锚点**：S-02 / PR #60；最终 `5 / 5` 场景、`27 / 27` 断言通过。

### UG-08 — 使用方主导语言与表达方式

- **语义职责**：语言是使用方项目规则；已有规则时以使用方权威为准，没有规则时沿用当前权威需求和主要协作输入的主导语言，不继承上游或旧会话语风。
- **权威指针**：§3.1；§7。
- **触发条件**：项目初始化、人工输出、新上下文恢复、语言规则缺失或冲突。
- **主要消费者**：所有面向人的使用方输出；项目初始化。
- **强度**：**条件必需**，具体语言值由使用方决定。
- **上下文层级候选**：条件规则；如果使用方仓库已经固化语言规则，应直接由使用方本地权威激活，不需要反复读取上游本段。
- **交叉关系**：与 `AGENTS.md` / README / 术语指南以及 `external-operation-guidelines.md` 的外部协作语言存在交叉；A4 重点检查是否只是必要摘要。
- **证据锚点**：Issue #58 Finding F 记录过使用方仓库协作约定可发现性缺口，后由 PR #61 收敛为 Existing Consumer baseline-upgrade checklist。

### UG-09 — 不预建没有真实需要的长期结构

- **语义职责**：架构、ADR、任务计划、路线图、配置和技能等长期结构只在出现真实持续协调 / 权威价值时建立，不为形式完整性预建空体系。
- **权威指针**：§3.2；§6.2。
- **触发条件**：项目初始化、新增长期产物、准备新增目录 / 模板 / Skill / 配置治理时。
- **主要消费者**：项目治理、技术规划、初始化职责。
- **强度**：**指导默认**，但禁止无真实需要的形式化结构膨胀。
- **上下文层级候选**：条件规则。
- **交叉关系**：与工程纪律“实现最小化”存在概念相似，但作用层不同；A4 应避免把项目知识结构最小化与代码实现最小化混为同一规则。
- **证据锚点**：Issue #52 的选择性采用与最小化证据可作为正向参考，但不是本规则专门评估。

### UG-10 — 按职责选择 Skill，平台专项能力条件加载

- **语义职责**：不要求所有 Skill 在每项工作中出现；核心 Skill 按当前职责调用，平台专项非核心 Skill 只有当前仓库 / 运行环境满足触发条件时加载。
- **权威指针**：§4“使用 Skill”。
- **触发条件**：选择执行职责、运行环境具有 GitHub Actions 等平台特征、准备安装 / 暴露 Skill 时。
- **主要消费者**：协调层、所有技能调用入口。
- **强度**：**条件必需**。
- **上下文层级候选**：任务能力。
- **交叉关系**：与 Skill Architecture、各 Skill `Use When` / `Do Not Use When` 以及 `github-actions-verification` 直接交叉；使用指南应主要承担能力发现，不复制 Skill 全部过程。
- **证据锚点**：S-04 / PR #61 支持 GitHub Actions 专项规则应按真实验证风险激活，而不是成为所有任务默认上下文。

### UG-11 — 意图澄清与领域权威候选路由

- **语义职责**：只有会实质影响产品目标、范围、行为、边界或验收的歧义才进入 `clarify-intent`；可能跨多个功能持续有效的领域事实交给 `specify` 验证和授权，不从聊天直接晋升长期权威。
- **权威指针**：§5.1。
- **触发条件**：产品意图存在阻塞歧义，或澄清暴露跨功能领域事实。
- **主要消费者**：`clarify-intent`、`specify`。
- **强度**：**条件必需**。
- **上下文层级候选**：任务能力。
- **交叉关系**：与两个 Skill 契约属于职责消费；A4 应检查使用指南是否只需保留流程导航。
- **证据锚点**：无 A1 专门历史场景。

### UG-12 — 规格说明与长期领域事实生命周期

- **语义职责**：规格说明形成最小充分 WHAT / WHY；只服务当前功能的行为留在规格说明，跨功能持续消费的业务事实进入使用方领域权威，并显式更新 / 取代陈旧事实。
- **权威指针**：§5.2。
- **触发条件**：形成规格说明、识别领域事实、旧领域事实失效或冲突。
- **主要消费者**：`specify`、`readiness-check`、`converge`。
- **强度**：**条件必需**。
- **上下文层级候选**：任务能力。
- **交叉关系**：与 `specify` 及后续 Gate 的领域权威检查交叉。
- **证据锚点**：当前 A1 场景集中在激活 / 验证 / 路线问题，本单元暂没有专门失效样本。

### UG-13 — 技术计划、架构上下文与 ADR 分层

- **语义职责**：只有跨执行单元长期协调的 HOW 才需要技术计划；跨功能长期系统结构变化进入架构权威；只有需要长期保留背景、理由、权衡或替代关系的重要决定才形成 / 更新 ADR。
- **权威指针**：§5.3。
- **触发条件**：实施前出现跨单元持久技术决定、架构状态改变、重要架构决定、执行 / 调试 / 收敛阶段暴露架构权威缺口。
- **主要消费者**：`technical-plan`、`readiness-check`、`systematic-debug`、`converge`。
- **强度**：**条件必需**。
- **上下文层级候选**：任务能力。
- **交叉关系**：与 Technical Planning、Architecture Context、ADR Authority 职责交叉；不属于所有任务常驻知识。
- **证据锚点**：S-03 的就绪回退场景包含技术计划基础被当前实现证据推翻的实例。

### UG-14 — 切分 / 就绪责任与验收证据覆盖

- **语义职责**：`slice-work` 形成候选执行单元，并把规格验收义务映射到实现责任、验证责任和计划证据；`readiness-check` 检查这些责任和证据是否足以进入执行。稳定标识不等于就绪通过或执行授权。
- **权威指针**：§5.4。
- **触发条件**：规格说明就绪后切分、执行前门禁、验收责任或验证覆盖不足。
- **主要消费者**：`slice-work`、`readiness-check`。
- **强度**：**条件必需**。
- **上下文层级候选**：任务能力。
- **交叉关系**：与两个 Skill 的完整过程高度重叠；A4 应核验使用指南的合适摘要粒度。
- **证据锚点**：S-02 / PR #60。

### UG-15 — 上游语义修订后旧候选 / 旧就绪证据失效

- **语义职责**：就绪检查发现原 WHAT、HOW 或架构基础不成立时，返回真实上游职责修订；实质修订后必须重新 `slice-work → readiness-check`，不能用已有标识、历史通过状态或工作产物继续授予执行权限。
- **权威指针**：§5.4 末段。
- **触发条件**：`readiness-check` 当前证据推翻原规格说明 / 技术计划 / 架构前提，或上游权威发生实质修订。
- **主要消费者**：`readiness-check`、`slice-work`、协调层。
- **强度**：**条件必需**。
- **上下文层级候选**：条件规则，只有 Gate drift / upstream correction 风险出现时加载。
- **交叉关系**：与 `readiness-check` 的明确职责实现高度重叠；很可能适合“使用指南短激活提示 + Skill 完整语义”，但删除 / 缩减结论留给 A4 / D1。
- **证据锚点**：S-03 / PR #61；最终 `6 / 6` 场景、`37 / 37` 断言通过。

### UG-16 — 单执行单元的新执行上下文

- **语义职责**：每个新的 `execute-unit` 上下文只执行一个唯一当前执行单元，并只加载其必要权威、规格、计划、证据与相关代码；非预期失败转 `systematic-debug`。
- **权威指针**：§5.5。
- **触发条件**：执行一个已就绪执行单元。
- **主要消费者**：`execute-unit`、协调层。
- **强度**：**条件必需**。
- **上下文层级候选**：任务能力。
- **交叉关系**：与 `execute-unit` Purpose / Inputs / Context Rules 直接重叠；使用指南主要承担流程发现。
- **证据锚点**：Issue #33 的新上下文实验提供整体正向背景，但不是单执行单元专项评估。

### UG-17 — 配置责任与已有能力优先复用

- **语义职责**：固定值是否应外部配置取决于真实维护者、变化来源和生命周期；实现通用技术能力前先检查当前代码、框架、标准库和依赖，已有能力满足契约时优先复用，差异只做薄适配。
- **权威指针**：§5.6。

## 8. A2 结论

A2 得出以下阶段性结论：

1. `using-agentic-dev.md` 当前可以按语义辨识出 **27 个激活单元候选**；章节数、文件大小和最终激活单元数量没有一一对应关系。
