# 实现最小化与推测性复杂度控制研究

**研究日期：** 2026-09-02  
**本项目基线：** `dygapp/agentic-dev` `master@070cbb448118a6ee0494063c2d2c8ae689bfb5f3`  
**对应工作项：** WI-02 — 实现最小化与推测性复杂度控制  
**性质：** 研究（Research）与候选能力设计，非规范性权威

## 1. 研究目标

本文研究 **Implementation Minimality & Speculative Complexity Control（实现最小化与推测性复杂度控制）** 是否值得成为 `agentic-dev` 的正式工程纪律，以及它应如何与当前 `execute-unit`、PR #41 的配置责任 / 已有能力复用规则、PR #42 的 Karpathy Skills 研究结论组合。

本研究解决的不是“如何让代码尽可能少”，而是：

> 在满足当前权威需求、验证责任、工程健康和长期约束的前提下，如何避免 Agent 为尚未出现的未来需求提前引入没有当前证据支持的功能、抽象、配置、扩展点、依赖和结构复杂度。

本文只形成 Candidate Capability 和可执行的专项评估（Targeted Eval）设计，不直接修改 Method、Architecture、Skill Contract 或 `SKILL.md`。

## 2. 证据来源与基线

### 2.1 Martin Fowler — YAGNI

- 来源：Martin Fowler，`Yagni`；
- 发布日期：2015-05-26；
- URL：`https://martinfowler.com/bliki/Yagni.html`；
- 本次读取日期：2026-09-02；
- 证据类型：专家方法总结 / Extreme Programming 设计实践解释。

关键证据：

- 不应因为预计未来会需要某项能力，就提前实现当前尚未使用的“推测性功能”（presumptive feature）；
- 提前实现不仅有构建成本，还有延迟当前价值的成本和持续携带额外复杂度的成本；
- 同样的判断适用于为未来灵活性提前创建抽象与参数化；
- 这并不意味着禁止所有抽象；使当前需求更难理解的未来式抽象应被高度怀疑；
- YAGNI 不应被解释成拒绝重构、自测试或其他保持代码可修改性的工程实践；
- 如果一个面向未来的选择几乎不增加当前复杂度，却能显著降低后续成本，可以单独进行成本判断，而不是机械拒绝。

这一来源提供了本研究最重要的边界：**“未来需求没有证据时不提前建设”不等于“禁止为当前代码健康付出成本”。**

### 2.2 Kent Beck Simple Design，经 Martin Fowler 整理

- 来源：Martin Fowler，`Beck Design Rules`；
- 发布日期：2015-03-02；
- URL：`https://martinfowler.com/bliki/BeckDesignRules.html`；
- 本次读取日期：2026-09-02；
- 证据类型：专家整理；文中说明 Kent Beck 复核过该文章，并引用 XP Simple Design 的权威表述。

核心规则包括：

1. 测试通过；
2. 不保留重复逻辑；
3. 清晰表达程序员意图；
4. 使用尽可能少的类和方法 / 元素。

该来源明确说明：为了未来灵活性而增加架构元素，常常反而让系统更难修改；同时“最少元素”并不是孤立指标，它与正确性、表达意图和重复消除共同组成简单设计。

因此，本研究不能把实现最小化退化为：

```text
更少行数 = 更好
更少函数 = 更好
没有抽象 = 更好
```

正确性、可理解性和真实当前设计需要仍然优先。

### 2.3 Google Engineering Practices — Complexity / Over-engineering

- 来源：`google/eng-practices`；
- 仓库状态：已归档，但仍是长期公开的 Google 工程实践材料；
- 研究基线：`master@3bb3ec25b3b0199f4940b1aa75f0ac5c5753301c`；
- 文件：`review/reviewer/looking-for.md`；
- 文件 Blob：`c27e26edbf0f42603a16dd719c825f6801226191`；
- URL：`https://github.com/google/eng-practices/blob/3bb3ec25b3b0199f4940b1aa75f0ac5c5753301c/review/reviewer/looking-for.md`；
- 证据类型：成熟大型软件组织的工程实践。

该材料将过度工程（over-engineering）明确描述为：

- 代码比实际需要更通用；
- 增加系统当前并不需要的功能；
- 解决开发者猜测未来可能出现的问题，而不是已经知道当前需要解决的问题。

同时它把复杂度与两个可观察结果联系起来：

- 代码难以被读者快速理解；
- 后续开发者更容易在调用或修改时引入错误。

这使“复杂度”不再只是抽象审美，而具有工程可观察性。

### 2.4 Sandi Metz — The Wrong Abstraction

- 来源：Sandi Metz，`The Wrong Abstraction`；
- 发布日期：2016-01-20；
- URL：`https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction`；
- 本次读取日期：2026-09-02；
- 证据类型：专家工程经验。

该材料强调：错误抽象可能比暂时重复更昂贵。常见失败路径是：

```text
发现表面重复
→ 立即抽象
→ 新需求与抽象只有部分匹配
→ 增加参数和条件分支维持抽象
→ 抽象逐渐同时承载多个并不真正相同的概念
→ 修改越来越困难
```

这一来源不能被机械解释为“优先复制代码”，而应与 Simple Design 的“不重复”共同阅读：**重复是设计信号，但并不是所有重复都已经证明存在稳定、正确的共享抽象。**

### 2.5 Go 官方 Code Review Comments — Interfaces

- 来源：The Go Programming Language，`Go Wiki: Go Code Review Comments`；
- URL：`https://go.dev/wiki/CodeReviewComments`；
- 本次读取日期：2026-09-02；
- 证据类型：官方语言工程实践；
- 适用范围：该具体规则首先适用于 Go，但可作为“抽象应由真实使用形状驱动”的技术实例，不直接泛化为所有语言的接口规则。

Go 官方材料明确建议不要在真实使用出现之前定义接口，因为没有现实使用示例时，很难判断接口是否必要、应该包含哪些方法。

该证据支持本研究的一个重要方向：**抽象的形状应尽量由当前真实消费者和当前变体决定，而不是由提供方预先猜测。**

### 2.6 当前仓库本地证据

本项目已有两组直接相关证据。

#### PR #41 — 配置责任与已有能力复用

当前 `execute-unit` 已明确：

- 不因为发现字面量就机械把值外部化；
- 应根据维护者、变化来源、稳定性和安全 / 协议约束判断配置责任；
- 实现通用能力前先检查当前代码库、框架、标准库和已引入依赖；
- 已有能力满足真实契约时优先复用，并只用薄适配承载项目差异；

这两条规则本质上已经在限制“为了未来变化而配置化”和“为了通用性而重新建设已有能力”。

## 3. 多来源一致结论

上述来源在不同背景下形成了高度一致的工程判断。

### 3.1 当前需求优先于未来猜测

YAGNI、Google Engineering Practices 和 PR #42 都反对仅根据“以后可能需要”提前建设功能或通用性。

共同语义不是“永远不要面向未来”，而是：

> **当前新增复杂度必须有当前可追溯的需求、约束、风险或工程价值支撑。**

### 3.2 复杂度本身存在持续成本

复杂度不仅消耗当前开发时间，还会影响：

- 阅读和理解；
- 修改和调试；
- 测试与验证；
- 后续功能的实现成本；
- 错误概率；
- 回滚与替代成本。

因此“现在顺手把未来能力一起做掉”不能只比较当前编码成本，还必须考虑额外复杂度的持续携带成本。

### 3.3 抽象应该追随已观察到的稳定形状

Go 官方接口建议、Sandi Metz 的错误抽象分析和 YAGNI 对未来抽象的讨论共同支持：

- 不应因为单一实现“以后可能有第二种”就预先创建通用接口；
- 不应因为两个片段表面重复，就自动假设它们属于同一个稳定概念；
- 当前已经存在多个真实消费者 / 变体，并且共享语义已经清晰时，抽象仍然是合理工具；
- 错误抽象开始依赖大量条件参数维持时，应允许退回更直接的结构重新观察真实形状。

### 3.4 最小化不是最少代码

Beck Simple Design 和 Google 的可理解性要求共同否定“代码越短越简单”。

实现最小化必须同时满足：

- 当前行为正确；
- 当前验收义务可验证；
- 当前安全、性能、可观察性等有效约束；
- 代码意图清晰；
- 当前维护成本合理；
- 不为了减少元素而制造晦涩控制流或隐藏真实差异。

### 3.5 保持代码可修改性不是推测性功能

YAGNI 明确区分：

- 为尚未出现的未来功能增加能力；
- 为当前代码保持可测试、可重构、可修改而进行的工程实践。

因此不能用“最小实现”作为以下行为的借口：

- 不写当前必要测试；
- 拒绝为了当前变更做必要的小规模行为保持重构；
- 忽略当前已经存在的清晰设计问题；
- 绕过当前安全、错误处理或可观察性责任。

## 4. 需要显式处理的张力与边界

### 4.1 YAGNI 与架构前瞻性的边界

并非所有未来影响都可以延迟。

如果当前 Repository Authority 已经存在：

- 公共契约；
- 难以回滚的数据格式；
- 已确定的部署拓扑；
- 当前必须满足的兼容义务；
- 安全 / 隐私要求；
- 已经确认的多消费者 / 多实现需求；

这些属于**当前约束**，不是“未来猜测”。

`execute-unit` 不应为了追求简单而忽略它们；高影响决定仍应返回 `technical-plan` 或适当权威层。

### 4.2 不重复与错误抽象的边界

Beck Simple Design 把“不重复”作为重要规则，而 Sandi Metz 警告错误抽象可能比重复更贵。

本研究的收敛判断是：

> **不要把重复数量本身当成抽象触发器；应判断重复是否已经代表同一稳定语义。**

如果当前差异只是实现偶然相似、未来变化方向仍不清楚，允许暂时保留小规模局部重复；如果当前已经存在稳定共享概念，且抽象能让意图更清晰、减少真实重复而不引入未来式分支，应进行适当抽象。

### 4.3 “以后加也行”与现在低成本准备的边界

YAGNI 也承认：某些现在即可完成、几乎不增加复杂度、却能显著降低后续成本的设计选择可以合理存在。

因此候选纪律不能使用绝对规则：

```text
所有未被当前验收标准直接点名的设计都必须删除
```

更合理的判断需要比较：

- 当前新增复杂度；
- 当前是否产生额外维护责任；
- 延迟实现的真实成本；
- 当前是否已有可信变化证据；
- 是否会形成难以撤回的公共扩展面。

## 5. 与当前 `execute-unit` 的缺口分析

当前 `execute-unit` 已经具备以下良好基础：

1. 单执行单元边界；
2. 实现满足 Current Unit 所需的最小变更；
3. 不扩大未经授权的 Product Scope；
4. 不顺手修复无关相邻问题；
5. 不把当前 Unit 变成完整 Feature 重构机会；
6. 配置责任必须有真实维护者与变化来源；
7. 优先检查和复用当前代码、框架、标准库与依赖；
8. 必要当前验证必须闭环。

因此当前不是缺少“简单优先”方向，而是缺少更明确的**复杂度正当性判断**。

主要缺口有四个。

### 5.1 缺少对“未来式抽象”的显式默认判断

当前“最小变更”可以间接推导出不要提前抽象，但没有明确告诉 Agent：

- 为假想第二实现建立 Strategy / Factory / Interface；
- 为尚不存在的消费者建立扩展点；
- 为未出现的变化维度参数化；

这些都需要当前证据，而不是因为“看起来更可扩展”就自动合理。

### 5.2 缺少必要复杂度与推测性复杂度的区分框架

当前规则告诉 Agent 不扩大范围，但没有系统回答：

> 一个不改变产品 Scope、但增加了额外类、接口、配置、依赖或抽象层的设计，是否仍然属于不必要复杂度？

这正是 WI-02 应补足的判断层。

### 5.3 缺少防止“伪最小化”的反向边界

如果只增加“不要多做”规则，Agent 可能错误地：

- 选择难读的一行式实现；
- 为减少函数数量而保留复杂控制流；
- 把当前必要的小规模重构视为越界；
- 把测试、可观察性或安全措施误认为额外复杂度。

因此候选能力必须同时规定“不能为了元素更少牺牲当前工程质量”。

### 5.4 配置与复用规则目前是具体案例，尚未抽象出统一判断

PR #41 已经分别解决配置化和框架复用，但它们背后的共同原则尚未显式表达：

> **所有新增结构复杂度都应有当前责任和当前证据。**

统一这一判断可以减少未来继续通过单点 Finding 增加零散规则，但不能削弱 PR #41 已有精确边界。

## 6. Candidate Capability：实现最小化与推测性复杂度控制

### 6.1 候选核心规则

> **在满足当前权威需求、验证责任、有效长期约束和当前工程健康的前提下，选择当前证据能够支持的最低必要复杂度。仅服务假想未来需求的功能、抽象、配置、扩展点、依赖、层次或条件分支，默认不进入当前实现；只有存在可追溯的当前责任、当前变化证据或明确的低复杂度高收益理由时才例外。**

这里的“最低必要复杂度”不是最少行数或最少文件，而是避免没有当前价值的结构和行为。

### 6.2 当前正当性来源

一个新增复杂度元素可以由以下当前证据之一或组合支持：

1. **当前验收义务**：直接满足当前 Specification / Execution Unit 的行为；
2. **当前长期技术约束**：Technical Plan、Architecture、ADR、公共契约或迁移义务已经要求；
3. **当前非功能责任**：安全、隐私、性能、可靠性、可观察性、测试性等当前有效约束；
4. **当前真实变体 / 消费者**：已经存在多个需要被统一处理的真实场景，而不是假想第二实现；
5. **当前 Repository Rule / Engineering Rule**：项目明确要求的稳定工程方式；
6. **已有能力集成需要**：为了正确复用当前框架 / 标准库 / 依赖所需的薄适配；
7. **低复杂度高收益的演进准备**：现在几乎不增加理解和维护成本，但有当前证据表明显著降低已知后续成本。

仅有以下理由通常不足：

- “以后可能会有第二种实现”；
- “看起来更企业级”；
- “这样未来更灵活”；
- “设计模式一般都这么写”；
- “把所有值做成配置更通用”；
- “也许以后会换框架”；
- “先把接口 / 插件机制预留出来不会有坏处”。

### 6.3 复杂度承载对象

评估对象不仅是代码行数，还包括：

- 新功能或隐藏行为；
- 新类、接口、继承层次；
- Strategy / Factory / Registry / Plugin 等扩展结构；
- 新配置项、数据库设置、环境变量；
- 新依赖或框架；
- 新公共 API；
- 新数据字段或状态；
- 为未来情况增加的条件分支和错误路径；
- 仅用于“以后方便”的基础设施层。

### 6.4 决策启发式

Agent 在实现前或 JIT 计划中可以依次检查：

1. **它解决当前什么责任？** 能否追溯到当前需求、约束、真实变化或工程责任？
2. **删除它，当前系统会失去什么？** 如果答案只是“以后可能不方便”，默认视为推测性。
3. **当前已有能力是否已满足契约？** 先检查代码库、框架、标准库和已有依赖。
4. **现在抽象的真实共同形状是否已经出现？** 没有真实消费者 / 变体时，不用假想形状设计通用层。
5. **现在做和以后做的成本如何？** 同时考虑构建、延迟价值、持续携带和未来修复成本，而不是只比较当前编码量。
6. **更少元素是否会损害当前理解和质量？** 正确性、清晰性、安全、验证和代码可修改性不能为了“更少”被牺牲。

这一检查默认是执行纪律，不要求创建新的持久化“复杂度说明表”。只有当决定本身形成跨 Unit 的长期架构约束时，才进入现有 Technical Plan / Architecture / ADR 生命周期。

### 6.5 与抽象的关系

候选纪律不是“反抽象”。

允许抽象的典型当前证据包括：

- 已经存在两个或更多真实消费者，并且共享语义稳定；
- 当前重复代表同一个业务 / 技术概念，而不是偶然代码相似；
- 抽象使当前意图更清晰，而不是增加条件参数隐藏差异；
- 当前框架或 Repository Authority 已经规定该扩展模型；
- 抽象直接改善当前测试性、可维护性或明确的非功能责任。

反之，如果抽象主要依靠假想消费者、未来参数或不断增加的条件分支维持，应优先回到当前真实需求重新判断。

### 6.6 与配置治理的关系

PR #41 的配置责任规则保持不变。

本候选纪律只提供更高一层解释：

- 没有当前维护者 / 变化来源的动态配置，本身就是推测性复杂度；
- 当前明确由运营、部署或流程维护的值，则具有当前责任，不属于 YAGNI 禁止对象；
- 稳定安全 / 协议参数不能因为“可配置更灵活”而被错误外部化。

### 6.7 与已有能力复用的关系

PR #41 的复用规则保持不变。

本候选纪律进一步明确：

- 重复建设框架已经满足的通用能力会增加不必要实现复杂度；
- 为了“以后可能复用”引入新的依赖同样可能增加不必要依赖复杂度；
- 判断标准始终是当前功能契约、当前约束和已有技术栈实际能力，而不是“自研优先”或“框架优先”的绝对规则。

### 6.8 与重构 / 测试的关系

以下行为不应被机械视为推测性复杂度：

- 为当前变更建立必要测试；
- 为保持当前行为可验证而进行的小规模重构；
- 移除当前已经证明错误的抽象；
- 改善当前代码意图和可修改性的必要调整；
- 当前安全 / 可观察性 / 可靠性责任要求的工程措施。

判断关键不是“用户是否逐字要求了这个代码结构”，而是它是否服务**当前可追溯的工程责任**。

## 7. 架构落点判断

### 7.1 不修改 Core Method

本候选能力不增加开发阶段、不改变 WHAT / WHY 与 HOW 边界、不改变 Human Escalation 或 Integration Boundary。

因此没有 Method Gap。

### 7.2 不新增 Task-oriented Skill

该能力没有独立的任务入口、稳定单独输出或自己的 Stage Transition；它主要约束 `execute-unit` 和未来 Engineering Quality Review 在局部实现选择中的判断。

因此当前没有新 Skill 的独立职责证据。

### 7.3 候选落点：独立 Engineering Discipline + 薄执行引用

由于该规则未来还可能被以下能力共同消费：

- `execute-unit`；
- Engineering Quality Review；
- Refactoring Discipline；
- Technology Profile；
- framework / dependency upgrade 类任务；

只把全部内容继续堆进 `execute-unit/SKILL.md` 会增加重复和后续维护成本。

因此当前候选落点是：

> **形成独立 Engineering Discipline 权威，由 `execute-unit` 保留薄的执行检查 / 引用；未来其他 Profile 或 Review 能力按需消费。**

正式持久化路径和具体文本应在 Candidate 通过 Targeted Eval 后再确定，本 Research 不提前创建新的规范目录或权威文件。

### 7.4 不需要修改 Engineering Capability Architecture

当前架构已经明确允许：

- Engineering Discipline 独立存在；
- Discipline 不自动 Skill 化；
- 外部成熟证据可以触发候选设计；
- 候选进入权威前必须经过 Targeted Eval 和 AI Review。

因此 WI-02 没有暴露新的能力架构缺口，满足进入条件性 WI-03 的前提。

## 8. Targeted Eval 设计

本节只设计 Candidate Eval，不把这些场景直接加入当前 `evals/behavior/execute-unit.json`，因为当前 Candidate 尚未进入规范性 Skill 行为。正式集成时再将通过审核的场景转换为 Behavior Eval。

### 8.1 C-MIN-01 — 假想第二实现导致提前抽象

**场景：** 当前 Unit 只需要为一个已存在支付渠道增加固定签名校验。仓库只有这一个渠道，没有第二实现、插件需求或公共扩展契约。实现者建议同时创建 `PaymentVerifier` 接口、Factory、Registry 和配置化 provider 名称，以便“以后增加其他支付平台”。

**期望：**

- 满足当前签名校验；
- 不为假想第二实现创建通用扩展框架；
- 如果当前代码已有合适抽象则复用，不机械删除；
- 明确未来真实第二渠道出现时可根据实际形状重构。

**关键断言：**

1. 不把“以后可能有第二渠道”当作当前接口 / Factory / Registry 的充分证据；
2. 保留当前必要的正确性、安全和测试；
3. 不把“最小化”解释成跳过签名失败路径或安全校验；
4. 当前方案能够在真实新渠道出现时安全演进，而不是宣称永远不允许抽象。

### 8.2 C-MIN-02 — 表面重复诱导错误抽象

**场景：** 两个当前流程各有约 8 行相似代码，但一个以业务年度为边界，另一个以自然年为边界；未来变化方向未知。有人要求“DRY”，提议提取一个带多个布尔参数的通用函数。

**期望：**

- 不因为行级重复自动提取错误共享抽象；
- 识别两个流程当前语义不同；
- 可以保留小规模局部重复，或只提取真正稳定的纯共享部分；
- 不用布尔参数和条件分支掩盖当前差异。

**关键断言：**

1. 抽象依据是共享语义，不是重复行数；
2. 不创建需要根据调用方类型切换语义的“万能函数”；
3. 如果存在真正稳定公共计算，可做最小局部提取；
4. 不把“允许重复”解释成忽略所有明确可安全消除的重复。

### 8.3 C-MIN-03 — 伪最小化：为了元素少牺牲可读性

**场景：** 当前功能可以写成复杂的一行表达式，也可以使用一个清晰命名的小函数和直接测试。有人要求“最少代码，所以必须一行写完”。

**期望：**

- 选择能够清晰表达当前意图的直接实现；
- 不以 LOC 或函数数量作为唯一复杂度指标；
- 保持当前必要测试；
- 不额外引入无当前作用的层次。

**关键断言：**

1. 正确性与可理解性优先于机械减少代码行；
2. 可以使用服务当前意图的小函数；
3. 不因为“简单”删除当前验证；
4. 同时避免为该小函数再增加无需要的接口 / 工厂 / 插件层。

### 8.4 C-MIN-04 — 误用 YAGNI 拒绝当前必要重构

**场景：** 当前 Unit 需要新增一个分支，而现有 150 行函数已经存在难以隔离测试的明确行为耦合。一个很小的行为保持重构可以建立测试 Seam，然后实现当前需求。有人说“重构不是需求，按 YAGNI 不做”。

**期望：**

- 允许为当前可验证性和安全实施所必需的小规模行为保持重构；
- 重构范围必须直接服务当前实现 / 验证，不扩大成完整模块重写；
- 修改前后保持当前行为证据。

**关键断言：**

1. 不把 YAGNI 用来禁止当前必要的代码健康 / 可测试性工作；
2. 重构与当前 Unit 有明确追溯关系；
3. 不顺手重构整个模块；
4. 有当前验证证明行为保持和新需求满足。

### 8.5 回归场景

正式验证 Candidate 时应至少回归当前：

- `B-EU-07`：配置责任判断；
- `B-EU-08`：已有框架能力复用。

目标是确保更高层“实现最小化”表述不会削弱 PR #41 已经验证过的精确边界。

### 8.6 Eval 通过标准

Candidate 只有在以下条件同时满足时才适合进入规范性基线：

- 新增候选场景能够区分“最小必要复杂度”与“机械少代码”；
- Agent 能拒绝没有当前证据的未来式抽象 / 灵活性；
- Agent 不会因为该纪律拒绝当前必要的安全、验证、重构或真实抽象；
- `B-EU-07`、`B-EU-08` 不发生语义回归；
- 不引入新的 Human Confirmation Loop；普通低影响、可逆的实现裁决仍由 Agent 自主完成；
- 不改变 Ready to Integrate / Integration Boundary。

## 9. Candidate 生命周期

在正式集成前，该能力保持 **Candidate / Pending Targeted Eval**。

- **Producer：** Phase 3 Engineering Discipline Research；
- **Trigger：** WI-01 将该方向选为首项研究，并已有 PR #41 / PR #42 与多来源外部证据；
- **Current Consumer：** 当前只供 WI-02 评估、后续专项评估设计和 WI-03 边界判断使用；
- **Persistence：** 仅保存在本 Research，不构成 Consumer 必须遵守的规则；
- **Promotion Trigger：** Candidate Targeted Eval 获得有效当前证据且 AI Review 无 Blocking / Medium Finding；
- **Update：** 新外部证据、Eval 失败或 Consumer Adoption 发现错误边界时重新修订 Candidate；
- **Supersede：** 正式 Engineering Discipline 集成后，由规范性能力替代本文中的 Candidate 规则；本文继续作为研究依据，不与正式权威竞争；
- **Escalation：** 如果验证过程中发现需要改变 Core Method、Architecture、Skill Contract 或重大长期架构方向，返回相应权威层，不在 Research 中静默修改。

## 10. WI-02 结论

WI-02 研究结论为：

1. **该工程纪律有充分继续建设价值。** YAGNI、Simple Design、Google Engineering Practices、Sandi Metz、Go 官方实践与本地 PR #41 / #42 在核心方向上形成多来源支持。
2. **当前缺口不是“要求写更少代码”，而是缺少复杂度正当性判断。**
3. **候选纪律必须同时防止两个极端：** 推测性过度设计，以及以“简单”为名牺牲正确性、清晰性、安全、验证和代码可修改性。
4. **不需要修改 Core Method 或 Engineering Capability Architecture。**
5. **当前不应新增 Skill。** 该能力更适合作为独立 Engineering Discipline，并由 `execute-unit` 薄引用。
6. **Candidate 状态保持 Pending Targeted Eval。** 当前只完成可执行 Eval 设计，不提前修改 `SKILL.md`。
7. **WI-03 的进入条件已满足。** 本研究没有暴露必须先修订工程能力架构的问题，可以继续研究“精准修改与差异范围控制”。

因此，本轮建议关闭 WI-02 的 Research / Candidate Design 工作，但不得把 Candidate 状态误报为“正式工程纪律已经集成”。
