# 实现最小化与推测性复杂度控制研究

**研究日期：** 2026-09-02  
**本项目基线：** `dygapp/agentic-dev` `master@070cbb448118a6ee0494063c2d2c8ae689bfb5f3`  
**对应工作项：** WI-02 — 实现最小化与推测性复杂度控制  
**性质：** 研究（Research）与候选能力设计，非规范性权威

## 1. 研究目标

本文研究 **Implementation Minimality & Speculative Complexity Control（实现最小化与推测性复杂度控制）** 是否值得成为 `agentic-dev` 的正式工程纪律，以及它应如何与当前 `execute-unit`、PR #41 的配置责任 / 已有能力复用规则、PR #42 的 Karpathy Skills 研究结论组合。

本研究解决的不是“如何让代码尽可能少”，而是：

> 在满足当前权威需求、验证责任、工程健康和长期约束的前提下，如何避免 Agent 为尚未出现的未来需求提前引入没有当前证据支持的功能、抽象、配置、扩展点、依赖和结构复杂度。

本文完成 Research 与 Candidate Design，并给出后续 Draft Capability / Targeted Eval 设计依据；它本身不修改 Method、Architecture、Skill Contract 或任何 `SKILL.md`，也不构成 Consumer 必须遵守的规范。

## 2. 证据来源与基线

### 2.1 Martin Fowler — YAGNI

- 来源：Martin Fowler，`Yagni`；
- 发布日期：2015-05-26；
- URL：`https://martinfowler.com/bliki/Yagni.html`；
- 本次读取日期：2026-09-02；
- 证据类型：专家方法总结 / Extreme Programming 设计实践解释。

关键证据：

- 不应因为预计未来会需要某项能力，就提前实现当前尚未使用的推测性功能（presumptive feature）；
- 提前实现不仅有构建成本，还有延迟当前价值的成本和持续携带额外复杂度的成本；
- 同样的判断适用于为未来灵活性提前创建抽象与参数化；
- 这并不意味着禁止所有抽象；使当前需求更难理解的未来式抽象应被高度怀疑；
- YAGNI 不应被解释成拒绝重构、自测试或其他保持代码可修改性的工程实践；
- 如果一个面向未来的选择几乎不增加当前复杂度，却能显著降低已经可预见的后续成本，可以单独进行成本判断，而不是机械拒绝。

这一来源提供了最重要的反向边界：**“未来需求没有证据时不提前建设”不等于“禁止为当前代码健康付出成本”。**

### 2.2 Kent Beck Simple Design，经 Martin Fowler 整理

- 来源：Martin Fowler，`Beck Design Rules`；
- 发布日期：2015-03-02；
- URL：`https://martinfowler.com/bliki/BeckDesignRules.html`；
- 本次读取日期：2026-09-02；
- 证据类型：专家整理；文中说明 Kent Beck 复核过该文章，并引用 XP Simple Design 的权威表述。

核心规则包括：

1. 测试通过；
2. 不保留重复逻辑；
3. 清晰表达程序员意图；
4. 使用尽可能少的类、方法或其他设计元素。

该来源说明“最少元素”不是孤立指标，它必须与正确性、表达意图和重复消除共同理解。因此不能把实现最小化退化为：

```text
更少行数 = 更好
更少函数 = 更好
没有抽象 = 更好
```

### 2.3 Google Engineering Practices — Complexity / Over-engineering

- 来源：`google/eng-practices`；
- 仓库状态：已归档，但仍是长期公开的 Google 工程实践材料；
- 研究基线：`master@3bb3ec25b3b0199f4940b1aa75f0ac5c5753301c`；
- 文件：`review/reviewer/looking-for.md`；
- 文件 Blob：`c27e26edbf0f42603a16dd719c825f6801226191`；
- URL：`https://github.com/google/eng-practices/blob/3bb3ec25b3b0199f4940b1aa75f0ac5c5753301c/review/reviewer/looking-for.md`；
- 证据类型：成熟大型软件组织的工程实践。

该材料把过度工程（over-engineering）描述为：代码比实际需要更通用、增加系统当前并不需要的功能、解决开发者猜测未来可能出现的问题，而不是已经知道当前需要解决的问题。

同时它把复杂度与两个可观察结果联系起来：

- 代码难以被读者快速理解；
- 后续开发者更容易在调用或修改时引入错误。

### 2.4 Sandi Metz — The Wrong Abstraction

- 来源：Sandi Metz，`The Wrong Abstraction`；
- 发布日期：2016-01-20；
- URL：`https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction`；
- 本次读取日期：2026-09-02；
- 证据类型：专家工程经验。

该材料说明错误抽象可能比暂时重复更昂贵。典型失败路径是：

```text
发现表面重复
→ 立即抽象
→ 新需求与抽象只有部分匹配
→ 增加参数和条件分支维持抽象
→ 抽象逐渐同时承载多个并不真正相同的概念
→ 修改越来越困难
```

这不能被机械解释成“优先复制代码”，而应与 Simple Design 的“不重复”共同阅读：**重复是设计信号，但并不是所有重复都已经证明存在稳定、正确的共享抽象。**

### 2.5 Go 官方 Code Review Comments — Interfaces

- 来源：The Go Programming Language，`Go Wiki: Go Code Review Comments`；
- URL：`https://go.dev/wiki/CodeReviewComments`；
- 本次读取日期：2026-09-02；
- 证据类型：官方语言工程实践；
- 适用范围：该具体规则首先适用于 Go，用作“抽象应由真实使用形状驱动”的技术实例，不直接泛化为所有语言的接口规则。

Go 官方材料建议不要在真实使用出现之前定义接口，因为没有现实使用示例时，很难判断接口是否必要、应该包含哪些方法。

### 2.6 当前仓库本地证据

#### PR #41 — 配置责任与已有能力复用

当前 `execute-unit` 已明确：

- 不因为发现字面量就机械把值外部化；
- 根据维护者、变化来源、稳定性和安全 / 协议约束判断配置责任；
- 实现通用能力前先检查当前代码库、框架、标准库和已引入依赖；
- 已有能力满足真实契约时优先复用，并只用薄适配承载项目差异；
- 不为了复用扩大依赖面、改变产品行为或覆盖当前 Architecture Authority。

这些规则已经在限制“为了未来变化而配置化”和“为了通用性而重新建设已有能力”。

PR #42 已识别两个候选增强方向：

- 推测性抽象警示（Speculative Abstraction Warning）；
- 推测性灵活性警示（Speculative Flexibility Warning）。

PR #42 只使用了一个第三方项目作为定向 Research。本次 WI-02 用多来源独立证据对这一候选方向进行验证、限制和完善。

## 3. 多来源一致结论

### 3.1 当前责任优先于未来猜测

YAGNI、Google Engineering Practices 和 PR #42 都反对仅根据“以后可能需要”提前建设功能或通用性。

共同语义可以收敛为：

> **当前新增复杂度必须有当前可追溯的需求、约束、风险或工程责任支撑。**

### 3.2 复杂度本身存在持续成本

复杂度不仅消耗当前开发时间，还会影响：

- 阅读和理解；
- 修改和调试；
- 测试与验证；
- 后续功能的实现成本；
- 错误概率；
- 回滚与替代成本。

因此“现在顺手把未来能力一起做掉”不能只比较当前编码成本，还必须考虑额外复杂度的持续携带成本。

### 3.3 抽象应该追随已观察到的稳定形状

Go 官方接口建议、Sandi Metz 的错误抽象分析和 YAGNI 对未来抽象的讨论共同支持：

- 不因单一实现“以后可能有第二种”就预先创建通用接口；
- 不因两个片段表面重复，就自动假设它们属于同一个稳定概念；
- 当前已经存在多个真实消费者 / 变体，并且共享语义已经清晰时，抽象仍然是合理工具；
- 错误抽象开始依赖大量条件参数维持时，应允许退回更直接的结构重新观察真实形状。

### 3.4 最小化不是最少代码

Beck Simple Design 和 Google 的可理解性要求共同否定“代码越短越简单”。

实现最小化必须同时满足：

- 当前行为正确；
- 当前验收义务可验证；
- 当前安全、性能、可观察性等有效约束；
- 代码意图清晰；
- 当前维护成本合理；
- 不为了减少元素而制造晦涩控制流或隐藏真实差异。

### 3.5 保持代码可修改性不是推测性功能

不能用“最小实现”作为以下行为的借口：

- 不写当前必要测试；
- 拒绝为了当前变更做必要的小规模行为保持重构；
- 绕过当前安全、错误处理或可观察性责任；
- 拒绝处理已经直接阻塞当前任务的代码健康问题。

## 4. 需要显式处理的张力与边界

### 4.1 YAGNI 与当前长期约束

如果当前 Repository Authority 已经存在：

- 公共契约；
- 难以回滚的数据格式；
- 已确定的部署拓扑；
- 当前必须满足的兼容义务；
- 安全 / 隐私要求；
- 已经确认的多消费者 / 多实现需求；

这些属于**当前约束**，不是未来猜测。`execute-unit` 不应为了追求简单而忽略它们；高影响决定仍应返回 `technical-plan` 或适当权威层。

### 4.2 不重复与错误抽象

本研究的收敛判断是：

> **不要把重复数量本身当成抽象触发器；应判断重复是否已经代表同一稳定语义。**

如果当前差异只是实现偶然相似、未来变化方向仍不清楚，允许暂时保留小规模局部重复；如果已经存在稳定共享概念，且抽象能让当前意图更清晰、减少真实重复而不引入未来式分支，则适当抽象仍然合理。

### 4.3 低成本演进准备

YAGNI 并不要求拒绝所有面向未来的设计选择。某个准备如果：

- 几乎不增加当前理解和维护成本；
- 不形成额外公共承诺或复杂扩展面；
- 有当前证据表明它显著降低已经可见的后续成本；

可以单独权衡，而不是机械删除。

## 5. 与当前 `execute-unit` 的缺口分析

当前 `execute-unit` 已经具备良好基础：

1. 单执行单元边界；
2. 实现满足 Current Unit 所需的最小变更；
3. 不扩大未经授权的 Product Scope；
4. 不顺手修复无关相邻问题；
5. 不把 Current Unit 变成完整 Feature 重构机会；
6. 配置责任必须有真实维护者与变化来源；
7. 优先检查和复用当前代码、框架、标准库与依赖；
8. 必要当前验证必须闭环。

当前主要缺口不是“简单优先”，而是更明确的**复杂度正当性判断**。

### 5.1 未来式抽象缺少显式默认判断

当前“最小变更”可以间接推导出不要提前抽象，但没有显式说明：为假想第二实现建立 Strategy / Factory / Interface、为尚不存在的消费者建立扩展点、为未出现的变化维度参数化，都需要当前证据，而不是因为“更可扩展”就自动合理。

### 5.2 范围没有扩大，不等于结构复杂度就必要

一个实现可能完全不增加产品 Scope，却增加额外类、接口、配置、依赖或抽象层。因此“产品范围控制”和“实现复杂度正当性”是相关但不同的工程判断。

### 5.3 需要防止伪最小化

如果只增加“不要多做”规则，Agent 可能错误地选择难读的一行式实现、拒绝当前必要的小规模重构，或者把测试、安全和可观察性误认为额外复杂度。

### 5.4 PR #41 的具体规则需要统一上层解释

配置治理和已有能力复用背后存在一个共同判断：

> **新增结构复杂度应能够解释其当前责任和当前证据。**

这一统一视角可以减少未来继续以单点 Finding 追加零散规则，但不得削弱 PR #41 已经形成的精确边界。

## 6. Candidate Capability：实现最小化与推测性复杂度控制

### 6.1 候选核心规则

> **在满足当前权威需求、验证责任、有效长期约束和当前工程健康的前提下，选择当前证据能够支持的最低必要复杂度。仅服务假想未来需求的功能、抽象、配置、扩展点、依赖、层次或条件分支，默认不进入当前实现；只有存在可追溯的当前责任、当前变化证据或明确的低复杂度高收益理由时才例外。**

“最低必要复杂度”不是最少行数或最少文件，而是避免没有当前价值的结构和行为。

### 6.2 当前正当性来源

新增复杂度可以由以下当前证据之一或组合支持：

1. **当前验收义务**：直接满足当前 Specification / Execution Unit 的行为；
2. **当前长期技术约束**：Technical Plan、Architecture、ADR、公共契约或迁移义务已经要求；
3. **当前非功能责任**：安全、隐私、性能、可靠性、可观察性、测试性等当前有效约束；
4. **当前真实变体 / 消费者**：已经存在多个需要统一处理的真实场景，而不是假想第二实现；
5. **当前 Repository Rule / Engineering Rule**：项目明确要求的稳定工程方式；
6. **已有能力集成需要**：为了正确复用当前框架 / 标准库 / 依赖所需的薄适配；
7. **低复杂度高收益的演进准备**：现在几乎不增加理解和维护成本，但有当前证据表明显著降低已知后续成本。

以下理由通常不足：

- “以后可能会有第二种实现”；
- “看起来更企业级”；
- “这样未来更灵活”；
- “设计模式一般都这么写”；
- “把所有值做成配置更通用”；
- “也许以后会换框架”；
- “先把接口 / 插件机制预留出来不会有坏处”。

### 6.3 复杂度承载对象

评估对象不仅是代码行数，还包括：

- 新功能或隐藏行为；
- 新类、接口、继承层次；
- Strategy / Factory / Registry / Plugin 等扩展结构；
- 新配置项、数据库设置、环境变量；
- 新依赖或框架；
- 新公共 API；
- 新数据字段或状态；
- 为未来情况增加的条件分支和错误路径；
- 仅用于“以后方便”的基础设施层。

### 6.4 决策启发式

Agent 在实现前或 JIT 计划中可以依次检查：

1. **它解决当前什么责任？** 能否追溯到当前需求、约束、真实变化或工程责任？
2. **删除它，当前系统会失去什么？** 如果答案只是“以后可能不方便”，默认视为推测性。
3. **当前已有能力是否已满足契约？** 先检查代码库、框架、标准库和已有依赖。
4. **真实共同形状是否已经出现？** 没有真实消费者 / 变体时，不用假想形状设计通用层。
5. **现在做和以后做的总成本如何？** 同时考虑构建、延迟价值、持续携带和未来修复成本，而不是只比较当前编码量。
6. **更少元素是否会损害当前理解和质量？** 正确性、清晰性、安全、验证和代码可修改性不能为了“更少”被牺牲。

这一检查默认是执行纪律，不要求创建新的持久化“复杂度说明表”。只有当决定本身形成跨 Unit 的长期架构约束时，才进入现有 Technical Plan / Architecture / ADR 生命周期。

### 6.5 与抽象的关系

候选纪律不是“反抽象”。允许抽象的典型当前证据包括：

- 已经存在多个真实消费者，并且共享语义稳定；
- 当前重复代表同一个业务 / 技术概念，而不是偶然代码相似；
- 抽象使当前意图更清晰，而不是增加条件参数隐藏差异；
- 当前框架或 Repository Authority 已经规定该扩展模型；
- 抽象直接改善当前测试性、可维护性或明确的非功能责任。

如果抽象主要依靠假想消费者、未来参数或不断增加的条件分支维持，应回到当前真实需求重新判断。

### 6.6 与配置治理的关系

PR #41 的配置责任规则保持不变：

- 没有当前维护者 / 变化来源的动态配置，通常属于推测性复杂度；
- 当前明确由运营、部署或流程维护的值具有当前责任，不属于 YAGNI 禁止对象；
- 稳定安全 / 协议参数不能因为“可配置更灵活”而被错误外部化。

### 6.7 与已有能力复用的关系

PR #41 的复用规则保持不变：

- 重复建设框架已经满足的通用能力会增加不必要实现复杂度；
- 为了“以后可能复用”引入新的依赖同样可能增加不必要依赖复杂度；
- 判断标准始终是当前功能契约、当前约束和已有技术栈实际能力，而不是“自研优先”或“框架优先”的绝对规则。

### 6.8 与重构 / 测试的关系

以下行为不应被机械视为推测性复杂度：

- 为当前变更建立必要测试；
- 为保持当前行为可验证而进行的小规模重构；
- 移除当前已经证明错误的抽象；
- 改善当前代码意图和可修改性的必要调整；
- 当前安全 / 可观察性 / 可靠性责任要求的工程措施。

判断关键不是“用户是否逐字要求了这个代码结构”，而是它是否服务**当前可追溯的工程责任**。

## 7. Architecture Fit 初步判断

### 7.1 不修改 Core Method

本候选能力不增加开发阶段、不改变 WHAT / WHY 与 HOW 边界、不改变 Human Escalation 或 Integration Boundary，因此当前没有 Method Gap。

### 7.2 不新增 Task-oriented Skill

该能力没有独立任务入口、稳定单独输出或自己的 Stage Transition；它主要约束 `execute-unit` 和未来 Engineering Quality Review 在局部实现选择中的判断，因此当前没有新 Skill 的独立职责证据。

### 7.3 候选落点

由于该规则未来可能被多个能力共同消费：

- `execute-unit`；
- Engineering Quality Review；
- Refactoring Discipline；
- Technology Profile；
- framework / dependency upgrade 类任务；

当前最合理的 **Candidate Architecture Fit** 是：

> **独立 Engineering Discipline + `execute-unit` 薄执行引用。**

这只是候选层次判断，不是已经集成的 Repository Authority。WI-03V 必须在两个首批 Candidate 都完成后重新执行 Architecture Fit Review；只有 Fit 仍成立，才形成可被评估的 **Draft Capability**。

### 7.4 不需要先修改 Engineering Capability Architecture

当前架构已经明确允许 Engineering Discipline 独立存在、Discipline 不自动 Skill 化、外部成熟证据主动触发 Candidate，以及 Draft Capability 在 Targeted Eval 之前形成。因此 WI-02 没有暴露需要先修订能力架构的问题，满足进入 WI-03 的条件。

## 8. Candidate Targeted Eval 设计

本节只设计 Candidate Eval。当前 Candidate 尚未形成 Draft Capability，因此**不把这些场景直接加入现有 `evals/behavior/execute-unit.json`**，也不把它们当作当前 Skill 已承诺行为。

WI-03V 的正确顺序是：

```text
Candidate
→ Architecture Fit Review
→ Draft Capability
→ 将 Candidate Eval 设计转换为针对 Draft 的正式隔离 Eval
→ Targeted Eval
→ AI Review
→ Ready to Integrate
→ Human / Repository Integration Decision
```

### 8.1 C-MIN-01 — 假想第二实现导致提前抽象

**场景：** 当前 Unit 只需要为一个已存在支付渠道增加固定签名校验。仓库只有这一个渠道，没有第二实现、插件需求或公共扩展契约。有人建议同时创建 `PaymentVerifier` 接口、Factory、Registry 和配置化 provider 名称，以便“以后增加其他支付平台”。

**期望：**

- 满足当前签名校验；
- 不为假想第二实现创建通用扩展框架；
- 如果当前代码已有合适抽象则复用，不机械删除；
- 保留当前必要的正确性、安全和验证责任；
- 真实第二渠道出现时再根据实际形状重构。

**关键断言：**

1. 不把“以后可能有第二渠道”当作当前接口 / Factory / Registry 的充分证据；
2. 不把“最小化”解释成跳过签名失败路径或安全校验；
3. 已有合适抽象时不为了追求更少元素机械移除；
4. 不宣称未来永远不允许抽象。

### 8.2 C-MIN-02 — 表面重复诱导错误抽象

**场景：** 两个当前流程各有约 8 行相似代码，但一个以业务年度为边界，另一个以自然年为边界；未来变化方向未知。有人以 DRY 为理由，提议提取一个带多个布尔参数的通用函数。

**期望：**

- 不因为行级重复自动提取错误共享抽象；
- 识别两个流程当前语义不同；
- 可以保留小规模局部重复，或只提取真正稳定的共享部分；
- 不用布尔参数和条件分支掩盖真实差异。

**关键断言：**

1. 抽象依据是共享语义，不是重复行数；
2. 不创建根据调用方类型切换语义的万能函数；
3. 存在真正稳定公共计算时允许最小局部提取；
4. 不把“允许暂时重复”解释成忽略所有可安全消除的真实重复。

### 8.3 C-MIN-03 — 伪最小化：为了元素少牺牲可读性

**场景：** 当前功能可以写成复杂的一行表达式，也可以使用一个清晰命名的小函数和直接测试。有人要求“最少代码，所以必须一行写完”。

**期望：**

- 选择能够清晰表达当前意图的直接实现；
- 不以 LOC 或函数数量作为唯一复杂度指标；
- 保持当前必要测试；
- 不额外引入无当前作用的层次。

**关键断言：**

1. 正确性与可理解性优先于机械减少代码行；
2. 可以使用服务当前意图的小函数；
3. 不因为“简单”删除当前验证；
4. 同时避免为该小函数再增加无需要的接口 / 工厂 / 插件层。

### 8.4 C-MIN-04 — 误用 YAGNI 拒绝当前必要重构

**场景：** 当前 Unit 需要新增一个分支，而现有 150 行函数已经存在难以隔离测试的明确行为耦合。一个很小的行为保持重构可以建立测试 Seam，然后实现当前需求。有人说“重构不是需求，按 YAGNI 不做”。

**期望：**

- 允许为当前可验证性和安全实施所必需的小规模行为保持重构；
- 重构范围直接服务当前实现 / 验证，不扩大成完整模块重写；
- 修改前后取得行为保持和新需求的当前证据。

**关键断言：**

1. 不把 YAGNI 用来禁止当前必要的代码健康 / 可测试性工作；
2. 重构与当前 Unit 有明确追溯关系；
3. 不顺手重构整个模块；
4. 有当前验证证明行为保持和新需求满足。

### 8.5 回归场景

正式验证 Draft Capability 时至少回归：

- `B-EU-07`：配置责任判断；
- `B-EU-08`：已有框架能力复用。

目标是确保更高层“实现最小化”Draft 不削弱 PR #41 已经验证过的精确边界。

### 8.6 Eval 通过标准

Draft Capability 只有在以下条件同时满足时才可以进入后续 AI Review：

- 新增场景能够区分“最小必要复杂度”与“机械少代码”；
- Agent 能拒绝没有当前证据的未来式抽象 / 灵活性；
- Agent 不会因为该纪律拒绝当前必要的安全、验证、重构或真实抽象；
- `B-EU-07`、`B-EU-08` 不发生语义回归；
- 不引入新的 Human Confirmation Loop；普通低影响、可逆的实现裁决仍由 Agent 自主完成；
- 不改变 Ready to Integrate / Integration Boundary。

## 9. Candidate 生命周期

WI-02 完成后，该能力状态为：

> **Candidate / Preliminary Architecture Fit Assessed / Pending Draft Capability**

它尚未成为规范权威，也尚未成为当前 `execute-unit` 的新行为契约。

- **Producer：** Phase 3 Engineering Discipline Research；
- **Trigger：** WI-01 将该方向选为首项研究，并已有 PR #41 / PR #42 与多来源外部证据；
- **Current Consumer：** 当前只供 WI-03 边界判断、WI-03V Architecture Fit Review 和 Draft 设计使用；
- **Persistence：** Candidate 仅保存在本 Research，不构成 Consumer 必须遵守的规则；
- **Next Gate：** WI-03V 先重新执行 Architecture Fit Review，再创建未集成的 Draft Capability；
- **Validation：** Targeted Eval 必须针对该 Draft Capability 和其 Draft 消费入口执行，而不是针对不存在的未来规范；
- **AI Review：** Draft 通过有效当前 Eval 后，对最终拟集成变更执行 AI Review；
- **Integration：** AI Review PASS 只达到 Ready to Integrate，不等于自动集成；最终 Merge / Integration 仍由 Human Authority 或 Repository Policy 决定；
- **Update：** 新外部证据、Eval 失败或后续 Consumer Adoption 发现错误边界时，返回 Candidate / Draft 修订并重新验证；
- **Supersede：** 正式 Engineering Discipline 集成后，由规范性能力替代本文中的 Candidate；本文继续作为研究依据，不与正式权威竞争；
- **Escalation：** 如果后续发现需要改变 Core Method、Architecture、Skill Contract 或重大长期架构方向，返回相应权威层，不在 Research / Draft 中静默修改。

## 10. WI-02 结论

1. **该工程纪律有充分继续建设价值。** YAGNI、Simple Design、Google Engineering Practices、Sandi Metz、Go 官方实践与本地 PR #41 / #42 在核心方向上形成多来源支持。
2. **当前缺口不是“要求写更少代码”，而是缺少复杂度正当性判断。**
3. **Candidate 必须同时防止两个极端：** 推测性过度设计，以及以“简单”为名牺牲正确性、清晰性、安全、验证和代码可修改性。
4. **当前不需要修改 Core Method 或 Engineering Capability Architecture。**
5. **当前不应新增 Skill。** 初步 Architecture Fit 更适合独立 Engineering Discipline，并由 `execute-unit` 薄引用；这一落点仍须在 WI-03V 重新确认。
6. **当前状态不是 Pending Targeted Eval，而是 Pending Draft Capability。** 现行架构要求先形成 Draft，再用 Targeted Eval 验证 Draft。
7. **WI-03 的进入条件已满足。** 本研究没有暴露必须先修订工程能力架构的问题，可以继续研究“精准修改与差异范围控制”。

因此，本轮可以关闭 WI-02 的 Research / Candidate Design 工作，但不得把 Candidate 状态误报为“正式工程纪律已经集成”或“已经通过运行时验证”。
