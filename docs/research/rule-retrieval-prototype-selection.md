# 最小规则检索原型选择

决策日期：2026-09-08

阶段：**规则治理与知识激活 v1 / 阶段 B / B2 — 原型选择**

文档性质：**研究决策 / B3 原型实施边界**

选择基线：`master@f287d0c7852e2b040e84373cdaee3de40fbef961`

B1 契约：`docs/research/minimal-rule-retrieval-contract.md`

本文只选择能够进入 B3 的最小原型形态，不实现原型本身，不修改现行指南、Skill、方法、架构、工程纪律或技术画像。

## 1. 选择结论

B2 选择：

> **JSON 派生规则索引 + Python 标准库薄查询器**

拟在 B3 使用的原型位置：

```text
evals/rule-retrieval/rule-index.json
evals/query_rule_index.py
```

两者共同构成一个评估原型：

- `rule-index.json` 只保存可从当前仓库权威重新构建的派生检索信息；
- `query_rule_index.py` 只负责按 B1 契约执行确定性过滤、来源身份检查、关系分组和回退信号；
- 查询器不解释或重写规范性规则，不授予权限，不缓存人工授权；
- 原型删除后不损失任何规范性事实。

这不是新的运行时层，也不是未来长期实现承诺。阶段 C / D 可以基于真实评估结果保留、替换或删除它。

## 2. 为什么选择这一形态

### 2.1 与当前仓库已有模式一致

当前 `evals/` 已使用：

- JSON 场景语料；
- Python 评估执行器；
- Python 标准库 `json`；
- 无第三方 Python 包的薄执行模式。

因此本方案不要求引入新的语言、包管理器、数据库或解析依赖。

### 2.2 能满足 B1 的确定性要求

B1 要求：

- 稀疏查询字段可显式表达；
- 全部已触发条件必需规则必须被召回；
- 每个结果项独立回指规范性源；
- `equivalent / scope-variant / superseded-by` 可以机器检查；
- 来源陈旧时能明确回退；
- 阶段 C 能记录规则召回、无关结果、读取数量等指标。

结构化 JSON 比 Markdown 表格更适合进行这些确定性检查；薄 Python 查询器则避免把检索行为交给模糊文本搜索或 Agent 自由解释。

### 2.3 保持人类可审计

JSON 原型仍应使用缩进、稳定字段名和短摘要。人工可以直接检查：

- 查询条件；
- 源路径与章节；
- 来源身份；
- 规则强度；
- 关系；
- 必需检查。

不需要图数据库或专用可视化工具才能理解原型。

## 3. 备选方案比较

| 方案 | 优点 | 主要问题 | B2 结论 |
|---|---|---|---|
| Markdown 段落 / 表格索引 | 最易人工阅读；无执行依赖 | 条件集合、关系、陈旧检测和阶段 C 计量需要再次解析；容易把“人工可读索引”误当作查询实现 | **不选为 B3 主原型**；可继续作为 Research 解释载体 |
| YAML 派生索引 | 结构化且较易手工编辑 | 当前仓库没有 YAML 解析依赖；为了原型引入 PyYAML 或自写解析器没有必要 | **不选** |
| JSON 派生索引，无查询器 | 无第三方依赖；结构化 | 仍需 Agent / 人工自行解释过滤，无法稳定验证完整召回和误激活 | **不足以单独满足 B1** |
| 单一 Python 文件内嵌全部规则数据 | 一个文件即可执行 | 数据与执行逻辑耦合，不利于人工审计和独立验证派生索引 | **不选** |
| JSON + Python 标准库薄查询器 | 结构化、确定性、无第三方依赖、适合评估、与现有 evals 模式一致 | 比纯 Markdown 多一个执行文件 | **选择**；额外复杂度与可验证收益匹配 |
| 图数据库 / MCP / 独立服务 | 可扩展复杂关系和远程查询 | 对当前 55 个高影响指南候选及少量跨权威关系明显过度；引入新运行时与维护面 | **明确不选** |

## 4. B3 数据边界

B3 不建立全仓库规则库。

首轮原型只覆盖：

1. A2 的 `using-agentic-dev.md` 27 个语义激活单元候选；
2. A3 的 `external-operation-guidelines.md` 28 个条件激活单元候选；
3. 为 A4 高价值重复 / 范围敏感关系提供辨识所必需的少量当前规范性入口或职责消费项；
4. B1 场景中用于验证作用域、职责、阶段、对象、条件差异的必要条目。

默认不索引：

- Research 历史证据全文；
- PR / Issue 历史；
- 已完成项目记录的历史流水；
- 未进入阶段 A 审计面的普通文档；
- 所有技术画像、工程纪律或 Skill 的全文。

如果 B3 发现某个测试场景必须读取未覆盖的当前规范性源，允许补入最小相关条目，但必须记录为什么现有边界不足。

## 5. JSON 原型最小字段

B3 的每个活动条目至少应表达：

```text
entry_key            # 仅为原型内部定位，不是永久规则 ID
role                 # authority / pointer / consumer
source.path
source.section
source.identity      # 当前源内容身份，用于陈旧检测
scope
responsibilities[]
stages[]              # 可空
subjects[]            # 可空
conditions[]          # 可空
strength              # core-invariant / required-when-triggered / default-guidance
activation_summary
required_checks[]
relations[]           # 仅 equivalent / scope-variant / superseded-by
```

约束：

- `entry_key` 不具有规范性身份；未来可以重建或改变；
- `source.section` 应使用当前可读章节路径，不要求源文件增加 Front Matter；
- `source.identity` 使用可由当前 Git 内容重算的身份；
- 不把完整规则正文复制进 JSON；
- 不建立独立数值优先级；
- `evidence` 不作为活动规则条目进入首轮索引。

## 6. 查询器最小职责

`evals/query_rule_index.py` 在 B3 只需要：

1. 接收 B1 的逻辑查询维度：`scope + responsibility + [stage] + [subject] + [conditions]`；
2. 完整召回当前适用的核心不变量和全部已触发条件必需规则；
3. 只在直接相关时包含指导默认；
4. 排除作用域不匹配、条件未触发、已明确取代的条目；
5. 对 `equivalent` 只做分组展示，不合并掉独立源指针；
6. 检查命中条目的 `source.identity`；
7. 出现来源陈旧、指针失效、范围冲突、未建模条件或高影响授权不确定时返回显式 `fallback_required`，而不是猜测；
8. 输出机器可读 JSON，便于 B3 / 阶段 C 统计。

查询器不得：

- 自动修改源文档或索引；
- 自动新增规则；
- 自动决定权限；
- 自动根据时间戳推断取代；
- 用固定 Top-K 截断条件必需规则；
- 调用网络服务、模型或数据库。

## 7. 来源身份与陈旧检测

B3 优先采用 Git blob 兼容的内容身份。

实现可以通过 Python 标准库直接对当前文件内容计算 Git blob SHA-1，或使用等价的本地 Git 只读读取；选择其中更薄、可测试的一种即可。

要求：

- 只检查当前命中或被关系依赖的源；
- 单一源变化只使相关条目陈旧；
- 陈旧时返回回退信号；
- 不要求因为一个文件变化机械重建整个索引。

该设计继续不要求源文件增加统一文件头。

## 8. 原型可删除 / 可重建证明方式

B3 至少验证：

1. 删除 `rule-index.json` 和查询器不会删除任何规范性规则；
2. 每个索引活动条目都能回指当前规范性源；
3. 索引摘要没有新增源文档不存在的约束；
4. 重建依据来自当前仓库权威 + 阶段 A 语义审计过程，而不是聊天历史；
5. Research 只保留为什么这样映射的证据，不成为查询器的执行规则来源。

## 9. 为什么现在仍不引入文件头

B2 进一步确认：当前原型不需要给 Guide 或其他文档统一增加 Front Matter。

原因：

- 路径 + 章节 + 来源内容身份已经满足 B1 的定位和陈旧检测；
- JSON 可以承载原型所需的作用域 / 职责 / 条件元数据；
- 当前 B3 只覆盖有限高影响规则面，尚未出现稳定章节身份无法工作的证据；
- 若 B3 实际暴露章节定位频繁漂移，再以具体失败证据评估局部最小元数据即可。

## 10. B2 完成结论

B2 选择已经满足协调计划的五个标准：

- **可从仓库权威重建**：JSON 与查询器均为派生原型；
- **精确回指来源 / 段落**：条目保存路径、章节和来源身份；
- **能检测来源漂移**：命中源身份变化触发回退；
- **能支持评估**：查询与结果均可机器读取，适合 B3 / C 统计；
- **无新运行时层**：复用仓库已经存在的 JSON + Python 标准库评估模式，不引入第三方包、数据库、MCP 或服务。

因此下一实际工作应进入：

> **B3 — 原型验证**

B3 才负责创建最小 JSON 索引和薄查询器、对阶段 A 规则面建立首轮索引、执行手工与机器检查，并证明删除原型不会损失权威。
