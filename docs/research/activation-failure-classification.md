## 1. 分类维度

A5 使用以下五类失效：

- **发现 / 激活失败**：规则已经存在且适用于当前任务，但没有进入当前上下文或正确职责路径；
- **选择 / 冲突失败**：多个可见规则、状态或证据同时存在时，Agent 选择了错误对象、错误强度或错误职责；
- **指令密度问题**：规则虽可见，但被大体量、低相关或重复上下文淹没，导致注意力和执行精度下降；
- **误导 / 陈旧上下文**：编号、历史 `PASS`、旧基线、瞬时状态或过期证据被错误当作当前事实 / 授权；
- **真实规则缺口**：当时的当前权威中确实缺少足以得到正确行为的长期语义，需要新增或补充规则。

一个场景可以同时具有主类型和次类型。A5 不为了分类整齐强迫每个场景只有一个原因。

## 3. 逐场景依据

### 3.1 S-01 — 纯激活失败基准

PR #72 的仓库事实非常明确：

- “项目路线图与集成状态”边界在 PR #39 后已经进入 `using-agentic-dev.md`；
- PR #70 合并后仍机械派生尾部状态 PR，说明规则没有进入 `agentic-dev` 自身高影响 AI 复核的实际路径；
- PR #72 修改 `AGENTS.md` 与 `docs/project/ai-review-guidelines.md` 建立激活入口，同时保持 `using-agentic-dev.md` 不改。

因此 S-01 不属于“规则写得不够多”，而是最适合作为阶段 C 的**已有规则未被激活**基准。

### 3.2 S-02 — 误导线索 + 使用层规则缺口

核心方法已经区分规格、切分、就绪和执行职责，但真实使用方场景表明：预编号 `EU-xx`、项目路线图排序和 Issue 标签足以让新上下文提前推断执行身份。

PR #60 因此同时更新使用指南、`slice-work` 与 `readiness-check`，并以运行时评估证明新的明确身份链有效。说明当时不只是“没读到规则”，而是**通用阶段边界不足以消除这些具体误导线索**。

当前基线已经具备该规则，后续再发生相同行为应优先检查激活、检索和上下文误导，而不是继续新增同义规则。

### 3.3 S-03 — 历史状态误导 + 重入规则缺口

正确职责返回本身并非新概念；真正缺口是：WHAT / HOW / 架构基础发生实质修订后，旧候选、稳定标识和历史就绪结果是否继续有效。

PR #61 明确回答“不继续有效”，并要求新的当前权威基础重新进入 `slice-work → readiness-check`。因此该场景是**已有职责框架 + 缺少重入 / 失效语义**的混合型问题。

### 3.4 S-04 — 平台专项规则缺口

“证据先于声明”本来已经存在，但它不能自动回答 GitHub Actions 中 `paths`、label、手工门禁、可复用工作流等实际触发拓扑是否覆盖当前声明。

PR #61 增加专项对账链，说明这是一个真实的**平台专项执行语义缺口**，而不是靠加载更多通用证据原则就能解决。

当前后续检索必须能够：

- 在普通非 GitHub Actions 场景不加载整套平台规则；
- 一旦声明依赖 GitHub Actions 完成证据，就能激活实际触发拓扑对账。

### 3.5 S-05 — 明确的历史规则缺口

PR #59 直接以“补齐两个定向治理缺口”为目标：

1. 临时执行证据被接受为长期输入后的持久化、来源与完整性关系；
2. 单实例评审环境的所有者、租约、陈旧运行和人工占用策略。

因此 S-05 不能被重新包装成“原规则其实已经有，只是没激活”。

但在当前基线，这些语义已经进入使用指南、外部操作指南与 GitHub Actions Skill。A4 已证明新的风险是**完整语义多点维护和按需激活不精确**，所以当前工作重点已从“补规则”转为“检索 + 去重”。

### 3.6 S-06 — 本地权威恢复中的误导与使用指南缺口

Issue #33 Finding 1 明确记录：使用方中的精确上游基线与入口表述会诱导后续 Agent 在普通开发时持续跨仓库读取 `agentic-dev`，并且实际需要人工纠正。

该场景同时包含：

- **误导上下文**：精确基线被错误解释成持续读取义务；
- **发现 / 激活问题**：使用方本地方法 / 项目路线图没有成为最强普通恢复入口；
- **真实使用指南缺口**：既有使用方基线升级 / 选择性采用生命周期当时不够显式。

Issue #52 后续正向证据证明更合适的形态是：只选择性固化当前使用方真正需要的可复用能力，保留使用方覆盖边界，并不复制 `agentic-dev` 自身项目事实。

## 4. 指令密度的证据边界

六个历史场景中，**没有一个能够仅凭现有仓库事实被可靠定性为“指令密度是主要根因”**。

当前仓库确实存在：

- 两份高影响指南体量大；
- A4 发现多个完整规则在多层重复维护；
- S-01 证明规则存在仍可能没有进入正确路径。

这些事实支持把“指令密度 / 上下文噪声”作为阶段 C 必须测量的候选机制，但不支持在 A5 先验宣称历史失败就是因为输入令牌过多或指南太长。

因此阶段 C 应通过 A/B 新上下文运行直接比较，而不是把文件大小当作因果证据。

## 5. 当前规则缺口与历史规则缺口必须分开

A5 最重要的边界是：

> **历史上存在过真实规则缺口，不等于当前基线仍缺这些规则。**

当前 `master@5784373d97e408a88494c5db696a02fbcc7aa285` 已经包含 PR #59、#60、#61、#72 等收敛结果：

- S-01 的激活入口已经补入项目 AI 复核；
- S-02 的规划候选 / 候选执行单元 / 已就绪执行单元身份链已经固化；
- S-03 的上游实质修订后重新切分 / 就绪规则已经固化；
- S-04 的声明 / 风险 ↔ GitHub Actions 实际触发拓扑对账已经固化；
- S-05 的持久证据晋升与单实例资源生命周期已经固化；
- S-06 的既有使用方选择性采用与本地权威边界已经固化并获得正向使用方证据。

所以在当前里程碑继续面对这些场景时，默认问题不应再是“再补一条同义规则”，而应依次检查：

```text
规则当前是否存在
→ 是否被正确发现 / 激活
→ 是否选择了正确范围和强度
→ 是否被陈旧 / 误导上下文覆盖
→ 是否存在重复导致的噪声或漂移
→ 只有都不是，才重新判定真实规则缺口
```

## 6. 阶段 A 结论

A1～A5 已经共同证明：

1. 当前存在可按语义切分的规则激活单元，而不是只能整文件加载；
2. 当前存在合理的薄摘要 / 职责消费，也存在值得后续做减法的完整重复；
3. 历史失败不能统一归为激活失败，其中 S-04 / S-05 等确实曾有真实规则缺口；
4. 这些历史缺口已经进入当前仓库权威，当前不需要为了覆盖相同场景继续新增规则；
5. S-01 提供直接的纯激活失败证据，S-02 / S-03 / S-06 提供误导 / 陈旧上下文与选择问题证据；
6. “指令密度导致失败”目前仍是需要阶段 C 验证的假设，而不是已证明结论；
7. 下一步最值得验证的是：**能否用更小、可重建、范围敏感的检索入口，把当前已存在的正确规则稳定送入任务上下文，同时减少完整规则多点维护和无关上下文。**

因此阶段 A 的完成条件已经满足，下一阶段应进入：

> **阶段 B — 最小检索模型 / B1 — 冻结最小检索契约**

阶段 B 不应自动引入全库 YAML Front Matter、规则图数据库、MCP 或新的规范性索引权威。B1 先根据 A2～A5 结果确定真正具有辨识力的最小输入 / 输出 / 回退 / 重复与取代语义，再决定载体。
