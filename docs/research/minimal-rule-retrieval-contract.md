# 最小规则检索契约

冻结日期：2026-09-08

阶段：**规则治理与知识激活 v1 / 阶段 B / B1 — 冻结最小检索契约**

文档性质：**研究契约 / B2～C 阶段验证基线**

冻结基线：`master@d5bcd38551a9b6c96f302457bd23d32fec166a2f`

本文把阶段 A 已确认的激活单元、范围敏感关系、重复候选和历史失效类型收敛为一个最小、工具无关的检索契约，供 B2 原型选择、B3 原型验证和阶段 C A/B 评估使用。

本文不是新的规范性规则权威。检索结果只能帮助 Agent 找到当前需要读取和执行的仓库权威，不能替代源文档、改变仓库权威顺序、授予额外权限，也不能把 `docs/research/*` 提升为执行规则。

本文使用 `scope`、`responsibility` 等逻辑键，只为让 B2～C 能稳定描述和测试同一语义；B2 可以采用等价载体或字段名，不要求把这些键原样写入 Markdown、YAML / JSON 或文件头。

## 1. B1 只冻结什么

B1 只冻结五件事：

1. 什么最少输入足以辨识当前需要的规则；
2. 如何从匹配项构造“最小正确规则集”，避免漏掉必需规则或装入大量无关规则；
3. 检索至少返回什么，才能既可解释又不复制完整规则；
4. 无索引、来源陈旧、结果冲突或无法可靠判断时如何回退；
5. 如何表示重复、范围差异和取代，而不制造第二权威。

B1 不选择 Markdown、YAML / JSON、脚本、数据库、MCP 或其他具体实现，也不修改现行指南、Skill、方法、架构、工程纪律或技术画像。

## 2. 核心原则

### 2.1 使用稀疏查询，不要求人工填写完整表单

最小查询由两个必需语义维度和三个条件维度组成：

```text
必需：作用域 + 当前职责
条件：阶段 + 目标对象 + 风险 / 状态条件
```

这些是**逻辑输入**，不是要求用户手工填写的表单。实现可以从当前仓库、任务和已确认状态中可靠推导；只有无法可靠推导且该信息会改变规则选择时，才需要显式补充。

未知条件不得为了“完整”而猜测。

### 2.2 作用域必须保真

阶段 A 已确认，多组同义规则只有在保留项目 / 仓库范围后才能正确选择，例如：

- `agentic-dev` 自身默认中文表达，不等于所有使用方项目都必须中文；
- `agentic-dev` 自身的人工 / 集成边界，不等于使用方项目的集成策略；
- 使用方仓库权威优先，不等于普通开发持续跨仓库读取 `agentic-dev`。

因此作用域不是可省略的附加信息。

跨仓库任务也不能只压缩成“跨仓库”一个标签。至少必须能够识别：

- 当前任务事实由哪个仓库权威主导；
- 当前职责正在读取或改变哪个仓库 / 外部对象；
- 其他仓库是只读方法来源、使用方事实来源，还是获得了明确写入授权。

B1 不规定具体数据结构，但禁止因为压平作用域而扩张授权或误激活其他项目规则。

### 2.3 检索只返回规则入口，不复制第二份权威

检索结果可以包含短语义摘要、匹配理由和必需检查，但必须精确回指当前规范性来源。

派生摘要不能脱离源指针成为独立长期规则；检索层也不能通过“更完整”“更晚更新”等理由覆盖仓库权威顺序。

### 2.4 不用检索内部优先级覆盖仓库权威

B1 不定义独立数值优先级。

发生范围、强度或语义冲突时，仍回到当前仓库权威顺序和规范性源文档判断，而不是让索引分数决定规则真伪。

### 2.5 陈旧或不确定时回退当前仓库

索引不可用、不可信或无法唯一解释当前高影响行为时，正确动作是直接读取当前仓库权威，而不是继续依赖旧摘要，也不是把“没有检索结果”解释成“没有规则”。

## 3. 最小输入契约

### 3.1 `scope` — 作用域，必需

回答：**当前任务由哪个项目 / 仓库的权威约束，当前职责又作用于哪个仓库或外部对象？**

单仓库任务至少需要识别当前权威仓库。

跨仓库任务至少保留主权威域与当前操作目标，不允许把多个仓库的授权折叠成一个通用“跨仓库已授权”状态。

### 3.2 `responsibility` — 当前职责，必需

回答：**当前 Agent 正在承担什么职责？**

典型语义包括但不限于：

- 新上下文恢复；
- 需求澄清 / 规格说明；
- 技术规划；
- 工作切分 / 就绪检查；
- 执行；
- 调试；
- 验证；
- 整体收敛；
- AI / 人工复核；
- 集成决策；
- 外部状态操作。

B1 不冻结永久枚举。B2 只需为当前已审计规则建立足够稳定、可测试的职责词汇。

### 3.3 `stage` — 当前阶段 / 门禁，条件必需

只有当规则取决于生命周期位置时提供，例如：

- 规划候选尚未切分；
- 候选执行单元正在就绪检查；
- 已就绪执行单元进入执行；
- 项目进入集成前复核；
- 既有使用方正处于明确基线升级，而不是普通开发恢复。

阶段必须来自当前仓库事实，不能由编号、项目路线图排序、旧 PASS 或历史状态推断。

### 3.4 `subject` — 目标对象 / 声明，条件必需

只有当规则依赖当前处理对象时提供，例如：

- 项目路线图 / 里程碑状态；
- 规格说明 / 技术计划 / 执行单元；
- PR / Issue / 分支；
- GitHub Actions 完成声明；
- 临时工作流产物；
- 单实例评审环境；
- 外部媒体 / 二进制资源。

`subject` 表达“当前处理什么”，不是把整个文件正文塞进查询。

### 3.5 `conditions` — 风险 / 状态条件，条件必需

只记录已经观察到、会改变规则适用性的事实。典型条件包括：

- 外部状态写入；
- 跨仓库；
- 高影响 / 不可逆操作；
- 异步运行；
- 共享资源 / 单实例资源；
- 临时证据晋升为持久输入；
- GitHub Actions 验证；
- 依赖 PR 拓扑；
- 当前 Head / base / 权威基础发生实质变化；
- 来源或索引可能陈旧。

不得为了触发更多规则而推测不存在的风险条件。

## 4. 查询组合与重新检索

### 4.1 最小正常查询

普通任务至少具有：

```text
scope + responsibility
```

如果这两个维度已经足以确定当前需要的薄核心 / 任务职责规则，就不继续增加条件。

### 4.2 条件扩展

只有规则集合会因为生命周期、对象或风险事实不同而变化时，才按需加入：

```text
+ stage
+ subject
+ conditions[]
```

因此 B1 采用**稀疏条件模型**，不是要求每次查询都携带相同的大型字段集合。

### 4.3 职责变化后重新检索

一个查询只描述一个当前职责。

任务从“执行”切换为“验证”、从“验证”进入“集成复核”，或从普通开发进入明确基线升级时，应重新检索；不能把第一次得到的规则集视为整个会话永久上下文。

## 5. 最小正确规则集的构造

B1 不允许未来原型简单按相似度 Top-K 截断结果，因为这可能丢失条件必需规则。

### 5.1 必须纳入

当前查询应纳入：

1. 与当前作用域相符、对当前职责成立的**核心不变量**；
2. 其触发条件已由当前事实满足的**条件必需**规则；
3. 当前职责为独立执行所必需的最小 Skill / 专项消费守卫；
4. 当某条条件必需规则指向平台专项执行语义时，按当前平台条件继续取得该专项来源。

### 5.2 只在相关时纳入

**指导默认**只有在它直接影响当前职责选择、实现或验证，并且没有被当前项目权威明确覆盖时才进入活动规则集。

### 5.3 默认排除

默认不进入活动规则集：

- 触发条件未满足的条件规则；
- 其他项目 / 仓库作用域规则；
- 纯历史证据；
- 已被当前权威明确取代的规则；
- 与当前职责无关的同指南其他段落；
- 为了“保险”而全量加载的相邻规则。

### 5.4 等价重复不能靠任意 Top-K 隐藏

多个当前条目被判断为 `equivalent` 时，可以在展示层标记为同一等价组，减少重复活动上下文，但每个条目仍保留自己的独立源指针。

如果当前职责能够依据仓库权威、条目角色和作用域明确选择一个详细来源，只读取该详细来源即可；其他来源作为重复关系保留，不复制正文。

如果来源之间出现实质差异或无法唯一确定当前应消费哪个来源，则不折叠为单一执行规则，必须回退规范性源并按仓库权威解析。

### 5.5 最小集合不是最少条数

“最小”指：

> **没有缺失任何当前必需规则，同时不装入当前职责不需要的规则。**

因此不能把固定条数、最低令牌数或最少文件数本身作为正确性目标。

## 6. 最小输出契约

每个活动结果至少包含以下信息。

### 6.1 `source_pointer` — 权威指针

必须能够精确回到当前规范性来源：

- 仓库路径；
- 可定位章节 / 段落；
- 用于陈旧检测的来源身份。

来源身份可以是 Git blob SHA、内容摘要或其他等价机制；B1 不规定具体实现，但必须能够判断条目对应的源内容是否已经变化。

一个结果项只对应一个具体源指针；等价组通过关系关联多个结果项，不把多来源压进一个不可追溯的“合成权威”。

### 6.2 `activation_summary` — 短激活摘要

只回答：

> 当前任务为什么需要这条规则，它约束什么？

摘要必须明显短于源规则，不复制完整过程，也不能脱离 `source_pointer` 独立成为长期权威。

### 6.3 `applicability` — 适用信息

至少表达：

- 匹配了哪些输入条件；
- 当前作用域；
- 规则强度。

B1 沿用阶段 A 已证明有辨识力的三档强度：

- **核心不变量**：跨多数任务成立的薄不变量；
- **条件必需**：触发条件成立时必须遵守；
- **指导默认**：稳定默认，但允许当前项目权威 / 当前证据覆盖。

### 6.4 `required_checks` — 必需检查

只列当前职责为了正确消费该规则必须完成的最少检查，例如：

- 重新读取当前 Head / base；
- 确认是否已完成就绪检查；
- 对账声明 / 风险与实际工作流触发；
- 检查持久证据来源与完整性；
- 确认当前仓库是否明确授权高影响操作。

该字段不能新增源权威没有的流程；详细动作仍回到规范性来源。

### 6.5 `matched_by` — 匹配解释

记录哪些查询维度触发了该结果，例如：

```text
scope=consumer
responsibility=readiness-check
stage=upstream-authority-revised
```

该字段用于 B3 / 阶段 C 检查误激活和漏激活。

## 7. 条目角色与最小关系

### 7.1 条目角色

B1 只需要区分：

- **authority**：当前规范性规则来源；
- **pointer**：高层薄摘要 / 激活指针，只负责引导到详细来源；
- **consumer**：Skill / 专项职责为了独立执行而保留的最小消费守卫；
- **evidence**：历史研究或验证证据，仅用于解释 / 评估，不参与活动规则集。

B2 不要求把所有证据做成索引条目；如果为了评估追溯保留 `evidence`，必须与活动规则结果隔离。

### 7.2 最小关系

B1 只冻结三类跨条目关系：

- **equivalent**：当前语义实质等价或高度重复；允许标记等价组，但每个来源仍保持独立可追溯；
- **scope-variant**：主题相近但作用域、强度或职责不同；必须保留区分，不能为了去重合并；
- **superseded-by**：旧规则被当前权威明确取代；活动检索默认不返回旧规则，只有历史研究明确需要时才读取。

不得仅凭文件更新时间、提交时间或“看起来更完整”推断 `superseded-by`。

### 7.3 B1 不提前指定永久唯一规则所有者

A4 已提出若干未来减法候选，但阶段 D 尚未授权重新分配详细规则的长期所有者。

因此 B1 不把某个 Guide / Skill 提前指定成所有等价语义的永久唯一来源。B2 只能依据当前仓库权威、作用域和职责决定本次需要读取哪个现行来源；真正的规则迁移、合并或删除仍留给阶段 D。

## 8. 陈旧检测与回退契约

### 8.1 必须回退的情况

出现以下任一情况，不得继续把派生索引摘要当作当前规则：

1. 索引不存在或不可用；
2. 选中条目的来源身份与当前源文件不一致；
3. `source_pointer` 无法解析；
4. 同一查询得到范围 / 强度相冲突且无法按当前仓库权威唯一解析的结果；
5. 当前职责属于高影响操作，但没有取得可追溯的规范性权威入口；
6. 检索结果涉及授权、合并、发布、部署或其他高影响状态，而当前真实授权状态尚未重新确认；
7. 查询遇到索引未建模的新条件或新规则结构。

### 8.2 回退动作

回退顺序：

```text
当前仓库权威
→ 当前职责直接相关的规范性源文档
→ 必要时读取相邻职责 / 平台专项权威
→ 重新判断当前规则集
```

使用方场景必须先读使用方仓库权威；只有明确基线升级或使用方本地规则无法回答必要方法问题时，才按当前使用指南进入 `agentic-dev` 上游规则。

### 8.3 局部陈旧，不默认使整个索引失效

如果只有某个源文件身份变化，只把受影响条目标为陈旧并直接读取该源。

B2 不需要为了单文件变化每次重建整个索引，除非所选实现无法可靠判断影响范围。

### 8.4 检索结果不授予权限

即使结果正确命中某类操作规则，当前仓库权限、人工授权和实时外部状态仍必须重新读取。派生索引永远不能成为权限缓存。

## 9. 对文件头的 B1 判断

**B1 不要求给项目库文档统一增加文件头。**

原因：

1. 当前契约需要的路径、章节、作用域、职责、强度和来源身份，可以由独立派生索引描述；
2. Git blob SHA / 内容摘要已经能够提供来源陈旧检测能力；
3. 阶段 A 没有证据证明“缺少文件头”是规则未激活的主要根因；
4. 全库文件头会把工具无关契约提前绑定到一种元数据载体，并扩大所有文档的维护面。

B2 如果证明某些高影响规则载体缺少稳定段落身份，可以比较“外部派生索引”和“少量规则载体增加最小元数据”的成本；即使后续需要元数据，也只应作用于真正的规则载体 / 激活单元，不默认覆盖 `docs/research/*`、历史项目记录和普通项目文档。

## 10. 用阶段 A 场景检查输入辨识力

以下只验证 B1 字段能否表达场景差异，不是阶段 C 行为评分。

### S-01 项目路线图集成后状态闭环

```text
scope: agentic-dev
responsibility: ai-review / integration-review
stage: integration-preparation
subject: project-roadmap / milestone-state
conditions: project-state-change
```

应命中项目路线图 / 集成后稳定状态相关规则，不需要加载完整外部操作指南。

### S-02 规划候选身份

```text
scope: consumer-repository
responsibility: slice-work / readiness-check
stage: planning-candidate or candidate-execution-unit
subject: pre-numbered-future-work
```

应命中候选身份 / 就绪授权边界，不能因为编号存在而激活执行授权。

### S-04 GitHub Actions 触发拓扑

```text
scope: current-repository
responsibility: verification
subject: completion-evidence-claim
conditions: github-actions
```

应命中通用证据边界与 GitHub Actions 专项触发拓扑规则，而不激活共享资源 / 证据晋升等无关条件规则。

### S-05 异步共享资源与证据晋升

```text
scope: current-repository
responsibility: external-operation / verification
conditions: async, shared-singleton-resource, evidence-promotion
```

应激活对应外部操作规则，并在 GitHub Actions 条件同时成立时再加载平台专项适配。

### S-06 既有使用方普通恢复与基线升级

普通恢复：

```text
scope: consumer-repository
responsibility: fresh-context-recovery
stage: normal-development
```

明确升级：

```text
scope: consumer-repository
responsibility: baseline-upgrade
stage: explicit-upgrade
```

两者必须得到不同规则集：普通恢复优先使用方本地权威；明确升级才进入精确 `agentic-dev` 基线的选择性采用规则。

## 11. B1 明确不建立的复杂结构

当前证据不足以要求：

- 全库统一 YAML 文件头；
- 全局永久规则 ID；
- 数值优先级系统；
- 图数据库；
- MCP Server；
- 运行时 Controller；
- 自动权限缓存；
- 为每个规则维护完整依赖图；
- 在索引中复制完整规则正文；

- 不要求全库文件头，也不要求任何特定索引技术。
