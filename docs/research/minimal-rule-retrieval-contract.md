# 最小规则检索契约

冻结日期：2026-09-08

阶段：**规则治理与知识激活 v1 / 阶段 B / B1 — 冻结最小检索契约**

文档性质：**研究契约 / B2～C 阶段验证基线**

冻结基线：`master@d5bcd38551a9b6c96f302457bd23d32fec166a2f`

本文把阶段 A 已确认的激活单元、范围敏感关系、重复候选和历史失效类型收敛为一个最小、工具无关的检索契约，供 B2 原型选择、B3 原型验证和阶段 C A/B 评估使用。

本文不是新的规范性规则权威。检索结果只能帮助 Agent 找到当前需要读取和执行的仓库权威，不能替代源文档、改变仓库权威顺序、授予额外权限或把 Research 提升为执行规则。

## 1. 设计目标

B1 只冻结以下语义：

1. 什么最少输入足以辨识当前需要的规则；
2. 检索至少返回什么，才能既可解释又不复制完整规则；
3. 无索引、索引陈旧、结果冲突或无法可靠判断时如何回退；
4. 如何表示重复、范围差异和取代而不制造第二权威；
5. 哪些复杂结构当前没有证据证明必要。

B1 不选择 Markdown、YAML / JSON、脚本、数据库、MCP 或其他具体实现，也不修改现行指南、Skill 或方法。

## 2. 核心原则

### 2.1 使用稀疏查询，不要求每次填写完整元数据

最小查询由两个必需维度和三个条件维度组成：

```text
必需：作用域 + 当前职责
条件：阶段 + 目标对象 + 风险 / 状态条件
```

只有某条规则的适用性确实依赖条件维度时，才要求补充对应信息。未知条件不得为了“完整”而猜测。

### 2.2 作用域必须显式

阶段 A 已确认，多组同义规则只有在保留项目 / 仓库范围后才能正确选择，例如：

- `agentic-dev` 自身默认中文表达，不等于所有使用方项目都必须中文；
- `agentic-dev` 自身的人工 / 集成边界，不等于使用方项目的集成策略；
- 使用方仓库权威优先，不等于普通开发持续跨仓库读取 `agentic-dev`。

因此作用域不是可省略的附加字段，而是最小查询的必需输入。

### 2.3 检索只返回规则入口，不复制第二份权威

检索结果可以包含短语义摘要、匹配理由和必需检查，但必须精确回指当前源权威。任何派生索引中的摘要都不能成为独立长期规则来源。

### 2.4 不用索引内部优先级覆盖仓库权威

B1 不定义独立数值优先级。发生范围、强度或语义冲突时，仍回到当前仓库的 Authority 顺序和源文档判断。

### 2.5 陈旧时失败开放到仓库直接读取

索引不可用或不可信时，正确回退是直接读取当前仓库权威，而不是继续依赖旧摘要或返回“没有规则”。

## 3. 最小输入契约

### 3.1 `scope` — 作用域，必需

回答：**当前任务由哪个项目 / 仓库的权威约束？**

至少需要能区分：

- `agentic-dev` 仓库自身；
- 某个使用方仓库；
- 明确的跨仓库任务。

具体实现不要求固定字符串枚举，但必须能保留当前 Authority 域，不能只记录抽象任务名称。

### 3.2 `responsibility` — 当前职责，必需

回答：**当前 Agent 正在做什么职责？**

典型语义包括但不限于：

- 新上下文恢复；
- 需求澄清 / 规格说明；
- 技术规划；
- 工作切分 / 就绪检查；
- 执行；
- 调试；
- 验证；
- 整体收敛；
- AI / 人工复核；
- 集成决策；
- 外部状态操作。

B1 不冻结一套永久枚举。B2 原型只需对当前已审计规则建立足够稳定的职责词汇。

### 3.3 `stage` — 当前阶段 / 门禁，条件必需

只有当规则取决于生命周期位置时提供，例如：

- 规划候选尚未切分；
- 候选执行单元正在就绪检查；
- 已就绪执行单元进入执行；
- 项目进入集成前复核；
- Existing Consumer 正处于明确基线升级，而不是普通开发恢复。

阶段不能由编号、Roadmap 排序、旧 PASS 或历史状态推断；必须来自当前仓库事实。

### 3.4 `subject` — 目标对象 / 声明，条件必需

只有当规则依赖当前处理对象时提供，例如：

- 项目路线图 / 里程碑状态；
- 规格说明 / 技术计划 / 执行单元；
- PR / Issue / 分支；
- GitHub Actions 完成声明；
- 临时工作流产物；
- 单实例评审环境；
- 外部媒体 / 二进制资源。

`subject` 表达“当前处理什么”，不是把整个文件内容塞进查询。

### 3.5 `conditions` — 风险 / 状态条件，条件必需

只记录已经观察到、会改变规则适用性的事实。典型条件包括：

- 外部状态写入；
- 跨仓库；
- 高影响 / 不可逆操作；
- 异步运行；
- 共享资源 / 单实例资源；
- 临时证据晋升为持久输入；
- GitHub Actions 验证；
- 依赖 PR 拓扑；
- 当前 Head / base / 权威基础发生实质变化；
- 来源或索引可能陈旧。

不得为了触发更多规则而推测不存在的风险条件。

## 4. 输入组合规则

### 4.1 最小正常查询

普通任务至少提供：

```text
scope + responsibility
```

若这两个维度已经唯一确定需要的薄核心 / 任务职责规则，则不继续增加条件。

### 4.2 条件扩展

只有检索结果会因为生命周期、对象或风险事实不同而改变时，按需加入：

```text
+ stage
+ subject
+ conditions[]
```

这意味着 B1 采用**稀疏条件模型**，而不是要求每个规则条目和每次查询都填写相同的大型字段集合。

### 4.3 任务职责变化后重新查询

一个检索查询描述一个当前职责。任务从“执行”切换为“验证”、从“验证”进入“集成复核”或从普通开发进入明确基线升级时，应重新检索，而不是把第一次得到的规则集视为整个会话永久上下文。

## 5. 最小输出契约

每个激活结果至少包含以下信息。

### 5.1 `source_pointer` — 权威指针

必须能够精确回到当前规范性来源：

- 仓库路径；
- 可定位章节 / 段落；
- 用于陈旧检测的来源身份。

来源身份可以是 Git blob SHA、内容摘要或其他等价机制；B1 不规定具体实现，但必须能判断索引条目对应的源内容是否已经变化。

### 5.2 `activation_summary` — 短激活摘要

只回答：

> 当前任务为什么需要这条规则，它约束什么？

摘要必须短于源规则，不复制完整过程，也不能脱离 `source_pointer` 独立成为长期权威。

### 5.3 `applicability` — 适用信息

至少表达：

- 匹配了哪些输入条件；
- 当前作用域；
- 规则强度。

B1 沿用阶段 A 已验证足够有用的三档强度：

- **核心不变量**：跨多数任务成立的薄不变量；
- **条件必需**：触发条件成立时必须遵守；
- **指导默认**：稳定默认，但允许当前项目权威 / 当前证据覆盖。

### 5.4 `required_checks` — 必需检查

只列当前职责为了正确消费规则必须执行的最少检查，例如：

- 重新读取当前 Head / base；
- 确认是否已经完成就绪检查；
- 对账声明 / 风险与实际工作流触发；
- 检查持久证据来源与完整性；
- 确认当前仓库是否明确授权高影响操作。

它不是新的流程定义；详细动作仍回到源权威。

### 5.5 `matched_by` — 匹配解释

记录是哪几个查询维度触发该结果，例如：

```text
scope=consumer
responsibility=readiness-check
stage=upstream-authority-revised
```

该字段用于后续 B3 / C 阶段检查误激活和漏激活。

## 6. 条目角色与最小关系语义

为避免把 A4 观察到的不同重复类型都当成平行规则，B1 区分**条目角色**和**规则关系**。

### 6.1 条目角色

每个索引条目只需要以下四种角色之一：

- **authority**：当前规范性规则来源；
- **pointer**：高层薄摘要 / 激活指针，作用是引导读取详细来源；
- **consumer**：Skill / 专项职责为了独立执行而保留的最小消费守卫；
- **evidence**：Research、历史项目记录、PR / Issue 等证据，不参与当前规则激活。

`evidence` 默认不能作为执行规则返回，只能作为解释或评估证据。

### 6.2 最小关系

B1 只冻结三类跨条目关系：

- **equivalent**：当前语义实质等价或高度重复；检索可以合并展示为一个语义结果并列出多个当前来源，不能据此自动删除任何源规则；
- **scope-variant**：主题相近但作用域、强度或职责不同；必须保留区分，不能为了去重合并；
- **superseded-by**：旧规则被当前权威明确取代；默认检索不返回旧规则，只有历史研究明确需要时才读取。

不得仅凭文件更新时间、提交时间或“看起来更完整”推断 `superseded-by`。

### 6.3 不冻结永久 canonical owner

A4 已提出若干未来减法候选，但阶段 D 尚未授权重新分配详细规则的长期所有者。因此 B1 不为这些候选提前指定永久 canonical source。

对当前多个活跃来源的实质重复，B2 可以：

1. 把它们折叠成一个语义结果；
2. 保留所有当前源指针；
3. 只加载当前职责真正需要的详细来源；
4. 若不同来源出现实质不一致，立即回退源权威直接读取并按 Authority 解决。

## 7. 陈旧检测与回退契约

### 7.1 必须回退的情况

出现以下任一情况，不得继续把派生索引摘要当作当前规则：

1. 索引不存在或不可用；
2. 选中条目的来源身份与当前源文件不一致；
3. `source_pointer` 无法解析；
4. 同一查询得到范围 / 强度相冲突且无法按当前 Authority 唯一解析的结果；
5. 当前任务属于高影响职责，但索引没有返回预期的规范性权威入口；
6. 检索结果涉及授权、合并、发布、部署或其他高影响状态，而索引无法证明当前仓库授权状态；
7. 查询遇到索引未建模的新条件或新规则结构。

### 7.2 回退动作

回退顺序：

```text
当前仓库 Authority
→ 当前职责直接相关的规范性源文档
→ 必要时读取相邻职责 / 平台专项权威
→ 重新判断当前规则集
```

使用方场景必须先读使用方仓库权威；只有明确基线升级或使用方本地规则无法回答必要方法问题时，才按当前使用指南进入 `agentic-dev` 上游规则。

### 7.3 局部陈旧，不默认使整个索引失效

如果只有某个源文件身份变化，只把受影响条目标为陈旧并直接读取该源。B2 不需要为了单文件变化每次重建整个索引，除非所选实现无法可靠判断影响范围。

### 7.4 检索结果不授予权限

即使结果正确命中“可以执行某类操作”的通用规则，当前仓库权限、人工授权和实时外部状态仍必须重新读取。派生索引永远不能成为权限缓存。

## 8. 对文件头 / Front Matter 的 B1 判断

**B1 不要求给项目库文档统一增加文件头。**

原因：

1. 当前最小契约所需的路径、章节、作用域、职责、强度和来源身份，可以由独立派生索引描述；
2. Git blob SHA / 内容摘要已经能够提供来源陈旧检测能力；
3. 阶段 A 没有证据证明“缺少文件头”是规则未激活的主要根因；
4. 全库文件头会把 B1 的工具无关契约提前绑定到一种元数据载体，并增加所有文档的维护面。

B2 如果证明某些高影响规则载体缺少稳定段落身份，允许比较“外部派生索引”与“少量规则载体增加最小元数据”的成本；即使后续需要元数据，也应只作用于真正的规则载体 / 激活单元，不默认覆盖 Research、历史项目记录和普通项目文档。

## 9. 用阶段 A 场景验证输入辨识力

以下只验证 B1 字段是否足以表达差异，不是阶段 C 行为评分。

### S-01 项目路线图集成后状态闭环

```text
scope: agentic-dev
responsibility: AI review / integration review
stage: integration-preparation
subject: project roadmap / milestone state
conditions: project-state-change
```

应命中项目路线图 / 集成后稳定状态相关规则，不需要加载完整外部操作指南。

### S-02 规划候选身份

```text
scope: consumer repository
responsibility: slice-work / readiness-check
stage: planning-candidate or candidate-execution-unit
subject: pre-numbered future work
```

应命中候选身份 / 就绪授权边界，不能因为编号存在而激活执行授权。

### S-04 GitHub Actions 触发拓扑

```text
scope: current repository
responsibility: verification
subject: completion evidence claim
conditions: github-actions
```

应命中通用证据边界与 GitHub Actions 专项触发拓扑规则，而不激活共享资源 / 证据晋升等无关条件规则。

### S-05 异步共享资源与证据晋升

```text
scope: current repository
responsibility: external operation / verification
conditions: async, shared-singleton-resource, evidence-promotion
```

应激活对应外部操作规则，并在 GitHub Actions 条件同时成立时再加载平台专项适配。

### S-06 Existing Consumer 普通恢复与基线升级

普通恢复：

```text
scope: consumer repository
responsibility: fresh-context recovery
stage: normal-development
```

明确升级：

```text
scope: consumer repository
responsibility: baseline-upgrade
stage: explicit-upgrade
```

两者必须得到不同规则集：普通恢复优先 Consumer-local Authority；明确升级才进入精确 `agentic-dev` baseline 的选择性采用规则。

## 10. B1 明确不建立的复杂结构

当前证据不足以要求：

- 全库统一 YAML Front Matter；
- 全局永久规则 ID；
- 数值优先级系统；
- 图数据库；
- MCP Server；
- 运行时 Controller；
- 自动权限缓存；
- 为每个规则维护完整依赖图；
- 在索引中复制完整规则正文；
- 把 Research / PR / Issue 统一转为当前规则节点。

如果 B2 / B3 无法用更小结构满足本契约，再基于具体失败证据增加最小字段或关系。

## 11. B1 完成结论

阶段 A 的材料已经足以冻结一个最小检索契约：

```text
Query
= scope
+ responsibility
+ [stage]
+ [subject]
+ [conditions]

Result
= source_pointer
+ activation_summary
+ applicability
+ required_checks
+ matched_by
```

其中：

- `scope` 与 `responsibility` 必需；
- 其他输入按规则适用性稀疏提供；
- 结果必须可回指当前规范性源并携带来源身份；
- 条目角色只区分 authority / pointer / consumer / evidence；
- 跨条目关系只冻结 equivalent / scope-variant / superseded-by；
- 任何陈旧、无法解析、范围冲突或高影响授权不确定都回退当前仓库直接读取；
- 不要求全库文件头，也不要求任何特定索引技术。

因此 B1 已满足协调计划的五项完成条件。下一工作项应进入：

> **B2 — 原型选择**

B2 应以“能否用最小实现完整满足本契约”为唯一选择标准，不因为某种载体更现代或更结构化而优先采用。
