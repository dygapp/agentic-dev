# 技术画像最小契约

**状态：** 基线 v0.1  
**性质：** 技术画像（`Technology Profile`）/ 验证画像（`Verification Profile`）规范性契约

## 1. 目的

本文定义 `agentic-dev` 中技术画像及其验证画像的最小长期契约。

目标不是建立统一的框架百科模板，而是回答：

> **一项特定技术工程知识在什么条件下可以成为可复用技术画像，以及后续 Agent 如何可靠判断它适用于什么、默认应怎么做、哪些做法应避免、如何验证，并在使用方仓库中如何被选择、限制、补充或覆盖。**

本文受 `AGENTS.md`、核心方法、工程能力架构和当前工程纪律权威约束，不创建新的方法阶段，也不要求技术画像自动形成任务型技能。

## 2. 技术画像的职责边界

技术画像描述特定技术体系下会稳定影响工程判断的：

- 当前有效技术语义与官方支持边界；
- 默认工程规则和成熟实践；
- 常见误用与高风险错误模式；
- 框架 / 标准库 / 现有生态能力的优先复用边界；
- 何时允许或需要项目自有实现；
- 与当前技术变更类型匹配的验证画像；
- 使用方本地权威的选择、限制、补充和覆盖边界。

技术画像不负责：

- 复制官方文档的完整 API / 教程内容；
- 保存某个使用方的项目目录、业务事实、精确依赖版本或本地命令；
- 规定所有项目必须采用相同架构、代码风格或测试框架；
- 替代规格说明、技术计划、架构 / ADR 或执行单元；
- 自动执行完整开发任务；
- 因技术名称存在就建立对应技能。

只有会改变工程决策、实现边界、误用判断或验证责任的技术知识，才应进入长期技术画像。

## 3. 技术画像最小结构

一个拟进入仓库权威的技术画像至少必须能够回答以下八类问题。载体可以是一个文件或一组具有单一当前入口的文件，不要求固定 YAML / JSON schema。

### 3.1 身份与适用范围

至少明确：

- 技术画像的名称 / 稳定标识；
- 覆盖的技术或技术组合；
- 研究与验证所针对的主要版本 / 版本范围；
- 适用运行条件、工程假设或已知不适用范围；
- 当前技术画像基线 / 修订版本。

版本范围不能只写“最新版本”。快速演进技术应保留可追溯的研究版本或发布日期锚点。

### 3.2 证据基线

技术画像的规范性结论必须可以回溯到满足工程能力架构证据门槛的来源。

至少保留：

- **来源**：官方文档、规范、仓库、成熟开源项目、专家原始材料或使用方 / 评估证据；
- **基线**：版本、Commit、发布日期或其他可识别锚点；
- **证据类型**：官方语义 / 官方推荐 / 成熟工程实践 / 专家经验 / 评估 / 使用方观察；
- **适用范围**：证据实际支持的技术版本和场景；
- **时效性**：研究时的有效性检查；
- **冲突**：重大来源冲突及当前裁决或待处理状态。

技术画像不要求在正文每句话后重复完整引用，但任何会影响工程行为的规则必须有可追溯证据链。

### 3.3 官方语义与支持边界

记录会影响正确实现的官方语义和支持边界，例如：

- 生命周期；
- API / 类型系统语义；
- 官方支持 / 不支持的组合；
- 已弃用或替代路径；
- 与兼容性、运行时或构建相关的关键限制。

这一部分只保留工程判断真正需要的语义，不复制官方参考手册。

如果成熟开源实践或专家建议与当前官方语义冲突，不能静默用“最佳实践”覆盖官方事实。

### 3.4 工程默认规则

记录在适用条件成立、且使用方没有更具体权威时，Agent 应优先采用的默认工程做法。

每项默认规则至少应能够判断：

- **为什么现在适用**；
- **解决什么当前工程责任**；
- **何时不再适用或需要重新评估**。

默认规则不得只是“通常大家这么写”。应优先选择能够减少错误、降低不必要复杂度、正确利用技术能力并提升可验证性的稳定实践。

### 3.5 常见误用与避免事项

记录具有辨识价值的常见误用，包括：

- 对官方语义的误解；
- 重复实现框架已经可靠提供的能力；
- 为假想未来过度抽象；
- 技术上可运行但违反生命周期 / 类型 / 状态管理 / 资源管理等稳定边界的做法；
- 容易导致验证盲区的实现方式。

该部分必须说明“为什么有问题”和适用条件，不建立无上下文的禁止清单。

### 3.6 能力复用与扩展边界

技术画像必须说明：

- 当前技术体系已经提供哪些应优先检查和复用的能力类别；
- 何时薄适配比重新实现更合适；
- 何时现有能力因功能、安全、性能、可观察性、生命周期或其他当前契约不匹配，可以基于证据采用项目自有实现；
- 不为了复用扩大依赖面、改变产品行为或覆盖使用方架构权威。

该部分具体化工程纪律中的“已有能力复用 / 实现最小化”，但不能放宽其通用边界。

### 3.7 使用方覆盖边界

技术画像是可复用默认基线，不是使用方的最终项目事实。

使用方仓库可以：

- 显式选择适用技术画像 / 基线；
- 固化自己的精确技术版本、项目架构、目录规则和依赖约束；
- 为项目特有原因限制、补充或覆盖工程默认规则；
- 指定真实 Build / Test / Lint / Browser / CI / 人工复核命令与证据载体；
- 禁用与当前项目不匹配的可选指导。

但使用方本地规则不能通过普通项目偏好改写客观的技术语义。如果项目有意使用官方不推荐、已弃用、实验性或兼容性受限路径，应由使用方权威明确记录这一事实、适用理由和风险，而不是让技术画像静默变成错误。

当技术画像与使用方发生冲突时，至少区分：

1. 合理项目特化；
2. 使用方使用的技术画像 / 技术基线已陈旧；
3. `agentic-dev` 技术画像本身存在通用缺口。

### 3.8 生命周期

每个技术画像必须明确或可从当前仓库权威中确定：

- 产生者；
- 触发条件；
- 消费者；
- 持久化；
- 更新；
- 取代；
- 升级。

技术画像的当前入口只能有一个。旧版本可以保留用于历史追溯，但必须明确取代 / 替换关系，避免多个技术画像同时被解释为当前规范。

## 4. 规则强度与表达

为了避免把所有工程建议写成绝对规则，技术画像的规范性内容至少应在语义上区分以下类型；不强制使用固定字段名。

### 4.1 技术约束（`Technology Constraint`）

来自当前技术语义、支持边界或明确兼容性约束。违反它通常意味着实现错误、未支持组合或已知高风险行为。

使用方如果必须偏离，应显式记录版本、实验性能力或风险依据，不能把普通偏好当作覆盖事实。

### 4.2 工程默认规则（`Engineering Default`）

在通常适用条件下优先采用的成熟工程做法。

使用方可以因更具体项目事实覆盖，但应有可说明的当前原因，而不是机械复制或机械拒绝技术画像。

### 4.3 条件性指导（`Conditional Guidance`）

只在特定变更类型、规模、风险或运行条件成立时适用。技术画像必须写明触发条件。

### 4.4 已知误用 / 避免（`Known Misuse / Avoid`）

用于识别常见错误或高风险模式。必须同时说明违反了什么语义 / 工程责任，以及合法例外的判断边界（如存在）。

## 5. 技术画像的组合与拆分

技术画像不要求“一项技术一个文件”，也不允许为了便利形成大而全的技术栈画像。

允许组合多个技术的条件是：

- 它们在真实工程任务中形成稳定且高频的联合决策边界；
- 大量关键规则、误用或验证责任只有结合后才有意义；
- 拆分会产生重复、冲突或使 Agent 无法可靠应用规则；
- 每个组成技术仍保留独立的版本 / 适用范围和证据锚点。

工程能力基础 v1 已冻结唯一代表性技术画像目标名称为：

> **Vue 3 + TypeScript 技术画像**

这一名称只定义当前里程碑的研究对象，不预先证明 Vue 3 与 TypeScript 的哪些具体规则必须合并。WI-05 必须通过当时当前的官方资料、成熟实践和专项评估判断联合规则的真实边界；如果部分知识可以独立表达，应在同一代表性技术画像内保持清晰分区、独立版本 / 适用范围和证据锚点，而不是为了“组合”制造不存在的共同规则。

Element Plus 不因为常与 Vue 一起使用就自动进入同一技术画像；只有未来独立研究证明其与当前技术画像职责存在不可合理分离的稳定工程边界，并且新的项目里程碑允许扩大范围时才可调整。工程能力基础 v1 内继续保持 v1 后候选。

当一个组合技术画像逐渐包含多个可独立演进的框架、工具和大量无关规则时，应评估拆分，而不是继续扩充一个“前端大全”。

## 6. 验证画像最小契约

验证画像是技术画像的必要组成部分或受其引用的独立能力，用于把技术变更映射到合理的验证责任。

它不固定项目命令，也不替代执行单元已经分配的验收义务。

### 6.1 变更类型

识别当前技术体系下会显著影响验证路径的变更类型，例如：

- 类型 / 编译期变化；
- 组件或模块行为变化；
- 生命周期 / 状态变化；
- 公共 API / 契约变化；
- 构建 / 打包变化；
- 浏览器 / 运行时行为；
- 样式 / 视觉变化；
- 性能、安全或兼容性敏感变化。

验证画像不要求穷举所有变更，只保留会改变验证责任的稳定分类。

### 6.2 验证层级

针对变更类型，说明通常需要考虑哪些验证层级，例如：

- type check / compile；
- unit / component test；
- integration / contract test；
- build；
- runtime / browser behavior；
- visual evidence；
- performance / security / compatibility evidence。

这些是验证层级，不是固定命令清单；具体命令名称保持真实工具原样。

### 6.3 证据责任

每个验证画像应能够帮助 Agent 判断：

```text
当前验收义务
→ 技术变更类型
→ 应由哪个验证层证明什么
→ 使用方当前可用机制
→ 已执行的当前证据
```

验证画像不能只因为“type check + build 都通过”就宣称业务验收义务已闭环。

### 6.4 风险升级

明确什么情况需要扩大验证，例如：

- 公共契约变化；
- 生命周期或并发变化；
- 多入口 / 多状态行为；
- 用户可见视觉变化；
- 安全 / 隐私 / 性能敏感路径；
- 框架升级或跨版本兼容性。

扩大验证必须与当前风险和责任相关，不为了完整性机械运行所有层级。

### 6.5 使用方解析

具体命令、测试框架、fixture、浏览器工具、CI 工作流和人工复核证据必须从使用方仓库权威、当前依赖和实际仓库状态解析。

如果技术画像建议某验证层，但使用方当前没有对应机制：

- 不编造命令或工具；
- 判断该层是否是当前完成状态的必要证据；
- 必要时建立最小验证能力、返回上游规划职责或保持未完成；
- 不通过降低验收义务来制造“通过”。

## 7. 研究 → 技术画像准入门槛

研究中的内容只有满足以下条件才进入技术画像：

- 对当前技术版本仍有效；
- 有足够权威或多来源成熟证据；
- 会实际改变工程选择、误用识别或验证责任；
- 适用范围可以说明；
- 与当前仓库权威不冲突；
- 能够形成有辨识力的专项评估或复核启发式。

以下内容默认继续留在研究，不进入技术画像：

- API / 配置项罗列；
- 教程式步骤；
- 单个项目的目录或代码风格；
- 单一低权威个人偏好；
- 缺少版本锚点的旧经验；
- 尚未解决的重大来源冲突；
- 只因为“可能以后有用”的知识。

## 8. 技术画像与工程纪律 / 技能的关系

技术画像必须服从当前工程纪律，并把通用原则具体化到技术上下文。

例如：

- 工程纪律要求避免推测性抽象；技术画像可以说明该技术中常见的无必要扩展点或错误抽象方式；
- 工程纪律要求精准修改；技术画像可以说明某技术变更会确定性地产生哪些必要伴随文件或验证责任。

技术画像不得复制一套新的通用工程纪律来与 `docs/architecture/engineering-disciplines.md` 竞争权威。

技术画像也不自动产生技能。只有后续出现具有独立使用条件、输入、过程、输出、退出和升级边界的稳定任务过程，才按技能架构另行评估。

## 9. 专项评估要求

技术画像在正式集成前必须具有针对其实际规范性声称的专项评估。

至少应验证：

- 能否识别适用 / 不适用范围；
- 能否区分技术约束、工程默认规则与条件性指导；
- 能否优先检查并复用技术体系已有能力，而不是重复实现；
- 能否识别典型误用而不过度禁止合法方案；
- 能否在使用方权威更具体时正确服从或升级；
- 能否根据技术变更类型选择合理验证层，而不是使用固定命令或主路径证据冒充完成；
- 能否保持实现最小化与精准修改等当前工程纪律。

专项评估应围绕技术画像的真实决策价值设计，不为了覆盖官方文档知识点建立百科问答测试。

## 10. 技术画像实例的最小完成条件

一个技术画像只有同时满足以下条件，才可以进入最终 AI 复核 / 已具备进入集成决策的条件：

- 身份 / 版本 / 适用范围明确；
- 证据基线可追溯且检查过时效性；
- 官方语义 / 支持边界已收敛到真正影响工程判断的内容；
- 工程默认规则有适用条件和理由；
- 常见误用有辨识价值并保留合法边界；
- 能力复用 / 项目自有实现边界明确；
- 使用方覆盖边界明确；
- 验证画像能把主要技术变更类型映射到验证层与证据责任；
- 研究内容已经过准入筛选，没有变成框架百科；
- 专项评估有有效当前通过证据；
- AI 复核不存在未解决阻塞 / 中等级问题；
- 未因技术画像的存在机械新增技能。

## 11. 生命周期

- **产生者：** 当前 `agentic-dev` 仓库权威授权的技术画像 / 工程能力维护职责；
- **触发条件：** 工程能力基础路线、成熟外部技术实践、专项评估、使用方采用或技术版本变化产生稳定技术画像需求；
- **消费者：** 使用方 Agent、`execute-unit`、后续任务型技能、验证能力与运行时适配器；
- **持久化：** 进入与技术画像层次匹配的当前仓库权威，并保持单一可发现入口；
- **更新：** 官方版本 / 支持边界变化、外部依据失效、评估失败、使用方回归或上游方法 / 纪律 / 架构变化时重新检查；
- **取代：** 新基线必须明确取代关系、适用版本范围和当前入口，旧内容只作为历史证据保留；
- **升级：** 如果技术画像需要改变核心方法、重大架构 / 契约、人工 / 集成边界，覆盖使用方权威，或外部权威冲突无法裁决，返回相应更高层处理。

## 12. 工程能力基础 v1 的应用边界

工程能力基础 v1 使用本契约只完成一个代表性实例：

> **Vue 3 + TypeScript 技术画像**

WI-04 只建立本文契约，不在本阶段研究 Vue / TypeScript 具体规则。

本文集成后进入 WI-05；WI-05 必须按本契约完整走通：

```text
研究
→ 候选技术画像
→ 架构适配
→ 技术画像草案
→ 验证画像
→ 专项评估
→ AI 复核
→ 集成决策
```

工程能力基础 v1 不因为本契约已经存在就自动启动 Element Plus、Spring、Gradle 或其他技术画像；这些继续保持 v1 后候选库。
