# 人工评审架构

## 1. 适用范围

本架构定义普通 Consumer 软件项目中，需求、功能规格、架构与技术方案如何转换为便于人工理解和判断的评审材料，以及人工反馈如何返回真实语义所有者。

它不用于规范 `agentic-dev` 自身的方法论研究、项目演进、Issue / PR 决策或能力设计过程。`agentic-dev` 只是该可复用能力的定义与承载仓库。

本架构不拥有具体产品事实、需求事实、架构事实或技术事实，也不建立新的通用 Method 阶段。

## 2. 核心责任

人工评审能力只拥有以下长期契约：

1. 何时把当前内容整理为人工评审材料；
2. 结构化 Markdown 评审草稿与真实权威内容之间的所有权边界；
3. 临时流程图、状态图、关系图、思维导图、矩阵等派生视图的生命周期；
4. 人工反馈的分类与回写规则；
5. 评审完成条件；
6. 最终交付格式必须显式请求的边界。

是否需要评审，由当前拥有责任的 Method、Skill、Repository Authority 或人工请求决定。人工评审能力不自行扩大项目范围，也不自行创造新的产品或架构决策。

## 3. 调用状态

人工评审按当前责任分为三种状态：

- **必须评审**：不经人工决定就不能安全确定真实产品意图、长期高影响结构或高风险技术责任；
- **建议评审**：AI 已能形成完整候选，但集中人工审阅能显著降低误解、遗漏或返工风险；
- **无需评审**：事项局部、低风险、可逆，且现有权威内容已经可以唯一决定结果。

人工明确要求评审本身构成有效调用理由，但不自动把评审结果提升为长期 Authority。

## 4. 默认工作介质

没有显式交付格式要求时，默认产物是 **结构化 Markdown 评审草稿**。

评审草稿是临时、非权威产物。其结构按评审对象适配，不要求固定模板，但应只选择当前判断真正需要的内容，例如：

- 评审目标与范围；
- 当前已确认事实；
- 当前方案或可观察行为；
- 关键角色与责任；
- 主要流程或生命周期；
- 关键规则与状态；
- 边界与失败行为；
- 验收或判断依据；
- 相对已确认基线的变化；
- 待确认事项；
- 已发现缺口或冲突；
- 确有价值时建议生成的辅助视图。

不得为了模板完整而生成没有实际语义的章节。

默认交付状态为：

```text
delivery_target = none
```

没有明确最终交付要求时，内容完成评审并正确回写真实所有者后即停止。

## 5. 不建立持久业务建模中间层

人工评审不得默认形成：

```text
需求
→ 持久业务模型
→ BPMN / UML 等模型
→ 人工评审视图
```

统一采用：

```text
当前真实语义所有者
→ 结构化 Markdown 评审草稿
→ 按需临时派生视图
→ 人工评审
→ 将确认语义回写真正所有者
```

流程图、泳道图、状态图、思维导图、关系图、矩阵、架构图、时序图以及临时 BPMN 表达都只是可再生投影：

- 只有明显提升人工理解或判断效率时才生成；
- 默认不拥有新事实；
- 默认不要求与 Authority 双向同步；
- 删除后不影响 Current Authority 恢复；
- 视图中暴露的新语义缺口必须返回真实 owner。

只有 Consumer 的合同、法规或其他外部权威明确要求某种模型本身成为正式交付依据时，目标 Repository 才可以单独建立该模型的长期责任。

## 6. 跨模块与全生命周期流程

当需要理解跨模块、多角色、长生命周期业务时，先从当前 Requirement owners 组合形成结构化 Markdown 流程描述。

如果触发条件、责任交接、状态衔接、失败处理和完成条件都可以由现有权威内容唯一恢复，该流程只是一种评审投影。

如果组合过程中发现现有 Requirement Authority 无法回答的真实业务问题，则记录为需求缺口并进入正确的 Requirement responsibility。人工确认后的长期事实必须回写能够真实承担该事实的现有 owner；只有事实确实跨多个能力持续成立、具有独立业务或验收意义、且不能合理归属于单一 owner 时，才评估进入 Consumer 已有的横向 Requirement owner。

不得因为需要端到端理解就建立新的持久业务模型层。

## 7. 人工反馈分类

人工反馈至少分为四类：

1. **展示反馈**：排版、措辞、顺序、图形布局、展开方式等，只修改评审投影；
2. **语义修正**：明确改变现有权威事实，必须回写原真实 owner；
3. **新增长期决定**：确认了此前不存在、且会长期约束后续工作的事实，必须提升到适当 Requirement、Specification、Architecture 或 Technical owner；
4. **未决问题**：人工仍无法或不准备决定，保持 unresolved，不得伪装成已确认事实。

一条反馈同时包含展示与语义变化时必须拆分处理。

## 8. 回写与重新生成

评审草稿、图形和最终交付文件都不是默认事实修订入口。任何会影响后续开发、验收、架构或技术约束的人工决定，在评审完成前都必须进入真实语义所有者。

标准闭环：

```text
人工反馈
→ 分类
→ 更新真实 owner
→ 重新读取并确认真实 owner 已持久化该决定
→ 重新生成受影响评审草稿 / 临时视图
→ 核对投影与 Current Authority 一致
```

禁止：

- 只修改评审草稿而不修改 Authority；
- 让 DOCX / HTML 成为事实修订入口却不回写；
- 在下游 Specification / Technical Plan 中静默覆盖上游 Requirement；
- 让人工口头确认长期停留在聊天记录中。

如果人工已经作出长期语义决定，但当前执行者没有目标 Repository 写入授权：

- 必须输出明确的待执行权威回写动作；
- 当前执行可以因为权限边界而返回，但评审状态必须标记为 **待权威回写 / 未完成**；
- 不得把“已经列出待执行回写动作”解释为“评审完成”或“语义已收敛”；
- 不得基于尚未进入真实 owner 的决定生成正式已确认交付物；
- 后续具备授权的执行者完成回写后，必须重新读取真实 owner，确认该决定已经实际持久化，再重新生成或校准评审草稿。

“人工已经决定”与“长期语义已经进入 Current Authority”是两个不同状态，后者才允许人工评审进入完成状态。

## 9. 完成条件

一次人工评审只有同时满足以下条件才算完成：

1. 当前评审范围明确；
2. 需要人工判断的高价值问题已经处理，或明确保持 unresolved；
3. 所有已经确认的长期语义变化都已实际回写真正 owner；
4. 已重新读取对应 Current Authority，并确认回写内容真实存在且没有被其他当前事实覆盖或冲突；
5. 评审草稿已根据重新读取后的 Current Authority 重新生成或校准；
6. 不存在只保存在草稿、图形、会话或“待执行回写动作”中的 durable fact；
7. 评审草稿与派生视图不会成为第二套 Current Authority；
8. 如果没有明确最终交付要求，则到此停止。

如果存在已经确认但尚未完成或尚未验证的权威回写，当前执行可以返回，但人工评审必须保持 **待权威回写 / 未完成**，不能满足本节完成条件。

人工评审完成不授予 merge、release、deploy 或其他外部操作权限。

## 10. 显式交付投影

最终交付只在调用方或人工明确指定格式时进入。没有显式请求时，`delivery_target = none`，不得为了“材料完整”自动生成 DOCX、HTML 或其他文件。

结构化 Markdown 评审草稿是最终交付前的默认内容确认介质。交付投影只能改变信息组织、导航、样式和展示方式，不得重新解释业务、架构或技术语义。

### 10.1 内容状态

最终交付前先判断内容状态：

- **评审中**：仍存在待确认语义时，可以显式生成 HTML 交互评审视图；必须清楚展示待确认项、缺口与草稿身份；
- **待权威回写**：人工已经确认长期语义，但真实 owner 尚未完成并验证回写；可以继续保留或生成明确标识为草稿的评审材料，但不得声明已收敛，也不得生成正式已确认交付物；
- **已收敛**：长期语义已经实际回写真正 owner，重新读取确认无误，评审草稿已重新校准，可以生成正式交付物；
- **显式草案交付**：如果人工明确要求在语义尚未完全收敛时输出 DOCX 等文件，必须标明“草案 / 待确认”，不得伪装成正式已确认文档。

正式 DOCX 默认以已收敛内容为输入。

### 10.2 HTML 交互评审视图

`delivery_target = html` 时，默认生成静态、轻量、无需后端服务的人工评审视图。可以根据内容规模采用单页或多页，但不得为了交互效果重新实现一套业务系统。

HTML 可以按需提供：

- 清晰的目录和章节导航；
- 展开 / 收起；
- 按角色、状态或“待确认事项”等有限筛选；
- 流程图、状态图、思维导图、架构图等派生视图；
- 差异、决策项、风险与验收信息的突出展示；
- 轻量语义原型，用于说明能力、状态和操作关系。

HTML 必须保持以下边界：

- 以确认后的 Markdown / Current Authority 为内容来源；
- 交互状态不产生新的业务事实；
- 页面中的人工修改意见如果改变语义，仍需回写真实 owner；
- 原型默认只是解释性投影，不自动成为 UI / Visual Design Authority；
- 优先使用可离线查看、容易归档和重新生成的静态实现；
- 不因为 HTML 支持脚本就引入不必要的后台服务、账号体系或持久数据层。

### 10.3 DOCX 正式文档

`delivery_target = docx` 时，先确定适用的文档模板与格式来源，优先级为：

1. 客户、合同、法规明确提供的正式模板或格式要求；
2. Consumer Repository 已确认的本地文档规范；
3. 无上述要求时，使用通用的中文正式办公文档默认配置。

通用默认配置只解决可移植性和正式性，不把某个历史项目的完整模板推广为所有 Consumer 的强制样式。至少遵守：

- 页面默认使用 A4；超宽表格或大型图形可通过独立分节使用横向页面；
- 通过 Word 样式统一控制文档标题、标题层级、正文、列表、表格、图题 / 表题、页眉页脚，避免逐段直接格式化；
- 中文与英文 / 阿拉伯数字字体显式分设，不依赖主题字体或自动字体回退；
- 中文正式文档无其他模板时，标题可使用黑体、正文可使用宋体，英文与阿拉伯数字使用 `Times New Roman`；
- 自动生成 OOXML 时，应显式设置适用样式和关键文本的 `eastAsia`、`ascii`、`hAnsi`、`cs` 字体属性，避免 WPS / Word 中英文和数字出现异常字体；
- 正文和普通表格以黑色文字为默认，不使用手写体、艺术字、自动斜体或装饰性字体；
- 表格应保持稳定列宽、合理内边距、明确对齐规则，跨页时能够重复表头并避免不合理拆行；
- 图形优先使用可编辑矢量图或足够清晰的位图，术语必须与正文一致；
- 目录、页码、图表编号等自动字段在正式交付前更新；
- 不把聊天记录、内部推理、未清理批注、修订痕迹、占位符或内部状态说明带入正式交付文档。

### 10.4 DOCX 兼容性与交付验证

“文件生成成功”不等于 DOCX 交付完成。正式交付至少验证：

- 内容与已确认 Markdown / Current Authority 没有语义丢失或擅自改写；
- 中文、英文、数字和技术名词字体显示正确；
- 标题层级、目录、分页、页码、表格、图形和题注没有明显错位；
- WPS / Word 等目标办公环境中不存在异常字体回退、手写体、意外斜体、文字裁切或错误分页；
- 如果同时导出 PDF，PDF 与 DOCX 的核心版式和内容保持一致。

运行环境无法实际生成或验证目标文件时，必须明确报告能力缺口并保留已确认 Markdown 输入，不得用“已生成”或“已验证”代替真实文件和真实验证。

### 10.5 其他格式

`pdf`、`xlsx`、`pptx` 等保留为后续扩展：

- PDF 适合固定版式、签章和归档；
- XLSX 适合需求、权限、验收、差异、决策等高密度结构化矩阵；
- PPTX 适合会议、Workshop 和专题评审。

v1 不要求为了形式完整一次性实现这些格式，也不为每种文件格式建立独立 Skill。

## 11. 与独立变更复核的边界

人工评审与 `skill:review-change` 不是同一责任：

- 人工评审帮助产品、业务、架构或工程人员理解并确认 Consumer 软件项目内容；
- `skill:review-change` 独立检查仓库变更是否符合当前 Authority、范围、规则、证据与生命周期。

人工评审通过不能替代独立变更复核；独立变更复核也不能替代客户、产品或架构人工确认。

## 12. 生命周期

### 12.1 产生者与触发

评审草稿可以由已采用 `skill:human-review` 的 Agent、拥有当前责任的 Method / Skill 或目标 Repository 授权的人工过程产生。

典型触发包括必须评审、建议评审以及人工明确请求。

### 12.2 消费者

主要消费者是目标项目的产品、业务、架构、工程与客户评审人员，以及需要根据人工决定更新真实 Authority 的后续 Agent。

### 12.3 持久化与退出

评审草稿和临时视图默认 transitional / disposable。只有目标 Repository 明确需要跨上下文继续评审、审计、签署或交付时才持久化；即使持久化，也不因此获得产品或架构事实所有权。

真实语义 owner 更新后，必须重新读取并确认回写已经进入 Current Authority，旧草稿再据此重新生成、更新或退出当前评审范围。可从 Current Authority 唯一再生的派生视图不需要长期同步维护。

如果当前执行因缺少写入授权而返回，允许持久化“待权威回写”状态与所需动作以便后续恢复，但该状态不是人工评审完成状态，也不能成为正式 Current Authority 的替代品。

### 12.4 升级边界

以下情况返回正确 Authority，而不是由人工评审能力自行决定：

- Product / Requirement ambiguity 或 conflict；
- 高影响、高成本难逆架构选择超出当前授权；
- 安全、隐私、生产或不可逆数据风险；
- owner 冲突或长期事实归属无法唯一确定；
- 外部合同或法规要求特殊正式模型 / 交付物成为权威依据。

## 13. Consumer 采用边界

Consumer 可以根据自己的语言、文档体系和组织流程调整评审草稿的物理路径、章节和最终交付格式，但必须保持：

- 真实事实仍由原语义所有者持有；
- 默认使用结构化 Markdown 作为低成本评审工作介质；
- 派生视图不成为平行事实源；
- 语义反馈必须回写；
- 已确认长期语义只有在实际回写并重新读取验证后，人工评审才算完成；
- 最终交付格式必须显式请求；
- 普通低风险工作不会因为采用本能力而增加固定人工审批。
