# 演进事项 7 — 长期知识健康治理与公共能力架构演进

## 1. 任务身份与当前状态

本文件是 Issue #191 对应演进事项的目标、方案边界、关键取舍及验收计划，不是已发布的 Consumer Skill 契约。按[单项演进协议](post-v0.1.0-consumer-feedback-evolution-plan.md#3-单项执行协议)执行。范围 A 采用按需治理导航、Consumer 自有维护约定和现有 Skills，新增 Skill 不准入；正式版本发布及 Consumer 升级仍待后续阶段。

稳定产品基线为 `agentic-dev-v0.3.0`，其 release commit 为 `477a5a8230878e4431d2618c57f6a630a334b55a`；本计划起草前核验的 Provider master 为 `97e845f6ab327b46362b89789f5955ae87fa4e46`。这些是历史定位，不代替执行时重新核验当前仓库及精确基线。已发布模型的 15 个 Skill、单一语义 owner、开放 Consumer-owned Current Authority、长期设计生命周期及最小产品边界继续成立。新方案只面向普通软件 Consumer，不向 Provider 自身套用 Consumer 需求、公共业务能力或文档治理流程。

本事项完成后，长期生效的执行语义、设计理由及导航必须迁入真实版本化 Skill / Architecture / Guide owner；本文件结束活动计划职责，保留为有明确历史角色的阶段计划或按文档 Authority 退役。Issue / PR 只承担协调、原始证据与复核记录。

## 2. 问题与证据边界

### 2.1 三类关联问题

1. **存量长期知识退化。** AI 从少量概念开始，在多轮讨论、开发和实现反馈中逐步生成需求、设计与契约；局部正确不保证项目整体健康。缺少统一维护责任时，出现结构碎片化、重复/过时/冲突权威、代码与设计漂移、历史研究混入正文、导航与再生性缺口。人工反复发出评审/整理命令仍可能因记忆和提示词遗漏导致漏查。
2. **知识细化失衡。** 同级业务概念可能因讨论深度不同，一侧形成大量需求、设计及甚至不必要的机制，另一侧由 AI 推演并实现却没有充分沉淀关键长期知识。知识组织应反映业务责任、成熟度、复杂度、安全风险与消费者需要，而不是会话关注程度、字数或目录对称性。合理差异必须允许，过度细化和细化不足均需检查。
3. **公共能力设计与持续架构演进不足。** 以 Feature 为中心的开发容易忽略主动发现横切技术机制、共享业务语义及其独立契约。演进中缺少提炼、抽象和隔离，可表现为同一规则散布、跨模块反复修改、混合测试环境和重复全量回归、局部任务持续扩大、补丁循环。不能将所有 AI 开发或所有失败归因于此，也不能靠文档重排解决结构性根因。

### 2.2 来源与强度

- Issue #191 的真实四仓文档整理反馈（E01–E21）提供问题、试验性本地 Skill 与治理规范。初始 24 份架构文档平铺、签发协作正文 408 行跨职责（E01），约 1245 条相对链接通过仍存在知识缺口（E04）；结构迁移保留有实际消费者的 8 条稳定路径并对比 58 份既有 Markdown 语义等价（E08，限记录中的规范化链接比较）。公共运行专题拆分并区分结构化日志目标与现状（E12）。独立评审 113 份文档/1645 链接通过仍发现旧数据库验证策略（E16）；有界再生性检查发现独立工具契约缺少消费者精确字段、状态和终态约束（E17）；人审又发现研究残留与术语问题（E19）。E20–E21 说明可再生人审材料和跨任务复用产物需要明确来源、版本与生命周期，属于已有 artifact / Consumer-local 责任的相关反馈，不单独证明新 Skill 必要。
- 上述证据支持项目级健康评审的独立价值（H1）与有界迁移/导航改善（H3），尚未充分证明独立 Skill 相对现有组合的增量收益（H2）、长期可持续性（H4）及跨 Consumer 泛化（H5）。原型与规范此前经只读核验真实存在；未重跑全部 E01–E21、组件测试或原生发现。原型仅供提炼，不能照搬固定路径、评审周期、分级、研究任务和本地产物目录。

## 3. 统一目标模型与取舍

纵向按总体目标/范围 → 能力/子系统 → 具体行为及必要设计 → 实现与验证渐进形成知识；横向在同一语义层比较实际覆盖，同时识别跨能力共同业务语义、技术机制和质量义务。两者共同形成有机、可追溯的知识与架构，而非固定层级树。

预防机制在需求与架构形成、局部设计和实现回流中按需生效；纠正机制由显式项目健康评审、里程碑、风险专项或 Consumer 约定周期触发。持续架构演进处理真实结构问题。日常局部变更不因此默认全面评审、提前设计全部功能、人工审批或全量回归。

统一范围内分 A、B 两个有界工作范围，先 A 后 B，逐项收敛，避免同时改写多条开发责任。A 输出的健康评审发现路由到 B 或现有真实 owner；B 提供公共能力形成和维护契约，供 A 检查，不互相复制程序。必要时依据新证据缩小范围或分拆协调，但不丢弃明确目标。除后续真正需要的正式能力外，不新增运行时、固定目录、中央索引/Registry、Method selector、批量模型 grader、常驻调度、多级 Gate 或通用业务框架。

## 4. 范围 A — 渐进知识形成与存量健康治理

### 4.1 目标与责任

建立按需使用的治理方法导航和独立健康评审执行责任。优先收敛 `document-governance` 候选 Skill（独立触发无待集成 diff、稳定输出、降低人工逐项提示依赖），并按[Skill 产品工程规范](../architecture/skill-architecture.md#8-准入)挑战是否已有机制能更简单可靠地承担。不是已经决定增加第 16 个 Skill：先验证现有 Skills + Consumer-local policy + 最小 Guide 的充分性，仅在现有 review-change 的自然契约有真实缺口时考虑扩展它，不把项目级评审混入普通 exact-diff review。若独立 procedure 确有增益则准入，否则收敛为最小 Guide 或现有能力修正。需要实证区分时采用小型同目标/权限/基线的隔离对照（A/C，必要时 B），不进行大规模重复实验，不将同会话作者自检称作独立盲测。

治理原则：明确单一 owner 与信息架构；总体、模块及横向专题责任清晰；知识粒度按实际职责和阅读维护成本确定；必要行为、规则、接口、状态/失败、安全、关键设计理由及验收可恢复；现行事实、候选、实际实现、验证与正式验收分开；研究仅在长期需要时保留依据，不把启发性对照提升为约束；历史有明确 provenance 角色；文档、IDL/Schema、代码契约、测试等均可按 Consumer 约定承载相应知识，不逐类写 Markdown。

### 4.2 候选执行契约

- 触发：显式项目维护、周期/里程碑、风险专项、无待集成 diff 的健康评审或获授权整理；普通局部任务继续现有回写。Skill 不自行调度。
- 输入：目标、授权、评审范围和模式、当前可恢复权威与本地政策、各参与仓身份/精确 HEAD/工作树、上次可恢复基线（若有）。不规定目录名；无法读取的仓或不可靠的基线显式保留。
- 过程：增量由可靠基线的实际差异入手，无变化可快速退出；无基线不等于无变化。全面由当前能力和知识入口开始，专项由 claim 和消费者开始。建立临时有界覆盖视图，按风险深查，其余有界抽样并记录未查范围。检查上下层责任与实现双向追溯、同级覆盖和细化合理性、共享能力/共同规则、导航和真实消费者、设计/代码/验证合同的现行一致性与有界可再生性。链接全绿不等于语义健康。
- 分类：缺失的已确认知识、真实需求/设计缺口、实现偏差、过时验证合同、冲突/重复/历史误用、过度细化、合理差异、证据不足；输出证据、影响、归属、优先级、最小处置及未核验范围。代码是证据，不擅自批准产品语义；不凭空补齐规则，也不自动删除安全义务或真实消费者依赖。
- 整改：默认只读，另获授权后冻结最小范围，保全有效语义、稳定路径/锚点、跨仓定位与实际消费者；按真实 Requirement / Design / implementation / verification 责任使用现有 Skills。高影响权威重组进入独立 `review-change`，按需 `converge`，检查实际差异、定向验证与独立恢复；只读评审不模拟实现收口。保留本地政策、产物生成来源及适用版本，投影不是第二套权威。
- 退出：报告范围、基线、发现、处置/升级与证据边界；无本地报告格式仍有最小可用结果；权限/owner/环境不足时仅阻塞受影响责任，不宣称未核验部分 PASS。不得自动扩大范围、推送、发布或重构业务。

### 4.3 渐进细化与人工评审

同级比较不按行数或文件数评分，复杂高风险模块可以更详尽，简单模块可以简洁，未实现功能不要求全面详细设计。通过总体→能力→具体行为/设计→实现/测试的逻辑追溯识别无上层依据的扩展、遗漏的必要知识和隐藏业务假设；人工可以逐层评审职责划分、覆盖和细化深度。按需复用 `human-review` 的可再生结构化投影及反馈回写，不能因评审视图出现而复制事实。评估 `establish-requirement-baseline`、`specify`、`clarify-architecture`、`technical-plan` 现有防止失衡的责任，仅对已确认的执行契约缺口作最小修订；范围 B 的公共能力确认/架构演进契约留 B 收敛。

## 5. 范围 B — 公共能力需求、设计与持续架构演进

### 5.1 在需求阶段主动确认公共能力

在新项目需求基线建立、既有需求基线系统性重建或显式公共能力梳理时，由 AI 根据产品目标、业务能力/流程、角色、数据、外部依赖、质量属性、安全合规、现行权威及本地约束识别候选。候选必须有项目依据，说明必要性、实际/预期消费者、可观察义务、待决风险、建议范围及优先级。检查共享业务能力（人员/组织、角色权限、字典、菜单、文件/归档等）及横切技术和质量需求（认证、鉴权、日志/审计、事务一致性、消息/异步任务与调度、配置、异常处理、数据访问、基础库适配等）。例示不是必选清单。

AI 提供精简分组候选并引导人工讨论，确认纳入、延期、排除或待确认的初始范围和关键约束。已确认权威义务直接恢复，不重复审批；可唯一推导且授权允许的事实直接处理；未确认产品取舍需人工决定；技术 HOW 候选转架构。非阻断待决能力不阻塞其他功能，安全/合规义务不能因延期而跳过。人工确认不是逐项技术审批。

确认后的 WHAT/WHY、共享业务不变量与可观察质量义务写入真实 Requirement/Domain/NFR owner，形成逻辑上的**初始公共能力需求基线**，不强制单独文件或 Registry；候选和评审投影默认非权威。**初始公共能力框架**是架构和技术选型对上述需求形成的最小职责/契约/依赖设计，不是需求阶段选定自研框架。此新增需求责任优先归 `establish-requirement-baseline`，复用 `human-review`；不新增公共需求 Skill 或固定阶段。

### 5.2 设计、抽象与独立收敛

- 前置抽象：在总体架构和技术选型时识别已知且有需求依据的跨模块共同义务、长期风险与真正必要的基础机制；先复用成熟框架/库或薄适配，不预建未确认 MQ、微服务、工作流、多租户或全部通用业务平台。当前 `clarify-architecture` 的 description、purpose 和步骤将实际阻塞 Specification/Technical Planning 作为条件，可能遗漏高返工/高成本难逆且已有依据的主动设计；最小调整该触发，不降低系统性责任门槛或恢复 Big Design Up Front。
- 演进式抽象：根据真实重复、规则漂移、变化传播、依赖循环、兼容与验证成本识别共同语义/不变量、变化原因、消费者与抽象收益。相似代码、同名对象不等于共同语义；不同业务失败规则或变化原因可以保持独立。先判断复用、组合、薄适配、局部重复或有界抽取；不预设通用上帝类、万能配置、继承/泛型/模板或所有 CRUD 同构。
- 技术与业务分责：通用机制不替业务确定权限、事务提交时点、失败回退、幂等/消息一致性等 WHAT；日志与安全审计可共用设施但责任不同，认证与授权分别明确。业务不变量回真实 Requirement owner，系统性职责回 Architecture，局部稳定共享契约回 Design；`technical-plan` 负责必要 HOW、适用/不适用消费者、数据/状态/事务/安全边界、依赖方向、版本、失败契约和验证设计，不建立第二套真值。
- 实施按实际依赖：`slice-work` 仍优先窄而完整的纵向单元，确有共同前置依赖或独立验证收益才切分基础单元，定义可验证交接和剩余集成义务；不机械按技术层切分，不要求所有公共能力全部建完才开始业务。实现可采用函数、模块、库、组合、适配器、拦截器等，具体技术和部署由 Consumer 决定。
- 独立验证：对规则和不变量运行单元/属性测试；事务、真实权限、MQ、持久化等用必要真实依赖验证契约及集成语义；以最小真实消费者验证接缝。测试替身不证明真实依赖，避免无关业务全链夹具成为默认前置。形成稳定的职责、公开契约、实际实现/版本与证据基线，不永久冻结代码。
- 影响控制：后续业务只消费未变契约且精确差异、依赖、配置证明旧 claim 不受影响时，按当前范围验证业务及必要接缝、复用未受影响证据；共享行为、运行配置、schema、安全、依赖版本、消费者或组合变化时按影响扩大验证。无可靠影响分析不能承诺跳过回归；最终系统集成与验收按实际 Consumer policy 执行。

### 5.3 持续架构演进与反复补丁的退出

“继续架构演进”作为面向人的任务意图和按需方法入口，而非预设同名 canonical Skill。Agent 恢复当前项目事实、范围和权限，主动识别新共同需求、抽象机会和架构退化，判断是否有真实收益；按问题返回 Requirement owner、`clarify-architecture`、`technical-plan` 或已有合法 Design owner。获授权后复用切分/执行/复核/收敛，维护依赖、契约、版本、真实消费者与证据。无收益时保持原结构；不自动触发全仓扫描或未授权重构。

开发中发现同一规则反复修改、跨模块返工、同一退出条件持续失败、schema/迁移不断扩张、混合夹具和重复无关验证时，`execute-unit` / `systematic-debug` / `converge` 应以证据区分实现缺陷、过时验证合同、环境、共享设计/架构缺口和任务范围扩大。若根因是设计或边界，停止扩展、冻结原目标并返回责任 owner，按授权收敛方案和定向验证，保留已确认的安全、集成和验收义务。不得借机全仓重构、虚报通过或继续追加补丁/门禁。固定失败次数、测试入口和阈值属于 Consumer policy。
