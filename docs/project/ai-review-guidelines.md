# AI 复核项目规则

本文定义 `agentic-dev` 仓库自身的 AI 复核规则。

**适用边界：** 本文属于 `agentic-dev` 的项目级治理，不是通用方法、Skill 契约、Skill 实现或使用方项目使用指南。其他项目只有在自身仓库权威明确采纳时才适用。

## 1. 目标

AI 复核用于在高影响变更进入最终人工复核或集成决策前，基于当前仓库权威和最终变更状态发现：

- 权威层级不一致；
- 方法语义回归；
- 契约与 Skill 实现断层；
- 未授权的范围扩大；
- 中文表达、正式概念身份或术语偏差；
- 人工 / 集成边界被弱化；
- 证据不足却被提升为长期结论；
- 新增或重大修改的长期权威产物缺少可执行的生命周期责任；
- 项目路线图、里程碑或其他恢复入口在当前变更一经集成后立即陈旧，并机械派生仅用于同步集成事实的尾部状态变更。

AI 复核不替代验证，也不构成人工批准或合并授权。

## 2. 必须执行 AI 复核的高影响变更

以下变更在进入最终人工复核或集成决策前必须完成与风险相称的 AI 复核：

- 修改方法或原则；
- 修改架构或 Skill 契约；
- 修改核心 Skill 实现；
- 修改 `AGENTS.md`、`docs/project/*` 或其他会改变本仓库长期治理行为的规则；
- 修改会实质改变 Agent 行为的使用 / 治理指南；
- 同时跨越方法、契约、Skill、治理等多个权威层的同步变更。

普通低风险文字修正、链接修正、无语义影响的排版调整，不要求为了形式完整性执行重型复核；如果它们属于上述高影响变更的一部分，则随该变更一并检查。

PR 不是触发 AI 复核的必要条件：

- 采用 PR 时，以最终 PR 状态和最终差异作为主要变更证据；
- 未采用 PR 时，以拟集成引用与目标基线之间的当前比较结果或等价可验证变更集作为主要证据；
- 不得通过选择非 PR 路径绕过本规则要求的 AI 复核。

## 3. 复核输入

复核不得只依赖作者的说明或此前聊天结论。至少重新读取：

1. 当前集成目标基线的仓库权威；
2. 采用 PR 时的 PR 元数据与变更文件，或非 PR 路径下对应的源 / 目标引用；
3. 最终差异或等价可验证变更集；
4. 当前变更层适用的更高优先级权威；
5. 面向人的内容发生变化时，适用的中文表达与术语规范；
6. 如果变更声称由使用方实验或证据驱动，相应 Issue 与可验证证据引用；
7. 如果变更新增、提升或重大修改长期权威产物，该产物的上游事实来源、当前消费者和现有替代 / 失效关系；
8. 如果变更涉及项目路线图、里程碑、当前状态或新上下文恢复入口，`docs/guides/using-agentic-dev.md` 中“项目路线图与集成状态”的现行维护边界。

复核依据必须来自当前可验证状态，不以会话历史代替仓库事实。

## 4. 复核维度

根据变更性质选择必要维度，不要求每个变更机械检查全部项目。

### 4.1 权威一致性

检查低层变更是否符合更高层权威，是否通过 Skill、Guide 或项目规则暗中改写方法 / 契约。

### 4.2 语义回归

检查措辞、重构或补充规则是否改变已有方法意图、阶段边界、授权边界或完成语义。

### 4.3 跨层一致性

当方法、契约、Skill 实现、使用指南存在映射关系时，检查是否出现一层已修改、其他受影响层仍按旧规则运行的断层。

### 4.4 范围控制

检查变更是否出现与目标无关的顺带修改、额外框架、额外 Skill、固定模板或其他缺乏证据的范围扩张。

### 4.5 中文表达、正式概念身份与术语

面向人的新增或修改文本必须遵循 `docs/guides/terminology-guidelines.md`。

重点检查：

- 叙述主体是否保持自然中文；
- 已有稳定中文表达的概念是否仍机械附带英文；
- 是否把“中文（英文）”或“英文（中文解释）”继续当作默认术语模板；
- 是否因为旧文档、工具输出、历史聊天或个人记忆的语风而扩散不必要英文；
- 必须保留原样的代码标识、路径、命令、API / CLI 参数、Git 引用、Skill 调用名、外部正式名称和固定值是否仍保持精确；
- 面向人工的状态是否优先用中文表达，而不是无必要地堆叠 `PASS`、`READY`、`BLOCKED` 等英文状态；
- 修改后的内容是否仍存在会诱导新上下文恢复旧中英文混写风格的高影响示例；
- 正式概念是否使用唯一首选中文名称，还是为同一正式英文身份引入了新的中文别名；
- 中文化是否把方法阶段、方法门禁、产物、能力层、Skill 概念或 Skill 调用名错误合并；
- 同一中文名称是否被用来指代两个具有不同职责或生命周期的正式对象，却没有提供足够的对象类型区分；
- 翻译是否改变 Technology Profile、Verification Profile、Task-oriented Skill、Runtime Adapter、Execution Unit、Technical Planning / Technical Plan 等既有概念的正式身份、架构层级、职责或契约边界；
- 旧中文迁移别名如果仍存在，是否只出现在历史材料或待收敛区域，而没有继续作为新增规范性表达扩散。

对于会持续塑造 Agent 输出行为的规则，**语义正确但无必要中英文混写**可以构成中等级治理问题，应在当前变更中收敛，而不是以“英文更精确”为由放行。

对于语言或术语修改，如果它把两个正式概念错误合并、把一个正式概念迁移到错误架构层、改变方法阶段 / 产物 / Skill 之间的对象身份，或者使后续 Agent 无法从当前权威稳定恢复原有工程语义，应至少记录为中等级问题；如果已经改变更高层方法、契约或授权边界，则按相应语义问题升级为阻塞。

### 4.6 人工与集成边界

检查变更是否错误地把工具能力等同于授权，或弱化人工升级、进入集成决策条件、合并 / 发布 / 部署等既有边界。

### 4.7 证据一致性

当变更基于实验、使用方或运行时发现时，检查结论是否超出了现有证据能支持的范围，并确认分类层级正确。

### 4.8 产物生命周期闭环

当变更新增、提升或重大修改长期权威产物时，检查是否能从方法、仓库权威与最终变更中明确回答：

- **产生者：** 哪个方法职责或已授权角色负责确认并形成该产物；
- **触发条件：** 什么事实或变化触发创建、权威提升或重大更新；
- **消费者：** 哪些后续阶段、Skill、人员或系统依赖它；
- **持久化：** 它如何在仓库权威中长期保存、被发现并参与优先级判断；
- **更新：** 新证据、需求变化或系统变化出现时，谁负责在什么条件下维护；
- **取代：** 旧内容失效时，如何标明取代关系、保留必要历史并避免冲突版本同时生效；
- **升级：** 哪些权限冲突、高影响变化、难逆决定或外部影响必须升级。

该检查不要求每个阶段创建文件，也不要求固定目录、模板或独立产物管理 Skill。对临时产物只检查其退出或丢弃边界；对长期权威产物，如果上述责任存在会导致后续 Agent 无法可靠产生、更新或识别当前有效事实的缺口，应记录为阻塞或中等级问题。

### 4.9 集成后状态闭环

当变更涉及 `AGENTS.md`、README、项目路线图、里程碑记录、协调计划或其他会被新上下文用于恢复当前项目状态的入口时，必须检查：

- 当前拟集成版本如果立即被接受并集成，是否仍能正确表达长期阶段、里程碑完成状态、已经决定的下一步和候选边界；
- 是否仍保留“等待当前 PR 合并”“由人工决定当前 PR 是否集成”等会在当前 PR 合并后立即陈旧的短期描述；
- 是否机械复制 PR 的打开 / 已合并状态、精确合并提交、临时分支删除等 GitHub 原生事实，而这些事实并不是长期路线恢复所需的证据锚点；
- 对尚未发生的合并是否保持事实准确，不虚构“已合并”，同时是否能使用与瞬时 merge 状态解耦的长期状态表达，使拟集成版本在合并后无需立即再修；
- 合并后如果发现状态差异，是否优先把精确集成证据留在 PR、Issue 或 Git 历史；只有出现合并前无法合理表达、且会立即阻塞或误导新上下文的长期路线变化时，才允许创建独立状态修复；
- 状态修复是否会递归产生另一个仅用于记录该修复已经合并的尾部状态 PR。

具体的路线图维护边界以 `docs/guides/using-agentic-dev.md` 的“项目路线图与集成状态”为准；本节只把该既有边界接入 `agentic-dev` 自身的高影响 AI 复核，不重新定义一套平行规则。

如果当前拟集成变更会在合并后立即使主要恢复入口陈旧，或按现有设计必然机械派生一个仅用于同步本次集成事实的尾部状态 PR，应至少记录为中等级治理问题并在当前变更中收敛；如果陈旧状态会进一步错误恢复活动里程碑、授权边界或重大项目路线，则按相应权威 / 语义问题升级为阻塞。

## 5. 问题等级与结论

AI 复核问题使用以下严重程度：

- **阻塞**：会导致权威冲突、错误方法语义、错误授权边界、明显契约 / Skill 断层，或使变更不应按当前状态进入最终人工复核 / 集成决策；
- **中等**：不会立即破坏核心语义，但会造成持续歧义、治理不一致、语言误导、正式概念身份漂移或明显维护风险，应在当前变更中收敛；
- **低 / 非阻塞**：可改进但不影响当前变更的安全接受。

只有在已检查维度中不存在未解决的阻塞或中等级问题时，才能报告：

> **AI 复核：通过**

“通过”只表示当前 AI 复核未发现阻塞当前变更的问题，不代表人工已经批准，也不授予 Merge 或其他集成权限。

## 6. 修复后的重新复核

必须使用以下闭环：

```text
复核
→ 发现问题
→ 修复
→ 重新读取最终变更状态
→ 针对性重新复核
→ 通过或保留未解决问题
```

如果复核后发生可能影响已检查结论的实质修改，旧复核不能自动覆盖新状态。必须重新读取最终变更状态，并至少对受影响维度重新复核。

纯粹不影响语义的元数据或格式变化可以采用轻量复核，不为了形式完整性重复全部检查。

## 7. 复核独立性与上下文

AI 复核不要求固定 Reviewer Agent，也不要求每次创建新会话，但复核者必须：

- 重新读取当前仓库权威与最终变更状态；
- 不把作者此前未持久化的推理当作复核依据；
- 对高影响方法、契约或治理变更，在运行环境支持且成本合理时优先采用新上下文或等价的独立复核方式；
- 不从历史聊天或个人记忆恢复已被当前仓库取代的语言风格。

关键要求是**独立重新建立证据与判断**，而不是机械要求新的窗口或新的 Agent 实例。

## 8. 复核结果记录

不要求为每次 AI 复核创建独立长期文档，但本规则要求执行的复核必须留下最小可追溯摘要。

采用 PR 时，在进入最终合并决策前，应在 PR 讨论或正式 Review 中记录：

- 复核范围 / 维度；
- 阻塞 / 中等级问题数量及必要的证据引用；
- 是否经过修复后的重新复核；
- 最终结论。

不需要把完整推理过程、聊天记录或大篇幅复核报告写入 PR。

未采用 PR 时，应在当前集成决策可见的外部协作记录中保留等价摘要，不要求为了记录复核再创建新的长期文档体系。

如果复核本身产生外部写操作，继续遵循 `docs/guides/external-operation-guidelines.md` 的“分析 → 执行 → 验证 → 汇报”闭环。

## 9. 与人工复核的关系

以下关系必须保持明确：

```text
AI 复核通过
≠ 人工批准
≠ 合并授权
```

会改变方法、契约、核心 Skill 行为、仓库权威或长期治理规则的变更，即使 AI 复核已经通过，仍应由适用的人工权威 / 仓库策略决定是否接受和集成。

AI 的职责是尽可能在人工决策前发现一致性、证据、语义和表达问题；人工的职责是决定高影响长期规则是否被项目接受。
