## 1. 目的

本文在 V3-02 已完成所有权盘点的基础上，只处理 Skill 身份、Skill 与其他工程能力 / Guide / 仓库本地规则之间的正文边界，以及未来新增 Skill 的准入判断。

本阶段不重新打开第一批核心 Skill 工程，不因为某段内容“可复用”“重要”“会被 Agent 读取”或“存在步骤”就自动 Skill 化。

稳定的新增 Skill 准入门禁已经提升到 `docs/architecture/skill-architecture.md`；本文记录 V3-04 的项目级裁决与证据关系，不维护第二份长期 Skill 架构。

## 2. Skill 身份判定

一个能力只有在同时具有以下稳定属性时才适合作为 Skill：

- 明确触发条件与不适用条件；
- 稳定输入；
- 可重复且足够独立的执行过程；
- 明确输出；
- 明确退出、阶段返回或升级条件；
- 可以独立组合或调用；
- 过程复杂度足以值得按需加载和独立维护。

以下信号单独存在时都不足以形成新 Skill：

- 跨仓库可复用；
- Agent 在普通运行中会读取；
- 内容很重要；
- 有若干按顺序执行的步骤；
- 会被多个现有 Skill 消费；
- 当前文件位于 `skills/` 或 Guide 中。

如果一个能力主要表达横切约束、默认知识、仓库本地值、使用方生命周期或人类说明，应由对应工程能力、仓库本地规则、生命周期权威或 Guide 持有，而不是为了激活方便升级为 Skill。

## 4. 关键重叠裁决

### 4.1 `execute-unit` 与工程纪律

`execute-unit` 的稳定任务入口、输入、输出、退出和阶段返回均成立，因此 Skill 身份不受影响。

`docs/architecture/engineering-disciplines.md` 已明确：三个工程纪律没有独立任务入口，应由多个职责消费，`execute-unit` **只需要保留薄执行规则，不复制完整纪律正文**。

V3-04 已将 `execute-unit/SKILL.md` 中原先展开的：

- 实现最小化与推测性复杂度控制；
- 精准修改与差异范围控制；
- 数据访问作用域与有界性控制；
- 相关配置责任与既有能力复用细则；

缩回为当前执行单元中的条件识别、规范所有者指针和薄执行判断。具体纪律规则只在 `engineering-disciplines.md` 单点维护。

本次去重没有改变 `execute-unit` 的职责、触发、输入、输出、一次一执行单元、调试返回、阶段返回或退出条件。

同时，Skill 不把 `agentic-dev` 上游物理路径变成使用方普通运行依赖：使用方采用后只消费自己的本地已采用工程纪律权威。

### 4.2 `converge` 与跨职责验证规则

`converge` 必须拥有功能整体收敛过程，包括：

- 从规格到系统状态的覆盖视图；
- 缺失、部分实现、冲突和未请求行为；
- 功能整体当前证据覆盖；
- 跨执行单元集成缺口；
- 领域 / 架构 / ADR / 产物生命周期 / Roadmap 缺口路由；
- `READY / GAPS` 结果语义。

这些是 `converge` 执行过程的组成部分，不应抽走。

但以下横切规则不是 `converge` 独有：

- 验证契约当前有效性；
- 证据类型与声明匹配；
- 跨提交复用证据声明；
- 视觉证据；
- 人工复核基线隔离；
- 数据库迁移完成证据。

它们应由跨职责验证工程能力持有。对当前 `converge/SKILL.md` 复核后，没有发现需要在 V3-04 立即删除的第二份完整规范正文，因此不为了阶段形式机械修改该 Skill。

当前证据不足以创建 `verify-evidence` Skill：这些规则没有统一独立任务入口、独立输出或稳定单独调度价值。

### 4.3 `github-actions-verification` 与通用外部操作 / 验证能力

该 Skill 具有独立且稳定的平台过程：

- 识别 GitHub Actions 验证范围；
- 检查工作流与运行环境能力；
- 选择可观察的触发路径；
- 对齐声明、验证层与实际触发；
- 分层反馈与完成验证；
- 运行时、Artifact、诊断与共享资源处理。

因此平台专项 Skill 身份成立。

其语义层级必须保持：

```text
通用外部操作 / 验证工程能力
→ GitHub Actions 平台过程
→ 使用方仓库具体工作流 / 策略 / 运行状态
```

`github-actions-verification` 不拥有：

- 通用“工具能力 ≠ 授权”原则；
- 所有平台的外部写后重读闭环；
- 通用“证据先于声明”规则；
- 使用方的 Merge / Release / Deploy 权限；
- 所有使用方的统一 CI 拓扑。

当前 `github-actions-verification/SKILL.md` 已明确自身实现既有方法 / 外部操作 / 验证语义并服从使用方策略；复核后没有证据要求在 V3-04 机械重写。

### 4.4 使用方生命周期不是采用 / 升级 Skill

V3-03 已明确“使用方生命周期（`Consumer Lifecycle`）”属于可复用工程能力，而不是产品开发方法阶段，也不因为具有状态转换和过程顺序就自动成为 Skill。

生命周期主要拥有**何时允许进入上游、何时完成采用 / 升级、普通运行如何回到本地、何时允许重新进入**等跨过程规范语义；具体动作由 Guide、仓库权威、验证能力和未来资源 / 发现架构共同实现。

因此 V3-04 不创建 `adopt-agentic-dev`、`upgrade-baseline` 或类似 Skill。

### 5.2 `consumer-local-rule-activation.md`

## 6. 验证与外部操作规则族

### 6.1 验证规则族

结论：**属于可复用验证工程能力，不形成独立 Skill。**

理由：

- 规则按条件横切 `execute-unit`、`converge`、平台专项 Skill 与调试场景；
- 没有统一稳定的独立任务入口；
- 没有单一独立输出；
- 多数规则是条件性约束和证据契约，而不是一个可独立调度过程。

物理载体、metadata 或画像形式留给 V3-05，不在 V3-04 冻结。

### 6.2 外部操作规则族

结论：**当前仍不形成新的通用外部操作 Skill。**

现有规则族混合了：

- 跨平台外部写前读取 / 写后重读验证；
- 授权与多仓库边界；
- 异步观察；
- 共享资源所有者 / 租约 / 清理；
- 临时证据向持久输入的晋升；
- 依赖 PR / 堆叠 PR 集成纪律；
- 二进制 / 媒体输入真实性验证。

它们没有一个统一稳定输出，也不是每次外部操作都需要全部执行。当前更适合作为若干可复用工程能力 / 仓库本地政策挂接点，被具体平台 Skill 按条件消费。

如果未来证据证明其中某个子过程具备稳定独立触发、输入、输出、退出和单独调度价值，再重新按 Skill 准入门禁判断；V3-04 不提前升级。

## 8. Skill 支持资源边界

稳定规则已经提升到 `docs/architecture/skill-architecture.md`：某个 Skill 下的 `references/*`、fixture、template 或脚本只有在以下条件下才保持支持资源身份：

- 直接服务该 Skill 执行过程；
- 不独立定义跨 Skill / 跨仓库长期规范语义；
- 生命周期随该 Skill 的当前身份管理；
- 被删除后不会丢失其 Skill 之外的规范事实。

如果支持资源开始被多个 Skill / Guide 独立消费，或出现独立触发 / 更新 / 适用范围，就必须重新判断真实语义所有者，不能因为物理位置在某 Skill 目录就继续把它当内部附件。

当前 `skills/github-actions-verification/references/*` 继续属于该平台 Skill 的支持资源，没有证据要求提升为平级语义所有者。

## 9. 新 Skill 准入门禁

稳定准入规则已经提升到 `docs/architecture/skill-architecture.md`。未来新增 Skill 至少必须同时回答：

1. **触发条件**：什么时候应进入该职责？什么时候明确不进入？
2. **输入**：是否存在稳定、可描述的最小输入？
3. **过程**：是否存在可重复、足够复杂、值得按需加载的过程？
4. **输出**：是否存在稳定独立输出，而不只是“遵守若干规则”？
5. **退出 / 返回 / 升级**：如何停止、返回上游或升级？
6. **可组合性**：能否作为独立职责被其他流程调用，而不是接管完整生命周期？
7. **所有权**：是否会复制核心方法、架构、工程纪律、使用方生命周期、仓库本地规则或 Guide 已拥有的正文？
8. **证据**：是否有官方 / 成熟工程实践、专项评估或使用方证据支持该独立职责，而不只是命名偏好？
9. **评估**：是否能设计有辨识力的行为评估证明它比现有语义所有者或支持能力更合适？

任一高影响边界无法回答时，保持工程能力 / Guide / Research 候选，不为了目录完整或运行时激活便利提前 Skill 化。

## 11. V3-04 门禁

- 9 个当前 Skill 的身份和重叠均有明确结论；
- `execute-unit` 的工程纪律消费不再形成第二规范所有者；
- `converge` 与跨职责验证规则边界明确；
- `github-actions-verification` 与通用验证 / 外部操作能力边界明确；
- 验证 / 外部操作规则族没有被错误 Skill 化；
- 使用方生命周期没有被错误 Skill 化；
- Guide / 派生路由不再被误认为 Skill 执行过程所有者；
- `first-batch-skill-design.md` 不再与当前 Skill 权威平行；
- 支持资源与平级语义所有者的判断规则明确；
- V3-05 / V3-06 可以直接消费 Skill 身份和准入结论；
- AI 复核对高影响 Skill 所有权 / 准入歧义不存在未解决的阻塞或中等级问题。

达到门禁后，只进入“是否启动 V3-05”的规划判断，不自动执行后序迁移、资源模型或发现架构。
