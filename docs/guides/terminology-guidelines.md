# 中文表达与术语规范

本文规定 `agentic-dev` 面向人的内容如何使用中文和必要的原始英文标识。

目标不是“中英文并列更完整”，而是让人工能够持续、低负担地理解 Agent 的分析、计划、状态、复核和项目文档，同时保留真正需要精确匹配的技术对象。

本文属于项目级文档治理，不重新定义方法、架构、契约或 Skill 的语义。术语含义发生冲突时，仍以对应仓库权威为准。

## 1. 适用范围

本规范适用于 `agentic-dev` 中所有面向人的内容，包括：

- `AGENTS.md`、`README.md`；
- 方法、架构、契约、决策和项目治理文档；
- 使用指南、研究、计划和其他说明性 Markdown；
- Agent 在聊天中的分析、进度汇报、结果总结和人工决策说明；
- Issue、PR、Review Comment、AI 复核摘要和人工复核说明；
- Git Commit 的中文摘要部分；
- 其他以人类阅读为主要目的的输出。

机器接口、代码和必须精确匹配的原始值按第 4 节处理。

使用方项目采用什么主导语言，由使用方自己的仓库权威决定；`agentic-dev` 不把自身中文规则自动强加给其他项目。但当使用方明确选择中文作为主导语言时，可以直接采用本规范的表达原则。

## 2. 核心原则

### 2.1 自然中文是默认值

当前仓库面向人的内容默认使用自然、完整、连续的中文。

如果一个概念已经有稳定、清楚且不会改变语义的中文表达，应直接使用中文，不再为了“精确”“专业”或“方便检索”机械附带英文。

推荐：

```text
执行单元完成后必须提供当前证据，再进入整体收敛。
```

不推荐：

```text
执行单元（Execution Unit）完成后必须提供当前证据（Current Evidence），再进入 Converge。
```

英文不是默认的精确性证明。真正的语义精确性来自当前仓库权威、上下文和必要的原始标识，而不是双语重复。

### 2.2 不把中英文并列当作标准模板

以下形式不再作为默认推荐写法：

```text
中文概念（English Term）
English Term（中文解释）
```

只有在缺少英文会造成真实歧义、需要与外部规范精确对照，或当前任务明确要求双语对照时，才可以在首次必要位置补充一次原始英文。

一旦对象已经明确，后续继续使用自然中文，不重复双语注释。

### 2.3 句子主体必须保持中文

即使句子中必须保留某个原始英文对象，也应让动作、判断、因果、状态和结论保持中文。

推荐：

```text
`readiness-check` 检查未通过，需要回到工作切分重新形成候选执行单元。
```

不推荐：

```text
Readiness FAIL 后需要 re-slice Candidate Execution Units，再重新 gate。
```

### 2.4 面向人工的状态优先中文表达

当 `PASS`、`FAIL`、`READY`、`BLOCKED` 等只是给人工阅读的状态说明，而不是必须精确匹配的机器字段时，应写成：

- 通过；
- 失败；
- 已就绪；
- 受阻。

只有在引用真实枚举值、日志、命令输出、协议字段或外部系统状态时才保留原值，并在需要时用中文解释。

### 2.5 正式概念身份保护

中文化只能改变**面向人的表达形式**，不得改变正式工程概念的身份、对象类型、架构层级、方法职责、契约或机器标识。

规则：

- 一个正式概念只维护一个首选中文名称；
- 正式英文身份只作为概念身份锚点，不要求在每次叙述中重复；
- 本文第 5 节的身份表只统一“这个中文名称指向哪个正式概念”，不覆盖方法、架构或契约文档对该概念职责的正式定义；
- 定义某个正式概念的权威文档可以在首次定义处保留一次正式英文身份，后续正文使用首选中文名称；
- 如果同一组词同时对应方法阶段、方法门禁、产物、能力层或 Skill 调用名，必须按对象类型区分，不能因为中文表达相近就合并语义；
- 精确 Skill 调用名、文件名、协议字段、枚举值和其他机器对象继续保持原样；
- 历史文档中的旧中文别名在完成全量收敛前可以作为迁移输入被识别，但不得继续作为新内容的推荐名称。

因此，正式术语的判断优先顺序是：

```text
当前仓库定义权威中的职责语义
→ 第 5 节正式概念身份映射
→ 当前上下文中的自然中文表达
```

不能反过来根据某个中文词的日常含义重解释正式工程概念。

## 3. Agent 会话与汇报规则

语言治理不仅约束文档，也约束 Agent 的实际协作输出。

当当前仓库规则指定中文时：

- 分析过程面向用户展示的部分使用中文；
- 进度更新使用中文；
- 规划候选、完成定义、风险和阻塞使用中文；
- 验证结果和 AI 复核结论使用中文；
- 不因为输入材料、工具输出、历史 PR 或旧文档大量使用英文，就自动模仿其语风；
- 不从历史聊天、其他会话或个人记忆恢复旧的中英文混写习惯；
- 当前用户明确要求另一种语言时，以该次明确要求为准。

如果必须引用英文原文，应把引用与自己的中文判断分开，不让原文语言扩散成整个回答的叙述语言。

## 4. 必须或适合保持原样的内容

以下内容默认保持原生形式，不强制翻译：

- Skill 的正式目录名、调用名，例如 `clarify-intent`、`execute-unit`；
- 文件名和路径；
- Branch 名、Commit SHA、Issue / PR 编号；
- 代码标识符、配置键、数据库字段、枚举值；
- API、CLI、命令和参数；
- GitHub Actions 的真实事件名、字段名或表达式；
- 外部产品、框架、协议、标准和规范的正式名称；
- 错误信息、日志、命令输出和需要逐字核对的外部文本；
- 必须与外部系统精确匹配的固定状态值。

保持原样只适用于对象本身，不代表围绕它的整句话也应切换成英文。

## 5. 正式概念的中文表达与身份映射

本节只统一正式概念的**名称身份**。正式职责、生命周期、输入输出和优先级仍由对应的方法、架构、契约或仓库权威定义。

### 5.2 容易被中文化合并的对象

以下对象必须保持区分：

| 中文表达 | 正式对象 | 不应混淆为 |
|---|---|---|
| 技术规划 | 方法阶段 `Technical Planning` | 技术计划产物 `Technical Plan` |
| 技术计划 | 条件性长期协调产物 `Technical Plan` | 方法阶段本身 |
| 整体收敛 | 方法阶段 / 职责 `Converge` | 精确 Skill 调用名 `converge` |
| 执行 | 方法阶段 `Execute` | 精确 Skill 调用名 `execute-unit` |
| 规格说明 | 方法阶段与权威规格产物 `Specification` | 精确 Skill 调用名 `specify` |
| 就绪门禁 | 方法门禁 `Readiness Gate` | 精确 Skill 调用名 `readiness-check` |
| 技术画像 | 工程能力层 `Technology Profile` | 任务型技能或项目技术配置文件 |
| 验证画像 | 工程能力层 `Verification Profile` | 固定验证命令清单或某次运行结果 |
| 使用方生命周期 | 工程能力层 `Consumer Lifecycle` | 产品开发方法阶段、单个采用 / 升级 Skill 或使用方项目事实 |
| 运行时适配器 | 工程能力层 `Runtime Adapter` | 通用方法或新的方法阶段 |
| 技能 | 仓库正式 `Skill` 概念 | 某项普通技术知识或技术画像 |

在需要同时讨论两种对象时，应直接写出对象类型，例如“技术规划阶段”和“技术计划产物”、“整体收敛阶段”和“`converge` 技能”，而不是依赖读者从同一个词猜测身份。

### 5.3 当前迁移别名

以下旧中文名称已在现有高优先级文档中发现，只作为全量收敛期间的迁移别名识别，不再用于新增内容：

- “技术配置档” → “技术画像” (`Technology Profile`)；
- “验证配置档” → “验证画像” (`Verification Profile`)；
- “运行时适配层” → “运行时适配器” (`Runtime Adapter`)，除非上下文明确只是在描述普通实现层而不是正式能力层。

如果后续扫描发现新的冲突别名，不应直接就地选择译名。先确认它指向的正式对象与定义权威，再更新本节映射或修正文档。

## 6. 标题、表格、列表和流程图

标题优先使用中文。

推荐：

```text
## 人工介入边界
## 新上下文恢复规则
## 技能契约对齐检查
```

表格、列表和流程图同样优先使用中文动作和状态。只有节点本身是代码、命令、固定 Skill 名称或外部系统字段时才保留英文。

流程示例：

```text
读取当前状态
→ 判断
→ 修改
→ 重新读取
→ 汇报
```

不应为了“方法感”把可以自然表达的流程全部改写成英文动词。

## 7. PR、Issue、复核和提交信息

除非外部平台或协作对象明确要求其他语言，当前仓库的面向人工协作内容使用中文：

- PR 标题和说明使用中文；
- Issue 标题、正文和评论使用中文；
- AI 复核和人工复核摘要使用中文；
- Git Commit 按提交规范保留固定的 `type(scope)` 结构，摘要使用中文；
- 代码片段、路径、日志和外部状态值按第 4 节保持原样。

不得因为 GitHub、Git 或 CI 属于英文生态，就把整段协作说明切换成英文。

## 8. 既有内容的收敛方式

本规范从“工程术语语义安全与现行文档全量收敛 v1”开始增加正式概念身份保护，并对当前仓库人类可读文档执行一次全量扫描。

扫描和修订必须遵循：

- 当前方法、原则、架构、契约、工程纪律、技术画像、Skill 实现与当前使用 / 治理文档逐文件检查；
- 高影响入口优先保证首选中文名称和正式概念身份一致；
- 发现英文时先判断它是普通叙述、正式概念身份还是机器 / 外部精确标识，不能机械翻译；
- 发现中文别名时先判断是否指向同一正式概念，不能通过翻译制造新的概念分支；
- 历史研究、已关闭计划、旧证据和 Git 历史纳入扫描分类，但不为了表面一致性整体重写；只有它们仍被当前入口引用并会造成当前语义冲突时才修订。

如果旧文档中的中英文混写同时暴露真实语义冲突，应按对应权威流程单独处理，不能用翻译替代语义决策。

## 9. 与知识边界的关系

项目事实和项目表达规则都应从当前可发现的仓库权威恢复。

历史聊天、其他会话、其他项目和个人记忆：

- 不能补充未固化的项目事实；
- 不能覆盖当前仓库的语言规则；
- 不能因为过去长期使用某种语风，就把它继续当作项目默认风格。

账户级记忆的删除不属于 Repository 能力。需要彻底移除旧项目记忆时，应由用户在 ChatGPT 的个性化设置和原始信息来源中完成清理，并在清理后使用真正的新上下文重新验证。

## 10. 复核检查

检查一段面向人的输出时，至少问：

1. 不看英文部分，中文是否已经能够完整表达结论？
2. 保留的每一个英文对象是否确实需要精确匹配或承担正式概念身份？
3. 正式概念是否使用第 5 节唯一首选中文名称，还是引入了新的别名？
4. 中文化是否把方法阶段、产物、门禁、能力层或 Skill 调用名合并成了同一个对象？
5. 是否存在可以直接翻成中文却仍被当作“术语”保留的普通词？
6. 是否因为旧文档、历史聊天或工具输出的语风而无意识扩散英文？
7. 人工是否能够连续阅读，而不需要频繁在两种语言之间切换？

只要英文不是为了精确匹配、正式概念身份或外部正式名称而必要，就优先删掉英文而保留自然中文。
