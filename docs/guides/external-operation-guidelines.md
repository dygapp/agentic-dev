# 外部操作协作指南

本文说明 `agentic-dev` 中的 Agent 在具备 GitHub、仓库、Issue、PR、外部 API 或其他可产生外部状态变化的操作能力时，应如何管理分析、执行、验证和汇报。

本文属于项目级操作治理，不新增方法阶段，也不定义新的 Skill。

## 1. 核心闭环

外部操作统一遵循：

```text
分析
→ 执行
→ 验证
→ 汇报
```

在 GitHub 等可读写系统中可以具体理解为：

```text
读取
→ 判断
→ 写入
→ 重新读取
→ 汇报
```

核心要求：

- 外部状态修改前先读取；
- 明确目标、权限和最小必要操作后再执行；
- 写操作后重新读取事实来源验证；
- 工具调用成功不等于目标状态已经完成；
- 只汇报已有当前证据支持的状态。

## 2. 分析：建立真实状态

执行外部写操作前，Agent 应确认：

- 当前仓库权威；
- 当前外部对象状态；
- 用户请求的目标结果；
- 当前运行环境可用能力；
- 当前操作授权边界。

不要依据旧聊天、缓存印象或此前状态推断当前外部状态。

### 2.1 能操作不等于已授权

拥有外部工具能力不代表自动获得执行授权。

以下操作仍需遵守人工权威或仓库策略：

- 合并；
- 发布；
- 部署；
- 破坏性清理；
- 其他不可逆或高影响修改。

### 2.2 多仓库操作分别确认授权

同一任务涉及多个仓库时，Agent 必须分别确认每个仓库的操作授权。某个仓库的读写权限、当前认证身份或运行环境工具能力，不会自动授予对另一个仓库的同类操作权限。

应根据当前人工权威与各仓库权威，按需区分：

- 读取文件、提交、PR、Issue 与 GitHub Actions 状态；
- 创建或更新 Issue / 证据；
- 修改文件、分支、提交或 PR；
- 触发、重跑或取消工作流；
- 合并、发布、部署或破坏性清理。

具体授权组合由当前项目决定，本指南不要求所有使用方项目使用统一权限矩阵，也不把“上游仓库只读”设为通用规则。

如果某项跨仓库操作的授权不明确，应停止该项操作并确认边界；其他已经明确授权且不依赖该操作的工作可以继续，不应把局部授权缺口扩大成整个任务的默认停止条件。

当这类边界会持续约束后续工作时，应按当前仓库权威固化到可发现的项目规则或等价载体，不能只依赖当前聊天或运行环境的临时授权印象。

## 3. 人工介入边界

Agent 不应把所有中间判断都升级给人工。人工介入应集中在真正需要人工权威或人工判断的节点。

### 3.1 默认原则

当以下条件同时满足时，Agent 应尽量自主完成一个完整闭环：

- 目标明确；
- 操作范围明确；
- 权限明确；
- 风险低；
- 操作可逆；
- 不改变长期规则或架构方向。

此时应连续完成分析、执行、验证和汇报，而不是在每个中间步骤请求确认。

### 3.2 需要提前人工介入的情况

包括但不限于：

- 目标、范围或验收标准存在关键歧义；
- 将改变方法、契约、仓库权威或长期治理规则；
- 存在多个长期影响明显不同的方案选择；
- 涉及高影响、不可逆或共享状态变化；
- 当前授权边界无法判断。

### 3.3 不需要频繁确认的情况

通常不需要单独请求确认：

- 文档措辞调整；
- 符合现有规则的文件组织；
- 低影响、可逆的实现细节；
- 已明确目标下的执行步骤。

目标是让人工关注决策和授权，而不是逐步审批 Agent 的每个动作。

## 4. 执行：只做最小必要操作

完成分析后，只执行当前目标要求的最小外部变更。

原则：

- 一次外部变更保持单一主要目的；
- 不顺带修改无关内容；
- 不为了完整性扩大范围；
- 不基于未经验证的假设继续操作。

### 4.1 验证外部二进制与媒体输入的真实内容

从外部站点、接口、附件或其他仓库取得的二进制 / 媒体资源，文件名、扩展名、URL 后缀和响应头只提供线索，不能单独证明内容类型。

把资源版本化或交给运行环境消费前，应按当前风险完成：

```text
取得资源
→ 验证内容签名或媒体类型
→ 必要时解码或解析
→ 必要时规范化
→ 版本化
→ 在目标运行环境验证
```

具体要求：

- 使用文件魔数、可靠的媒体类型识别或实际解码 / 解析核对真实格式；图片等资源按需要同时核对尺寸、色彩、透明度或其他会影响目标声明的属性；
- 如果真实格式与扩展名、声明类型或目标运行环境要求不一致，先判断应更正命名、转换格式还是拒绝输入；不得只改扩展名伪装格式；
- 转换或规范化后重新验证生成物，不把“转换命令成功”当作资源可用；
- 保留当前任务需要的最小来源关系，并在目标运行环境中验证加载和展示 / 消费结果；
- 只有内容类型、格式差异会影响当前行为、验证或安全边界时才增加相应检查，不要求对普通文本或所有文件无差别执行昂贵媒体分析。

## 5. 验证：写后重新读取事实来源

必须区分：

```text
写操作响应
≠
已验证的外部状态
```

写 API 返回成功，只证明操作被接受或执行，不代表目标状态已经成立。

外部写操作完成后，应重新读取相关事实来源验证：

- 文件修改后的内容和分支状态；
- Issue 的实际状态；
- PR 的元数据、变更文件与差异；
- 合并后的目标分支和提交。

如果验证失败，应重新分析，不得继续基于错误状态执行后续操作。

### 5.1 异步外部操作属于闭环中间状态

触发工作流、部署、远程任务或其他异步操作，只表示执行请求已被接受，不代表验证已经完成。`queued`、`pending`、`in_progress` 等非终态不能被当作目标状态，也不应仅因为外部系统仍在运行就默认把当前任务交回人工。

当当前目标包含取得执行结果或验证证据，且运行环境能继续观察状态时，应在授权范围内保持同一闭环：

```text
执行
→ 观察
→ 收集当前证据
→ 诊断
→ 在授权范围内修复或重试
→ 验证
→ 汇报
```

具体要求：

- 使用与正常运行基线相称的轮询间隔、等待上限、超时与取消策略，避免无限等待；
- 每次观察重新读取当前事实来源，不使用旧状态推断运行已经结束；
- 运行失败时先取得必要日志或诊断证据，再在当前授权范围内修复和重试；
- 只有需要人工权威的权限、业务、架构或高影响决定才升级人工；“仍在运行”本身不是人工决策；
- 运行环境无法继续取得必要证据且不存在已授权的替代路径时，记录为真实阻塞；
- 达到有界观察上限而运行仍未结束时，只能汇报“已执行但未完全验证”的当前状态，不能声明目标完成。

异步闭环可以在以下任一条件成立时结束：目标状态已由当前证据验证；出现真实阻塞；或达到有界观察上限并准确保留未验证状态。后两种结果都不能伪装成完成结论。

### 5.2 并发边界必须匹配真实共享资源

异步运行的逻辑标识不一定等于外部资源的排他边界。不同 PR、分支、Git 引用或运行任务可能仍然争用同一个固定域名、代理名、端口、部署 / 评审槽位、临时数据库、单例服务或受限账号资源。

当外部操作会取得或修改共享资源时，应先识别真实冲突域，再选择并发组、锁、租约或等价机制：

- 同一资源的所有触发路径与 Git 引用必须进入同一排他边界，不能只按 PR / Git 引用分组而留下跨组竞争；
- 不共享资源的运行应保留合理并行能力，不能把仓库级单例机械推广为所有工作流的固定政策；
- 长生命周期单实例环境应定义可观察的所有者、租约取得 / 续期 / 到期 / 释放条件和过期判定；自动验证与人工复核可以按用途采用不同保活生命周期；“保护仍在进行的人工评审”和“让最新提交取得验证环境”是不同目标，应由使用方仓库策略显式决定优先级，不能机械采用 `latest-head-wins`；
- 排他边界只回答“谁不能同时使用资源”，不自动决定竞争运行任务应排队还是取消；只有新运行任务确实取代旧工作，且取消后的资源释放闭环可靠时才使用取消机制，否则应让独立工作有界排队；
- 取消工作流、终止本地进程或成功取得锁，只能证明对应动作发生，不能单独证明外部资源已经释放、归属正确或目标服务可用；
- 对残留资源采用有界等待、重试、释放或接管路径，并在清理前核对资源标识、当前所有者、租约 / 活跃状态、环境与操作授权；释放或接管机制应可审计、使用最小权限，并在一次性机制完成后清理；不得盲目清理生产资源、仍处于有效人工评审租约的资源、其他所有者的资源或授权范围外的共享状态；
- 取得资源后重新读取其当前归属和状态，并验证目标地址、服务或结果确实对应当前运行任务、目标提交和预期环境。

并发与资源生命周期应形成：

```text
识别共享资源
→ 匹配排他范围
→ 带归属地取得或释放
→ 验证目标状态
```

具体实现由使用方仓库、平台能力与资源拓扑决定。本指南不固定并发键，也不要求所有使用方项目使用同一种锁或清理策略。

### 5.3 区分临时执行证据与已接受持久输入

工作流产物、远程任务输出、临时快照或其他执行产物，默认可以承担一次运行的证明、传输、诊断或审查职责。它们具有明确的来源运行与目标提交关联，但可能受保留期限、过期、平台可用性或访问权限限制，不能因此自动成为使用方项目的长期运行输入或仓库权威。

当其中的数据、资源或配置被适当的人工 / 产品权威接受，并将被后续稳定重放、迁移、评审或运行流程持续消费时，应执行显式晋升：

```text
临时执行证据
→ 权威接受
→ 晋升为已接受持久输入
→ 验证完整性与来源关系
→ 重新取得受影响的当前证据
```

具体要求：

- 接受必须来自当前使用方仓库权威允许确认该内容的职责；产物上传成功、下载成功或一次复核通过不会自动完成权威晋升；
- 只晋升后续消费者真正需要的已接受内容，不要求把所有日志、诊断文件、临时快照或完整工作流输出版本化；
- 持久输入应进入使用方可长期发现和维护的权威 / 版本化来源，具体目录、格式、拆分方式和存储介质由使用方决定；
- 保留足以追溯内容身份与接受来源的来源关系，例如来源运行、提交 SHA、产物 ID / 名称、内容摘要、生成规则或等价锚点，并在复制、解包、规范化或重组后核对完整性；
- GitHub Actions 产物等临时载体可以继续作为历史证据或来源锚点，但长期消费者不得把即将过期或不可稳定取得的临时对象作为唯一输入；
- 晋升如果改变仓库目标提交、输入内容、工作流、导入器、评审环境或其支持的证据声明，应在最终目标状态重新取得相匹配的当前证据；
- 如果执行产物只具有历史证明或短期诊断价值，不应为了形式完整性晋升为长期权威；
- 敏感数据、第三方许可、体积成本或保留义务会影响持久化时，按当前安全、隐私、法律与仓库策略升级或选择合适载体。

## 6. 汇报：只汇报已验证状态

汇报应描述当前已验证状态，而不是仅描述执行过的动作。

状态应区分：

- **已验证**：目标状态已确认；
- **已执行但未完全验证**：已执行但未完成足够验证；
- **受阻**：尚未执行或无法继续；
- **失败**：执行后目标未成立。

不要使用模糊表达掩盖验证状态。

## 7. 外部交互语言一致性

除非仓库策略、外部平台规范或用户明确要求其他语言，`agentic-dev` 面向人的外部协作内容使用自然中文。

包括：

- PR 标题和说明；
- Issue 标题、正文和评论；
- Git 提交的摘要部分；
- 复核评论；
- AI 复核和人工复核摘要；
- 状态汇报与人工决策说明。

代码标识符、文件名、路径、API / CLI 参数、Skill 调用名、外部正式产品 / 协议名称和必须精确匹配的固定值保持原样。

不再把稳定中文概念机械附带英文当作“精确表达”。完整规则见 `docs/guides/terminology-guidelines.md`。

## 8. GitHub 协作模式

### 8.1 Git / GitHub 执行路径选择

Git 分支是隔离机制，PR 是 GitHub 提供的协作与集成对象。二者都属于具体仓库 / 平台能力，不是通用方法的强制对象。

在 GitHub 使用方项目中选择执行路径时，不应只判断“是否能够直接写默认分支”，还应同时检查：

- **隔离性**：未完成工作是否会污染共享权威基线；
- **可逆性**：失败或方向调整时能否低成本恢复；
- **证据可观察性**：当前运行环境能否重新取得验证和 CI 结果；
- **仓库策略**：是否要求分支、PR、复核或特定 CI 触发方式；
- **工作风险与持续时间**：是否需要多轮实现、验证、调试或人工复核。

对于需要多轮修改、CI、调试或复核的工作，如果直接修改共享默认分支会降低隔离性、可逆性或证据可观察性，应优先采用当前仓库 / 运行环境支持的隔离路径。

在 GitHub 中，常见路径是：

```text
任务或功能分支
→ PR
→ GitHub Actions
→ 当前证据
→ 已具备进入集成决策的条件
→ 人工权威或仓库策略
```

PR 可以同时提供变更复核、CI 触发、证据关联和集成边界。因此，当当前 GitHub 运行环境对 PR 触发的 Actions 可观察性明显优于 `push` 触发的 Actions 时，Agent 可以优先选择该路径。

这不是“所有 GitHub 项目必须使用 PR”的通用规则。如果仓库策略允许直接推送，且当前运行环境能完整取得当前验证证据，低风险工作仍可以采用更轻量路径。

当 GitHub Actions 验证本身需要进一步设计、诊断或优化时，可按条件使用 `github-actions-verification`；本指南只定义协作与授权边界，不承载具体工作流、容器或镜像实现方案。

### 8.2 PR 复核

```text
读取仓库权威
→ 读取 PR 状态
→ 读取变更文件和差异
→ 判断
→ 执行授权修改
→ 重新读取 PR
→ 验证
→ 汇报
```

### 8.3 仓库修改

```text
读取当前状态
→ 修改
→ 重新读取
→ 验证
→ 汇报
```

### 8.4 Issue / 证据更新

```text
读取 Issue
→ 修改
→ 重新读取 Issue
→ 验证
→ 汇报
```

## 9. 与现有治理规则的关系

本指南落实已有规则，而不替代它们：

- 仓库权威；
- 证据先于结论；
- 人工升级；
- 集成授权；
- Git 提交规范；
- 中文表达与术语规范。

如果外部操作暴露方法、契约或 Skill 问题，应按现有权威顺序处理，不得通过一次操作暗中改变规则。
