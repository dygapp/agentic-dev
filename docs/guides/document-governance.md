# 长期知识健康治理

本文面向普通软件项目，帮助人和 AI 判断什么时候需要主动检查存量知识、如何判断知识健康，以及发现问题后应返回哪项责任。项目事实、维护权限、评审周期、严重程度与具体报告格式均由 Consumer 自己拥有；本文不是固定目录规范、运行时编排器或独立 Skill。

## 1. 日常维护与项目健康评审

普通局部变更继续由实际需求、设计、执行和复核责任更新受影响的长期知识，不为每次修改增加全仓扫描、报告、文档、Execution Unit 或全量测试。

当项目显式安排维护、里程碑评审、周期检查或风险专项时，可以独立检查当前知识，即使没有拟集成的变更。项目可在自身维护约定中明确入口、权限和必要产出；不需要统一周期或常驻调度。

| 当前目标 | 适合的检查范围 |
| --- | --- |
| 上次评审基线可靠，关注后续变化 | 实际差异及受影响的知识、实现和消费者；证实无变化时可快速结束 |
| 需要理解整体健康、没有可靠基线 | 从现行能力及权威入口建立有界覆盖视图，按风险深查，其余抽样并说明未查范围 |
| 怀疑某个契约、职责、失败或安全问题 | 围绕具体声明、真实 owner、实现、验证和消费者定向检查 |
| 已有拟集成的高影响权威重组 | 使用 `review-change` 独立复核精确变更及必要权威链，不把只读健康评审当作变更验收 |

没有可靠基线不等于没有变化。多仓项目按实际拓扑识别各参与仓库及精确状态，不能以项目仓干净或一个 PR 的差异覆盖全部组件；不可访问的仓库和未检查范围保留为限制。

## 2. 什么是健康的长期知识

知识的组织和细化深度应匹配业务责任、复杂度、成熟度、风险和实际消费者，而不是文档行数、固定层级或目录对称性。总体目标与能力边界、模块职责、必要行为与设计、实现和验证应可以双向追溯；跨模块共同规则有实际 owner。

| 观察角度 | 需要判断的问题 |
| --- | --- |
| 归属与层次 | 是否存在竞争的当前真值、职责混杂、无消费者的文档、孤立能力或不清晰的导航？ |
| 细化程度 | 同层能力是否遗漏已确认的关键行为、失败、安全与验收义务，或越过上层边界、过早设计无依据的机制？合理的复杂度差异不算缺陷。 |
| 当前性 | 已确认要求、设计目标、实际实现、验证证据与正式验收是否被混淆？历史研究是否被误作现行约束？ |
| 语义与追溯 | 权威、稳定接口、状态/失败、安全规则、实现及验证是否一致？在确有替换或独立消费者需要时，能否在不依赖被替换实现的情况下恢复必要契约？ |
| 消费与维护 | 实际路径、锚点、跨仓引用、机器可读契约和测试是否仍可消费？派生评审材料能否按适用版本从真实 owner 再生？ |

例如在预约系统中，已有复杂改约行为却缺少取消失败语义，与简单且已完整描述的查询功能不是同一种情况；为尚未确认的业务预先引入多层审批则可能是过度细化。链接检查通过只能说明部分导航可达，不证明这些语义成立。

## 3. 将发现返回真正责任

健康评审默认只读。报告可以是 Consumer 采用的任何有界形式；至少让人能够判断检查的目标、范围及基线、发现的位置和证据、影响、归属、优先级、最小处置与未核验范围。无本地报告模板时也能直接给出结果。

| 发现 | 后续责任 |
| --- | --- |
| 已确认知识未进入长期 owner，或旧入口、重复、历史内容误用 | 按 Consumer 维护程序恢复唯一 owner 与实际消费者；先确认权限 |
| 真实产品规则、需求缺口或冲突 | Requirement owner，按需 `specify` 或 `establish-requirement-baseline`；代码现状不自动成为已确认规则 |
| 真实系统性结构或稳定设计缺口 | Architecture / Design owner，按需 `clarify-architecture` 或 `technical-plan`；参见[长期设计知识](design-knowledge.md) |
| 实现偏差或过时验证合同 | 返回适用实现或验证责任，先依据当前权威确定哪一侧需要修改 |
| 需要人工确认的长期语义 | 按需 `human-review`；评审投影不是第二套权威，确认结果回真实 owner |
| 证据不足、owner 不明或权限不足 | 明示受影响的结论和最小待决责任，不自动补规则或宣布通过 |

获得整改授权后，优先最小迁移与修复，保全有效语义、稳定路径及实际消费者。当前有效事实可以由 Markdown、IDL、Schema、代码契约或测试等合法载体持有，不为统一外观强制转写。高影响重组使用 `review-change` 的独立权威链复核及适用的有界再生性挑战；其他改动按真实范围验证，按需使用现有执行和收敛能力。只读评审不模拟实施收口，整改不自动升级为业务重构或外部写入授权。

## 4. 渐进形成与人工评审

建立需求基线时可以从总体目标向能力及具体行为逐层收敛，并比较同一语义层的覆盖与深度；局部 Specification 只检查当前影响范围。设计只固化有长期约束价值的决定。人工可以按层审阅职责划分、必要覆盖和取舍，而非逐字段确认或要求未来所有功能一次设计完整。

需要人工裁决时使用[人工评审](human-review.md)；确有长期设计形成时使用[长期设计知识](design-knowledge.md)。有界覆盖视图、研究对照和评审投影只是导航、讨论或验证材料，不因为内容丰富自动成为长期事实。

项目可按真实维护经验调整自己的健康评审入口与约定。如果缺少可重复执行能力，应先观察现有方式的遗漏、误判、人工介入和维护成本，再判断是否需要独立 Skill，而非复制本 Guide 作为另一套运行时。
