# 基于本地 Docker 的自动化验证

本文帮助 Consumer 在持久本地环境中用 Docker 建立可重复的构建、集成、E2E 等自动化验证路径，并控制镜像与构建缓存占用。它可以独立承担项目选定的 CI 验证，不要求 GitHub、GitHub Actions、GHCR 或 PR；与[GitHub Actions 自动化验证](github-actions-automated-verification.md)是可选择的对应路径。项目自己的 Authority 决定要验证什么、哪些证据足够、是否仍有其他集成检查要求。

本文是按需方法向导，不提供通用 Docker 编排器、固定组件清单或强制脚本接口。Dockerfile、测试命令、组件依赖、缓存预算、数据集、镜像命名和宿主权限由 Consumer 持有；具体实现与验证仍由当前变更的执行责任和已安装 Skills 承担。

## 1. 从验证声明和运行环境开始

先把当前变更需证明的构建、测试、运行时、数据初始化和浏览器行为映射到仓库已有命令，区分快速反馈与最终完成证据。本地路径可以代替 GitHub Actions 执行这些计算，不是给 Actions 做预热；但缓存命中、镜像存在或容器启动不能替代本轮仍需运行的测试。

Consumer 应为所选择的验证责任提供可重复调用的本地入口，例如仓库脚本、任务命令或 Docker Compose 组合；入口能从声明的输入建立环境、执行检查、给出终态和诊断，并在再次运行时不依赖上次遗留的可写测试状态。不要求所有项目采用同一命令名称或机器可读 schema。

每次运行记录实际源码 subject：已有提交时记录仓库身份与精确 commit；含未提交差异时记录工作区状态与实际构建输入，不把 HEAD 冒充脏工作区。非 GitHub 仓库使用自己的版本身份或可复核的源码快照身份。跨多个独立仓库的验证记录参与仓库的精确组合，而不是依靠共同父目录推断版本。

在构建前确认 Docker context / daemon、所选 builder、可用磁盘、已有镜像与缓存占用，以及是否与其他项目共用宿主。`docker system df -v` 用于观察 daemon 的镜像、容器和卷；`docker buildx du --builder <builder>` 用于观察指定 builder 的缓存。两者统计对象不同，镜像大小也可能包含共享层，不能把各行显示值简单相加当作实际可回收空间。

具体用量字段见 Docker 的 [daemon 磁盘用量](https://docs.docker.com/reference/cli/docker/system/df/)与 [builder 缓存用量](https://docs.docker.com/reference/cli/docker/buildx/du/)说明。

## 2. 按真实输入复用组件

将验证环境拆成确有独立变化边界的组件，例如前端、后端和可重建的数据库验证基线；不为了套用此例强制拆仓或拆镜像。每个可复用组件的身份应覆盖会影响产物的真实输入，包括适用的源码、构建定义、依赖锁定、构建参数、基础镜像版本或 digest、目标平台，以及数据库 schema、导入工具与验证数据定义等相关依赖。可变外部输入未被固定或纳入身份时，不报告确定的缓存命中。密钥不作为可公开的身份内容或镜像元数据。

本地 CI 对每个组件按以下关系处理：

```text
输入未变化且已有匹配的已验证镜像 → 复用该镜像
输入变化或匹配状态无法确认 → 构建候选 → 验证候选
候选通过 → 作为新的当前版本 → 清理不再被使用的旧版本
候选失败 → 保留上一个可用版本，失败候选按诊断需要有界保留
```

例如只修改前端且后端、schema、导入数据及其构建输入未变化时，可以复用后端镜像与数据库预备基线，只重建前端。数据库基线可用确定性迁移和测试数据生成镜像或快照，避免每次重复导入；每轮测试仍从该基线建立隔离、可丢弃的数据库状态，不能长期沿用已被上轮测试改写的共享 writable volume。

缓存命中只影响构建工作量。本轮前端与后端接缝、E2E 或其他验收是否仍需运行，由当前 claim 决定。并行验证、正在使用的容器或有效人工复核可能暂时引用旧镜像；“保留当前版本”是稳态目标，不是强行删除正在使用的资源。

## 3. 让稳态磁盘占用保持有界

先减少新垃圾：用 `.dockerignore` 缩小构建上下文，按实际依赖组织层，必要时用多阶段构建减少最终镜像。验证完成后清理本轮可丢弃的 container、network、volume 和临时输出；失败诊断需要的资源只保留明确期限。镜像层可能共享，删除一个旧 tag 不保证立即回收其显示的全部大小。

构建层与上下文的优化方式见 Docker 的[构建缓存优化指南](https://docs.docker.com/build/cache/optimize/)；多阶段构建也不等于自动清理 builder 内历史缓存。

日常清理以组件为单位：新候选验证通过后确认当前镜像身份，再移除没有运行中引用、也不再承担有效复核责任的被替代镜像。可运行镜像与 BuildKit 构建缓存分开处理；通常保留各组件最近的有效镜像和有助于增量构建的有界热缓存，而不是每次验证后清空缓存。Consumer 根据磁盘预算与实测重建耗时选择 builder 的容量、保留时间或按需清理策略。

BuildKit 缓存属于所选 builder，镜像上的项目标签并不能自动实现共享 builder 的项目级缓存清理。如果共享 daemon 上必须能单独清掉某项目的构建缓存，可为该项目选择专用 builder；这会减少跨项目缓存共享，且由 Consumer 维护 builder 的自身状态。清理前后分别观察镜像与 builder 占用，不能只根据清理命令成功就声称磁盘目标已达到。

builder 的定期垃圾回收与手动清理范围见 Docker 的 [BuildKit GC](https://docs.docker.com/build/cache/garbage-collection/)和 [`buildx prune`](https://docs.docker.com/reference/cli/docker/buildx/prune/)说明。

## 4. 显式彻底清理

当磁盘压力高于下次重建成本时，可以主动放弃热缓存与当前本地镜像。先确认操作对象、是否有正在使用的验证或评审环境、后续能否从源码和受控输入重新建立；再按项目镜像的精确身份清理，并对项目专用 builder 使用 `docker buildx prune --builder <builder> --all` 清理可回收缓存。清理后重新观察剩余对象和磁盘用量，不把 `--all` 解释为能删除仍被引用的一切内容。

`docker system prune -a --volumes` 是作用于整个 daemon 的宿主级清理，不是项目级“彻底清理”的同义词。在专用宿主或宿主 owner 明确选择全局清理时可以使用；共享 daemon 上不能因当前项目希望省空间，就默认清掉其他项目的资源。该命令也不等于抹除所有正在运行的容器或所有命名卷。此路径接受后续重新拉取、导入与构建的时间成本，但不把无法重建的共享数据误称为缓存。

全局命令的实际清理对象以 Docker 的 [`system prune` 文档](https://docs.docker.com/reference/cli/docker/system/prune/)为准，不把 `--volumes` 理解为自动删除所有项目数据。

WSL / Docker Desktop 的宿主虚拟磁盘回收与 Docker 对象清理是不同责任；Docker 可回收空间减少，不自动证明 Windows 宿主文件已按相同字节数缩小。宿主级维护由其 owner 按平台实际情况另行处理。

## 5. 用实际迭代检验复用与清理

Consumer 先记录镜像、builder 缓存和剩余磁盘的基线，再按真实项目选择有界样例：相同输入重跑应命中可复用组件；只改前端时不重建未变化的后端与数据库基线，但仍运行受影响的集成验证；后端或数据库输入变化时只使对应依赖失效；候选失败不替换当前有效镜像；多轮成功重建后旧镜像与临时资源不持续累积。最后比较日常清理和显式彻底清理前后的占用与下一轮重建耗时。

具体容量预算、迭代次数和可接受重建时间由 Consumer 根据宿主和验证规模决定。单次命中或清理命令退出码为零，不能证明长期磁盘占用有界；无法观察到 builder / daemon 的真实占用时保留未验证结论。

## 6. 本地证据与失败处理

本地验证结果至少能对应目标源码或工作区、组件输入身份与实际使用的镜像、执行的命令、退出状态、关键日志 / 报告及清理后的资源状态。工作区中的日志和未提交差异是当前执行态证据；若结论需要跨上下文恢复，由 Consumer 选择持久位置及必要完整性信息。没有 GitHub Run 不降低证据要求，也不需要伪造 Actions 状态。

意外失败先区分实现缺陷、过期验证断言、Docker / 数据库环境和外部依赖，再进入 `systematic-debug`。`execute-unit` 或有界直接变更负责当前实现与验证，`converge` 按 Consumer Authority 判断全部验收是否已被当前证据覆盖。Docker 可用不授予共享宿主清理、生产发布或部署权限。

## 7. 发布边界

未来若 Consumer 使用 Docker 发布，可以复用适用的构建技术，但发布产物的身份、留存、Registry、回滚和部署授权与本地验证缓存不同。本 Guide 不设计生产镜像生命周期，也不允许把本地验证的自动清理规则直接套用于发布产物。
