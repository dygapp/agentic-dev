# AI 开发方法原则

**状态：** 基线 v0.1  
**性质：** 规范性文档

本文定义所有方法阶段和技能必须遵守的顶层原则。

## P1. 阶段是状态，不是文档

开发阶段描述当前工作所处的状态以及正在解决的问题。

阶段存在，并不意味着必须创建一份独立 Markdown 文档。

只有当信息具有独立的协调价值、权威价值、可追溯价值或长期知识价值时，才应持久化。

## P2. 需求事实与实现选择分离

统一采用：

```text
规格说明 = 做什么 / 为什么
技术计划 = 如何实现
```

规格说明负责：

- 必须实现的行为；
- 范围；
- 边界；
- 验收标准；
- 必要的非功能约束。

技术计划负责：

- 技术路线；
- 架构映射；
- 契约；
- 数据设计；
- 迁移；
- 技术接缝；
- 测试策略。

实现方案发生变化，不应自动改写需求。

## P3. 持久化知识，不持久化推理过程

会话、临时推理、探索过程和临时实现计划都不是长期项目事实。

需要长期保留的信息，应进入合适的权威载体，例如：

- 仓库规则；
- 项目路线图（满足跨里程碑 / 阶段 / 新上下文的长期协调与恢复条件时）；
- 领域上下文 / 术语表；
- 架构上下文；
- ADR；
- 规格说明；
- 必要的技术计划；
- 代码 / 测试。

其中，项目路线图只承载项目整体的已完成里程碑、当前阶段 / 核心目标、已决定的下一步和条件性方向，不替代功能规格说明、技术计划或临时任务计划；ADR 只用于保留需要跨功能长期约束后续工作的架构决定及其关键理由，不用于记录普通局部实现选择或尚未收敛的探索过程。

没有长期价值的信息可以随上下文一起结束。

## P4. 上下文容量是执行约束

执行单元必须控制在一个新上下文 Agent 可以完成以下全过程的范围内：

1. 理解；
2. 检查当前仓库状态；
3. 实现；
4. 验证。

该属性称为 **上下文适配（`context-fit`）**。

## P5. 优先纵向、可验证的工作单元

执行单元应尽量形成窄而完整的端到端行为，并满足：

- 纵向；
- 可独立验证；
- 边界明确；
- 可追溯；
- 上下文适配；
- 低隐藏依赖。

能够形成纵向切片时，不应默认拆成“数据库 → 后端 → 前端 → 测试”的横向阶段。

## P6. 新上下文是逻辑属性

新上下文（`Fresh Context`）不绑定某一种产品功能。

可以通过：

- 新聊天；
- 子 Agent；
- 新 CLI 会话；
- 隔离执行者；
- 临时 Agent；

等方式实现。

其核心判定标准是：

> 当前执行 Agent 不依赖此前未持久化的推理历史。

## P7. 使用渐进式披露

不要给每个执行 Agent 加载全部项目文档。

默认只加载：

- 仓库规则；
- 当前执行单元；
- 相关规格说明片段；
- 相关技术计划决定；
- 相关架构 / ADR / 领域上下文；
- 相关代码 / 测试。

## P8. 证据先于声明

任何状态声明都必须有当前证据。

例如：

- “构建通过”必须有当前构建结果；
- “测试通过”必须有当前测试结果；
- “API 可用”必须有当前行为验证结果。

当前证据必须能追溯到所声明完成的必需行为 / 验收义务，并足以区分该义务是否真实满足。

以下关系不能自动成立：

```text
实现存在 ≠ 验证覆盖
计划证据 ≠ 已执行的当前证据
主路径通过 ≠ 执行单元负责的全部验收义务已闭环
```

历史测试、代码阅读或其他 Agent 的无证据声明不能证明当前状态。

## P9. 人工升级依据权限、影响、可逆性

不能因为“存在歧义”就默认升级给人。

当一个选择：

- 影响局部；
- 可以安全回滚；
- 不改变外部可观察业务行为；
- 不超出 Agent 授权；

Agent 应自主作出合理裁决。

以下情况需要升级：

- 改变产品意图或范围；
- 多种选择产生不同用户可观察行为；
- 数据操作不可逆或难以恢复；
- 安全 / 隐私敏感；
- 重大架构方向；
- 权威来源冲突；
- 超出授权的共享 / 生产 / 外部副作用。

简化表达：

> **人工负责不可逆的意图决策；AI 负责可逆的执行判断。**

## P10. 验证、复核、收敛必须分离

**验证：** 当前事实是什么？

**复核：** 这个实现本身是否正确、合理、高质量？

**收敛：** 整个功能是否最终符合权威意图？

不能把三者统一模糊为“复核”。

## P11. 技术规划是条件阶段

技术规划（`Technical Planning`）只有当规格说明无法直接、安全地映射到当前架构时才进入。

典型触发包括：

- 跨模块工作；
- 新数据模型；
- 新外部集成；
- 迁移；
- 公共契约变更；
- 部署拓扑变化；
- 重大架构权衡。

小型、常规、已有稳定实现模式的修改可以直接进入工作切分。

技术规划需要同时判断其中形成的长期技术决策是否已经超出当前功能的协调范围并形成长期架构权威；只有满足 ADR 条件的决定才单独持久化为 ADR。

## P12. 长期技术设计与即时执行计划分离

技术计划（`Technical Plan`）是按需持久化的设计协调产物，主要服务当前功能或一组执行单元的长期“如何实现”协调。

即时执行计划（`JIT Execution Plan`）是 Agent 在查看当前代码状态后生成的临时施工计划，可以包含：

- 当前相关文件路径；
- 精确测试命令；
- 具体编辑顺序。

默认不作为长期项目知识保存。

跨功能、需要长期约束后续工作的重大架构决定不应只埋在技术计划或即时执行计划中；应按 P15 评估并进入适当的架构 / ADR 权威。

## P13. 技能必须小型、可组合

一个技能只承担一个清晰、可复用的职责。

禁止创建自动接管以下完整生命周期的超级技能：

```text
澄清
→ 规格说明
→ 规划
→ 执行全部工作
→ 收敛
→ 合并 / 发布
```

工作流转换必须保持可观察、可控制。

## P14. 集成是授权边界

通用方法的终点是：

> **已具备进入集成决策的条件（`Ready to Integrate`）**

提交策略、合并、推送、PR、发布、部署和破坏性清理由仓库策略或人工权威决定。

## P15. ADR 是条件性长期架构权威

架构决策记录（`Architecture Decision Record`，ADR）不是方法阶段，也不是技术计划的同义词。

一个技术决定只有在需要跨越当前功能持续约束后续工作，并且保留其选择理由、主要权衡或替代关系具有长期价值时，才应形成或更新 ADR。

典型信号包括：

- 约束多个未来功能、模块或独立工作流；
- 改变系统级组件、数据、集成、部署或共享契约边界；
- 替换成本高、难以安全回滚，或形成长期兼容 / 迁移义务；
- 多个合理方案具有实质不同的长期后果；
- 缺少该决定会导致后续 Agent 反复重新决策或产生冲突实现。

以下内容不应为了形式完整性创建 ADR：

- 只服务当前功能的普通技术计划决定；
- 单个执行单元内低影响、可逆的局部实现选择；
- 即时文件、命令或编辑细节；
- 尚未收敛的探索与推理过程。

ADR 的创建、更新与取代仍受仓库权威和人工升级规则约束。重大架构方向或高影响、难逆的权衡必须按权限、影响、可逆性升级；新 ADR 取代旧 ADR 时，应显式保留被取代 / 替换关系。
